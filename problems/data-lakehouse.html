Design a Data Lakehouse

Design a unified data platform that combines the best of data lakes (low-cost object storage, schema flexibility) and data warehouses (ACID transactions, SQL queries, performance) — the architecture behind Databricks Lakehouse, Apache Iceberg, and Delta Lake.

Hard Data Platform Asked at: Databricks, Snowflake, Netflix

1. Requirements

Functional Requirements

  • ACID transactions on object storage — Support concurrent reads and writes on Parquet files stored in S3/GCS with full ACID guarantees (atomicity, consistency, isolation, durability).
  • Schema evolution — Tables can evolve their schema (add columns, rename, reorder) without rewriting existing data. Readers see a consistent view.
  • Time travel — Query data as of any previous version. Enables auditing, debugging, and reproducible ML training.
  • SQL queries — Support standard SQL queries with query planning and optimization. Queries run against the latest committed version of the table.
  • Streaming ingestion — Ingest real-time data streams (Kafka) with exactly-once semantics and low-latency queryability.

Non-Functional Requirements

  • Scale: Support petabytes of data, billions of rows per table, thousands of concurrent queries.
  • Performance: Interactive queries (<10 seconds) on recent data. Full scans of historical data in minutes.
  • Cost efficiency: Store data on cheap object storage ($0.023/GB/month for S3) rather than expensive SSDs.
  • Open format: Data stored in open formats (Parquet) so it's not locked to a single vendor.
Interview Tip: This is the most Databricks-specific question you can get. The core insight is: how do you get ACID transactions on eventually-consistent object storage like S3? The answer is a transaction log (Delta Log / Iceberg metadata) that serializes all commits as ordered JSON files. The log is the single source of truth; Parquet files are just data.

3. API Design

SQL CREATE TABLE / INSERT / SELECT / MERGE

Standard SQL interface for all operations:

-- Create a table (stored as Parquet in S3)
CREATE TABLE events (
  event_id BIGINT,
  user_id BIGINT,
  event_type STRING,
  properties MAP<STRING, STRING>,
  event_time TIMESTAMP
) USING delta
LOCATION 's3://lakehouse/events/'

-- Streaming ingestion with exactly-once
INSERT INTO events
SELECT * FROM kafka_source
WHERE batch_id = {current_batch}

-- Time travel query
SELECT * FROM events VERSION AS OF 42
SELECT * FROM events TIMESTAMP AS OF '2024-01-15 10:00:00'

-- Schema evolution
ALTER TABLE events ADD COLUMN device_type STRING AFTER user_id

5. High-Level Design

Architecture Overview

Data Lakehouse Architecture
graph TD STREAM[Kafka Streams] --> INGEST[Ingestion Service] BATCH[Batch Sources] --> INGEST INGEST --> S3[S3 Object Storage] INGEST --> LOG[Transaction Log] SQL[SQL Queries] --> PLANNER[Query Planner] PLANNER --> LOG PLANNER --> OPT[File Pruning & Stats] OPT --> S3 S3 --> EXEC[Spark Executors] EXEC --> RESULTS[Results] LOG --> CHECKPOINT[Checkpoint Service]

ACID Transaction Flow

Write Transaction (Optimistic Concurrency)
graph TD W1[Writer A reads current version: 42] --> W2[Writer A writes Parquet files to S3] W2 --> W3[Writer A attempts to commit: 000043.json] W3 --> LOCK{Acquire commit lock} LOCK -->|Got lock| VERIFY{Version still 42?} VERIFY -->|Yes| COMMIT[Write 000043.json, release lock] VERIFY -->|No| CONFLICT[Conflict! Retry from new version] LOCK -->|Lock held| WAIT[Wait and retry]
Why Optimistic Concurrency? S3 doesn't support locks, so we use optimistic concurrency control (OCC). Writers read the latest version, do their work, then try to commit. If another writer committed first (version changed), the writer must retry. This works well because most writes are to different partitions and rarely conflict. When they do conflict, the retry is cheap (just re-commit the files with the new version number).

6. Deep Dive

Data Skipping with Statistics

Each commit JSON includes min/max statistics for every column in every file. When a query includes a WHERE clause, the planner reads these statistics to skip files that cannot contain matching data.

-- Query: SELECT * FROM events WHERE user_id = 42

-- Planner reads commit log:
-- File 1: min(user_id)=1,   max(user_id)=100   → INCLUDE (42 is in range)
-- File 2: min(user_id)=200, max(user_id)=300   → SKIP
-- File 3: min(user_id)=10,  max(user_id)=50    → INCLUDE

-- Result: Only 2 of 3 files scanned = 33% I/O savings

Compaction & Z-Ordering

File Compaction Process
graph TD S1[Small Files: 10MB each] --> COMPACT[Compaction Job] COMPACT --> L1[Large Files: 128MB each] L1 --> ZORDER[Z-Order by (user_id, event_time)] ZORDER --> OPTIMIZED[Optimized Files] OPTIMIZED --> COMMIT2[New commit in log]

Checkpoints for Fast Startup

Without checkpoints, a reader would need to replay all 10 million commit JSON files to determine the current state. Checkpoints are periodic snapshots (every 10 commits) that aggregate all changes into a single file. A reader loads the latest checkpoint + any commits after it.

7. Trade-offs

DecisionOption AOption BRecommendation
Table Format Delta Lake: Transaction log as ordered JSON. Simple. Databricks-native. Large log growth without checkpoints. Apache Iceberg: Manifest files + metadata layers. More complex. Better for multi-engine access (Spark, Trino, Flink). Both are viable. Delta Lake for Databricks-centric workloads. Iceberg for multi-engine environments. The concepts are similar.
File Size Large files (128MB+): Fewer S3 requests. Better scan throughput. Higher write latency (must buffer). Small files (10MB): Lower write latency. More S3 requests. Compaction overhead. Use small files for streaming writes (low latency), then compact to 128MB in background jobs. Best of both worlds.
Isolation Level Serializable: Strongest. Writers always conflict-check. Lower throughput. Snapshot isolation: Readers see consistent snapshot. Writers only conflict on same files. Higher throughput. Use snapshot isolation (default in Delta/Iceberg). Most workloads don't need serializable. Writers only conflict if they modify the same files.
