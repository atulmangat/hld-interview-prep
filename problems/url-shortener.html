Design URL Shortener (TinyURL)

Design a highly available service that converts long URLs into short, unique aliases and redirects users with minimal latency.

Medium URL / Web Infrastructure Asked at: Google, Amazon, Meta, Microsoft, Bloomberg, Uber

1. Requirements

Functional Requirements

  • Shorten URL: Given a long URL, generate a unique, short alias (e.g., https://tiny.url/a1B2c3D).
  • Redirect: When a user visits the short URL, redirect them to the original long URL.
  • Custom Alias: Users can optionally provide a custom short key (e.g., /my-brand-link). The system must validate uniqueness.
  • Expiration: URLs can have an optional TTL. Expired URLs return 404. Default expiration is 5 years.
  • Analytics (optional): Track click count, referrer, geo-location, and device type per short URL.
  • Delete URL: Authenticated users can delete their own short URLs.

Non-Functional Requirements

  • High Availability: The redirect path is read-heavy and must be 99.99% available. Downtime = lost revenue for customers.
  • Low Latency: Redirect (read path) must complete in <100ms at p99. Users should not perceive any delay.
  • Scale: Support 100 million new URLs created per day, with a 10:1 read-to-write ratio (1 billion redirects/day).
  • Uniqueness: Every generated short key must be globally unique. Collisions are unacceptable — a collision means a user gets redirected to the wrong page.
  • Durability: Once a URL mapping is created, it must not be lost. Data must survive hardware failures.
Key Insight: The read-to-write ratio (10:1 or higher) is the single most important characteristic of this system. It means the redirect path must be hyper-optimized — this is why caching dominates the design. A cache hit on redirect avoids a database round-trip entirely, dropping p99 latency from ~10ms (DB) to <1ms (Redis).

Short Key Length

How many characters do we need? Using Base62 (a-z, A-Z, 0-9):
62^6 = ~56.8 billion unique keys.
62^7 = ~3.5 trillion unique keys.
With 182.5 billion records over 5 years, 7 characters gives us ample headroom (~19x the required space). This is the standard choice.

3. API Design

POST

Request Body

{
  "longUrl":     "https://www.example.com/very/long/path?query=abc",
  "customAlias": "my-link",       // optional
  "expireAt":    "2028-12-31T23:59:59Z"  // optional, default = now + 5 years
}

Response — 201 Created

{
  "shortUrl":  "https://tiny.url/a1B2c3D",
  "shortKey":  "a1B2c3D",
  "longUrl":   "https://www.example.com/very/long/path?query=abc",
  "expireAt":  "2028-12-31T23:59:59Z",
  "createdAt": "2026-04-14T10:30:00Z"
}

Error Codes

  • 400 — Invalid URL format or custom alias contains disallowed characters.
  • 409 — Custom alias already taken.
  • 429 — Rate limit exceeded.

/{shortKey}

4. Data Model

URL Mapping Table

Column Type Description
id BIGINT / UUID Primary key (auto-increment or Snowflake ID)
short_key VARCHAR(16) The 7-char Base62 key. Unique index.
long_url VARCHAR(2048) Original URL
user_id BIGINT Owner (nullable for anonymous creation)
created_at TIMESTAMP Creation time
expires_at TIMESTAMP Expiration time (nullable = never expires)
click_count BIGINT Total redirects (denormalized counter)

SQL vs NoSQL

Criteria SQL (PostgreSQL / MySQL) NoSQL (DynamoDB / Cassandra)
Access pattern Simple key-value lookups work fine Optimized for key-value access — ideal fit
Scale Requires manual sharding at 182B records Horizontally scalable out of the box
Schema flexibility Rigid schema, migrations needed Flexible, easy to add attributes
Consistency Strong consistency (ACID) Eventual consistency (tunable in Cassandra)
Joins / relations Supported but not needed here Not supported — not needed here
Recommendation: NoSQL (DynamoDB or Cassandra) is the better fit. The access pattern is purely key-value (lookup by short_key), there are no joins, and horizontal scalability is critical at 182 billion records. DynamoDB with short_key as the partition key gives single-digit-millisecond reads at any scale. If you need strong consistency for custom alias uniqueness checks, DynamoDB supports strongly consistent reads.

5. High-Level Design

Architecture Overview

graph LR C[Clients - Browser / App] --> LB[Load Balancer - ALB / Nginx] LB --> APP1[App Server 1 - Stateless] LB --> APPN[App Server N - Stateless] APP1 --> CACHE[Cache Cluster - Redis] APP1 --> IDGEN[ID Generator - ZooKeeper Counter] APPN --> CACHE APPN --> DB CACHE -->|cache miss| DB[Database Cluster - DynamoDB / Cassandra] APP1 --> DB IDGEN --> APP1 IDGEN --> APPN

Write Flow — Creating a Short URL

1
Client sends POST /api/v1/shorten with longUrl and optional customAlias.
2
Rate Limiter checks per-user or per-IP request rate. Rejects with 429 if exceeded.
3
Input Validation: Verify the URL is well-formed (valid scheme, reachable domain). Sanitize custom alias (alphanumeric, hyphens only, 3-30 chars).
4
Key Generation: If no custom alias, the app server requests a unique ID from the ID Generator, then converts it to a 7-character Base62 string.
5
Collision Check (if hashing): Query the DB for the generated key. If it exists, regenerate. With counter-based approaches, this step is unnecessary.
6
Persist: Write the mapping (short_key, long_url, user_id, created_at, expires_at) to the database.
7
Cache Warm: Optionally write the mapping to Redis so the first redirect is fast.
8
Response: Return 201 with the full short URL to the client.

Read Flow — Redirecting a Short URL

1
Client sends GET /{shortKey}. The load balancer routes to any app server.
2
Cache Lookup: App server queries Redis with short_key. On cache hit (~90%+ of requests), return 302 immediately. Latency: <1ms.
3
Cache Miss → DB Lookup: Query the database by short_key. If found and not expired, populate the cache (TTL = 24h) and return 302.
4
Expiration Check: If expires_at is in the past, return 404 and optionally delete the cache entry.
5
Analytics (async): Fire-and-forget an event to a message queue (Kafka) with click metadata (timestamp, IP, user-agent, referrer). Do NOT block the redirect.

6. Deep Dive

6a. URL Shortening Approaches

The core challenge is generating a unique 7-character key for each URL. There are three major approaches:

Approach 1: Hash + Collision Resolution

Hash the long URL with MD5 or SHA-256, take the first 7 Base62 characters.

How it works
  1. Compute MD5(longUrl) → 128-bit hash.
  2. Take the first 43 bits (enough for 7 Base62 chars).
  3. Convert to Base62 → 7-char key.
  4. Check DB for collision. If collision, append a counter to the input and re-hash.
Pros
  • Same long URL always produces the same short URL (deduplication for free).
  • No centralized counter or coordination needed.
Cons
  • Collision resolution adds latency and complexity (worst case: multiple DB reads).
  • Deduplication breaks if users want different expiration dates for the same URL.

Approach 2: Base62 Counter (Pre-generated Range)

Use a global auto-incrementing counter. Each app server pre-fetches a range of IDs.

How it works
  1. A centralized service (ZooKeeper / DB sequence) assigns ID ranges to each app server (e.g., Server A gets 1M-2M, Server B gets 2M-3M).
  2. Each server increments locally within its range — no coordination per request.
  3. Convert the integer ID to Base62 → 7-char key.
Pros
  • Zero collisions — every ID is unique by construction.
  • No DB lookup needed before writing.
  • Very fast — local counter increment is O(1).
Cons
  • IDs are sequential — short URLs are predictable (security concern, can be mitigated with shuffling).
  • Range coordinator (ZooKeeper) is a dependency that must be highly available.
  • If a server crashes, unused IDs in its range are wasted (acceptable at this scale).

Approach 3: Snowflake ID

Use Twitter's Snowflake-style 64-bit ID: timestamp + datacenter + machine + sequence.

How it works
  1. Generate a 64-bit Snowflake ID (41 bits timestamp, 5 bits datacenter, 5 bits machine, 12 bits sequence).
  2. Convert to Base62 → produces an 11-char string. Truncate or use as-is.
Pros
  • Globally unique without coordination.
  • Time-sortable — useful for analytics.
  • Battle-tested at Twitter scale.
Cons
  • Produces longer keys (11 chars vs 7) unless truncated (which risks collisions).
  • Clock skew across machines can cause issues.
Recommended approach: Base62 Counter with pre-generated ranges. It guarantees zero collisions, requires no DB read before write, and is the simplest to reason about. Use ZooKeeper or a lightweight coordination service to assign ranges. This is the approach used by production URL shorteners.

6b. 301 vs 302 Redirects

Aspect 301 (Moved Permanently) 302 (Found / Temporary)
Browser caching Browser caches the redirect. Subsequent visits bypass your server entirely. Browser does NOT cache. Every visit hits your server.
Server load Lower — browsers handle repeat visits locally. Higher — every click goes through your infrastructure.
Analytics You lose visibility after the first click per browser. You see every single click — essential for analytics.
SEO Search engines transfer link equity to the destination URL. Link equity stays with the short URL.
Use when The mapping is permanent and analytics are not needed. You need click tracking, A/B testing, or the destination may change.
Recommendation: Use 302 by default. Most URL shortener use cases require analytics (click tracking), and 302 ensures every request flows through your servers. Offer 301 as an opt-in for users who prioritize performance over analytics.

6c. Caching Strategy

Redis is the caching layer between app servers and the database. It is critical for meeting the <100ms p99 latency requirement.

  • Cache key: short_key → long_url. Simple string-to-string mapping.
  • Cache TTL: 24 hours. Balances memory usage with hit rate. Hot URLs stay cached; cold URLs expire naturally.
  • Cache size: If 20% of URLs account for 80% of traffic (Pareto principle), caching the top 20% of daily active URLs is sufficient. At ~2M active URLs/day × 500B = ~1GB — easily fits in a single Redis node.
  • Eviction policy: LRU (Least Recently Used). Automatically evicts cold URLs when memory is full.
  • Write-through on creation: When a new URL is created, write it to both DB and cache. This avoids a cache miss on the first redirect.
  • Cache invalidation: On URL deletion or expiration, explicitly delete the cache entry to prevent stale redirects.

6d. Database Partitioning / Sharding

At 182 billion records over 5 years, a single database instance is not viable. We need horizontal partitioning.

Sharding Strategy: Hash-Based on short_key

  • Compute shard_id = hash(short_key) % N where N = number of shards.
  • This distributes data uniformly because short keys are already pseudo-random (Base62-encoded counters).
  • Lookups are O(1) — hash the key, go directly to the correct shard.
  • No hot spots because the hash function distributes evenly.

Replication

  • Each shard has 3 replicas across different availability zones.
  • Writes go to the primary; reads can go to any replica (eventual consistency is acceptable for redirects — a few seconds of delay for a brand-new URL is fine).

Resharding

  • Use consistent hashing to minimize data movement when adding/removing shards.
  • With DynamoDB, this is handled automatically — partition splits are transparent.

6e. Rate Limiting

Rate limiting protects the write path from abuse (spam URL creation, bot attacks).

  • Algorithm: Token bucket or sliding window counter, implemented in Redis.
  • Limits:
    • Anonymous users: 10 URLs / hour per IP.
    • Authenticated users: 1,000 URLs / hour per API key.
    • Enterprise tier: 100,000 URLs / hour.
  • Implementation: Redis key = rate:{user_id}:{window}, value = counter. Use INCR + EXPIRE for sliding window.
  • Read path: Generally not rate-limited (redirects should always work). Exception: DDoS protection at the load balancer level.

7. Trade-offs

Decision Option A Option B Recommendation
Hash vs Counter Hash-based: no coordination, but collisions possible Counter-based: zero collisions, but needs range coordinator Counter-based. Collision-free generation is worth the operational cost of ZooKeeper.
SQL vs NoSQL SQL: strong consistency, mature tooling, but manual sharding NoSQL: auto-scaling, key-value optimized, but eventual consistency NoSQL (DynamoDB). The access pattern is purely key-value, and auto-scaling is critical at 90TB+.
301 vs 302 301: lower server load, browser caches redirect 302: every click tracked, higher server load 302 by default. Analytics are a core feature. Offer 301 as opt-in.
Custom alias handling Allow any string: flexible but risks offensive/reserved words Restrict to alphanumeric + hyphens with blocklist: safer but less flexible Restricted with blocklist. Maintain a deny-list of reserved words (api, admin, health, etc.) and offensive terms.
Consistency vs Availability Strong consistency: no stale reads, but higher latency and lower availability during partitions Eventual consistency: faster reads, higher availability, but brief staleness window Eventual consistency for reads (redirects). Strong consistency only for custom alias uniqueness checks (conditional writes in DynamoDB).
Analytics: sync vs async Synchronous: accurate counts but adds latency to redirect Asynchronous (Kafka + batch processing): no redirect latency impact, but counts are delayed Asynchronous. Never add latency to the redirect hot path. Use Kafka → Flink/Spark → analytics DB.
Expiration cleanup Eager deletion: background job scans and deletes expired URLs Lazy deletion: check expiration on read, delete if expired Both. Lazy deletion on the read path (immediate user feedback) + periodic background cleanup job to reclaim storage.
