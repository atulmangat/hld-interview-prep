Design a Payment Authorization System

Design a payment authorization system like Visa/Mastercard that processes credit/debit card transactions in real-time, handling authorization, settlement, fraud detection, and high availability at the scale of 100,000+ transactions per second.

Hard FinTech Asked at: Databricks, Stripe, Visa

1. Requirements

Functional Requirements

  • Card authorization — When a merchant submits a transaction, the system must approve or decline in real-time (<500ms). It checks card validity, available balance, fraud signals, and velocity limits.
  • Settlement — After authorization, funds are held until settlement (typically end of day) when money actually moves between banks. The system batches and reconciles transactions.
  • Fraud detection — Real-time fraud scoring using ML models and rule engines to block suspicious transactions before authorization.
  • Transaction history — Cardholders can view their transaction history with pending and posted transactions.
  • Multi-currency — Support transactions in multiple currencies with real-time exchange rates and currency conversion.

Non-Functional Requirements

  • Ultra-low latency: Authorization decisions in under 500ms (p99). This is a hard SLA from card networks.
  • High availability: 99.999% uptime (5 nines). Payment systems cannot go down — every minute of downtime = millions in lost transactions.
  • Strong consistency: Account balances must be accurate. Double-charging or incorrect balance is unacceptable.
  • Massive throughput: Handle 100,000+ transactions per second at peak (Black Friday, holiday shopping).
  • Durability: No transaction can be lost. Every authorization must be persisted before responding.
Interview Tip: This is a Databricks specialty question. Focus on the real-time constraint — you have 500ms to make an irreversible decision. This drives every design choice: in-memory balance checks, geographically distributed data, and asynchronous settlement. Also emphasize that payments are fundamentally different from other systems — you cannot retry, you cannot lose data, and you must be strongly consistent.

Throughput & Storage

  Average TPS       = 5B / 86,400 ≈ 58,000 TPS
  Peak TPS (10x)    ≈ 580,000 TPS
  
Storage:
  Per transaction   = ~500 bytes
  Daily             = 5B × 500B = 2.5 TB/day
  Yearly            = ~912 TB/year
  7-year retention  = ~6.4 PB (regulatory requirement)

Memory (hot account balances):
  Active accounts   = ~500 million
  Per account state = ~200 bytes
  Total             = 500M × 200B = 100 GB (fits in-memory)
Key Insight: The critical realization is that account balance data for active accounts (500M × 200B = 100GB) fits entirely in memory across a few servers. This means we can serve authorization requests without touching disk — the key to hitting the 500ms SLA. The storage grows fast (6.4 PB over 7 years) but that's for historical transaction logs, not the hot path.

Capture a previously authorized transaction. Called when the merchant ships goods or provides service.

{
  "authorization_id": "auth_7f3a9b2c",
  "amount": 4999,             // Can be partial capture
  "idempotency_key": "req_uuid_def456"

POST /v1/transactions/settle

Batch settlement — called by the settlement service to finalize a batch of captured transactions. Moves funds between acquiring and issuing banks.

Why In-Memory Balance? The 500ms SLA means we cannot afford a disk read for every authorization. By keeping active account balances in Redis (100GB total), we can serve all authorization requests from memory. The balance is the most frequently updated and read data — it must be in the fastest storage layer. Writes (hold, settle) go through Redis first for speed, then asynchronously to PostgreSQL for durability.

6. Deep Dive

Strong Consistency for Balances

The hardest problem in payment authorization is ensuring that two simultaneous transactions for the same account don't both see the same balance and both get approved (double-spend). We solve this with optimistic locking:

// Pseudocode for atomic balance check + hold
function authorize(accountId, amount) {
  // Redis WATCH ensures no concurrent modification
  redis.WATCH(accountId)
  balance = redis.HGET(accountId, "balance")
  if (balance < amount) {
    redis.UNWATCH()
    return DECLINE_INSUFFICIENT_FUNDS
  }
  // Atomic: check balance AND place hold in one transaction
  multi = redis.MULTI()
  multi.HINCRBY(accountId, "balance", -amount)
  multi.HINCRBY(accountId, "hold_balance", amount)
  if (multi.EXEC() == null) {
    // Another transaction modified the balance — retry
    return RETRY
  }
  return APPROVE
}

Settlement Pipeline

Settlement is an asynchronous batch process that runs at end-of-day. It groups all captured transactions by merchant, calculates net amounts, and initiates fund transfers via ACH (US) or SEPA (EU).

7. Trade-offs

DecisionOption AOption BRecommendation
Balance Storage Redis (in-memory): Sub-ms reads. Must handle replication for HA. Data loss risk (mitigated by write-ahead log). PostgreSQL (disk): ACID guarantees. Too slow for p99 <500ms at 100K TPS. Disk I/O is the bottleneck. Use Redis with synchronous replication. Keep balances in Redis for speed, but write to PostgreSQL async for durability. On Redis failure, replay from WAL to rebuild.
Fraud Detection Synchronous (in-path): Every transaction checked before approval. Higher latency but no false approvals. Asynchronous (out-of-path): Transactions approved optimistically, fraud checked later. Faster but allows some fraudulent transactions. Use hybrid: fast rule-based checks synchronous (<50ms), ML model async for complex analysis. Block if rule score exceeds threshold.
Idempotency Client-generated UUID: Simple. Requires client to track and retry with same ID. Server-generated with dedup store: More reliable. Adds a Redis lookup per request. Use both: accept client idempotency keys, but also generate server-side transaction IDs. Store idempotency keys in Redis with 24h TTL for dedup.
