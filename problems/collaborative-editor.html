Design a Collaborative Editor

Design a real-time collaborative document editor like Google Docs or Figma where multiple users can simultaneously edit the same document with live cursors, conflict resolution, and offline support.

Hard Real-Time Asked at: Databricks, Google, Figma

1. Requirements

Functional Requirements

  • Real-time editing — Multiple users can edit the same document simultaneously. Changes from any user appear on all other users' screens within 200ms.
  • Conflict resolution — When two users edit the same paragraph concurrently, changes are merged automatically without data loss using Operational Transformation (OT) or CRDT.
  • Live cursors — Users can see other collaborators' cursor positions, selections, and typing indicators in real-time.
  • Offline support — Users can edit while offline. Changes are queued locally and synced when connectivity is restored, with automatic conflict resolution.
  • Version history — The system maintains a full edit history. Users can view any past version and restore it.

Non-Functional Requirements

  • Low latency: Edit operations propagated to all collaborators within 200ms (p95). Cursor updates within 100ms.
  • Consistency: All users must eventually see the same document state (eventual consistency). The merge algorithm must be commutative and associative.
  • Scalability: Support 100 concurrent editors per document, millions of documents, 50M daily active users.
  • Durability: No edits can be lost. Every operation is persisted before acknowledgment.
Interview Tip: This is a favorite at Databricks because it tests understanding of distributed consensus, CRDTs, and real-time data pipelines — all core to Databricks' data platform. The key insight is that OT and CRDT are fundamentally about making operations commutative so order doesn't matter. This is the same principle behind Delta Lake's conflict resolution.

Operational Transformation (OT)

OT Convergence Example
graph LR S0[State: "Hello"] --> O1[User A: Insert '!' at 5] S0 --> O2[User B: Insert ' World' at 5] O1 --> T1[Transform O2 against O1] O2 --> T2[Transform O1 against O2] T1 --> S1[State: "Hello World!"] T2 --> S1
Why OT over CRDT? OT is simpler for text editing because it works with position-based operations (insert at position X, delete at position Y). CRDT requires unique IDs for every character, which is more complex but has better offline support. Most production systems (Google Docs) use OT. Figma uses CRDT for its design objects.

6. Deep Dive

WebSocket Connection Management

Each document has a "room" on a specific WebSocket server. When a user opens a document, they connect to the server hosting that room. If the document has no active room, any server can host it.

Offline Sync

When a user goes offline, edits are stored in an IndexedDB queue. On reconnection, the client sends the queued operations with the last known version. The server transforms each operation against all intervening operations and broadcasts the result.

// Client-side offline queue
class OfflineQueue {
  constructor() {
    this.queue = [];          // Pending operations
    this.lastVersion = 0;     // Last synced version
  }
  
  addOperation(op) {
    op.version = this.lastVersion;
    this.queue.push(op);
    this.saveToIndexedDB();
  }
  
  async sync() {
    const response = await fetch('/sync', {
      method: 'POST',
      body: JSON.stringify({
        doc_id: this.docId,
        from_version: this.lastVersion,
        operations: this.queue
      })
    });
    // Server returns transformed ops + missed ops
    const { applied, missed } = await response.json();
    this.queue = [];
    this.applyMissed(missed);
  }
}

7. Trade-offs

DecisionOption AOption BRecommendation
OT vs CRDT OT: Position-based. Simpler for text. Requires central server for transformation. Google Docs uses this. CRDT: ID-based. Better offline support. No central server needed. More memory overhead. Figma uses this. Use OT for text (simpler, proven at Google Docs scale). Consider CRDT for non-text elements (drawings, annotations).
Snapshot Strategy Periodic snapshots: Save full document every N operations. Faster reads but more storage. Log-only: Store all operations, replay to get current state. Slower reads, less storage. Use snapshot + log: snapshot every 1000 operations. Load snapshot, then replay only recent operations. Balance read speed vs storage.
Cursor Updates Per-keystroke: Send cursor position on every keystroke. Most accurate but high bandwidth. Throttled: Send cursor position every 100ms. Lower bandwidth, slightly stale. Use 100ms throttle for cursor updates. Users won't notice the difference, but bandwidth drops 10x.
