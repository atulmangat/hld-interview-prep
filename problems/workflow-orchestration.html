Design a Workflow Orchestration System

Design a distributed workflow orchestration platform like Apache Airflow or Databricks Workflows that schedules, executes, and monitors complex multi-step data pipelines and ETL jobs with dependency management, retries, and observability.

Hard Data Platform Asked at: Databricks, Airbnb, Uber

1. Requirements

Functional Requirements

  • DAG definition — Users define workflows as Directed Acyclic Graphs (DAGs) where nodes are tasks and edges are dependencies. Example: "Extract data from S3, transform it, load into warehouse, then send alert."
  • Scheduling — DAGs can be triggered on a cron schedule (e.g., "every hour"), by external events (new file in S3), or manually via API.
  • Task execution — Tasks run on distributed workers. The system manages resource allocation, queues tasks, and tracks execution state (pending, running, success, failed).
  • Retry & error handling — Failed tasks are automatically retried with configurable backoff. DAGs support branching on failure (send alert, run cleanup task, skip downstream).
  • Observability — Real-time dashboard showing DAG runs, task status, logs, execution times, and SLA tracking.

Non-Functional Requirements

  • Scalability: Support 100K+ DAGs, 1M+ tasks per day, 10K+ concurrent task executions.
  • Reliability: No task execution can be lost. If a worker crashes, the task must be rescheduled on another worker.
  • Low scheduling latency: Tasks should be scheduled within 5 seconds of their dependencies completing.
  • Multi-tenancy: Different teams can define their own DAGs with resource isolation and access control.
Interview Tip: Databricks built its workflow system on top of Apache Airflow but heavily modified it for their data platform. Focus on the DAG scheduler — how do you determine which tasks are ready to run? How do you handle a worker crashing mid-task? The key insight is separating the scheduler (control plane) from the workers (data plane).

Register a new DAG definition (tasks, dependencies, schedule).

  "dag_id": "daily_etl_pipeline",
  "schedule": "0 2 * * *",           // 2 AM daily
  "timezone": "UTC",
  "tasks": [
    {"task_id": "extract", "type": "spark", "config": {...}},
    {"task_id": "transform", "type": "spark", "depends_on": ["extract"]},
    {"task_id": "load", "type": "sql", "depends_on": ["transform"]},
    {"task_id": "alert", "type": "email", "depends_on": ["load"]}
  ],
  "retry_policy": {"max_retries": 3, "backoff": "exponential"}
}
POST /v1/dags/{dag_id}/trigger

Manually trigger a DAG run with optional configuration overrides.

GET /v1/dags/{dag_id}/runs/{run_id}/tasks

Get status of all tasks in a DAG run.

6. Deep Dive

Exactly-Once Task Execution

The hardest problem is ensuring a task runs exactly once, even if the worker crashes mid-execution. We use a lease-based approach:

// Worker picks up a task with a lease
function acquireTask(workerId) {
  // Atomic: only one worker can claim a task
  result = db.execute(`
    UPDATE task_instances 
    SET status = 'running', worker_id = $1, lease_expiry = NOW() + INTERVAL '10 minutes'
    WHERE task_id = (
      SELECT task_id FROM task_instances 
      WHERE status = 'queued' 
      ORDER BY created_at 
      LIMIT 1 
      FOR UPDATE SKIP LOCKED
    )
    RETURNING *
  `, workerId);
  return result;
}

// Heartbeat to extend lease
function heartbeat(taskId, workerId) {
  db.execute(`
    UPDATE task_instances 
    SET lease_expiry = NOW() + INTERVAL '10 minutes'
    WHERE task_id = $1 AND worker_id = $2
  `, taskId, workerId);
}

// Scheduler reclaims expired leases
function reclaimExpiredTasks() {
  db.execute(`
    UPDATE task_instances 
    SET status = 'queued', worker_id = NULL
    WHERE status = 'running' AND lease_expiry < NOW()
  `);
}

7. Trade-offs

DecisionOption AOption BRecommendation
Scheduler Architecture Single active scheduler: Simple. All scheduling decisions in one place. Limited throughput (~10K DAGs). Single point of failure. Distributed schedulers: Higher throughput. Complex coordination (leader election, partition assignment). Better fault tolerance. Use active-standby with leader election. One scheduler is active (makes all decisions), standby takes over on failure. Partition DAGs across multiple schedulers if single scheduler is a bottleneck.
Task Queue Redis lists: Simple push/pop. Fast. No persistence (tasks lost on Redis crash). Kafka topics: Durable. Ordered. More complex. Higher latency than Redis. Use Redis as primary queue with PostgreSQL as source of truth. If Redis loses tasks, the scheduler can re-enqueue from PostgreSQL. Best of both worlds.
Worker Model Long-lived workers: Tasks run on pre-allocated workers. Fast startup. Wasted resources during idle. Ephemeral containers: Spin up a container per task. Better isolation. Higher startup latency (30-60s). Use long-lived worker pools for short tasks (<5 min) and ephemeral containers for long-running or resource-intensive tasks (Spark jobs, ML training).
