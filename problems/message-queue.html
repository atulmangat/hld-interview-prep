Design Distributed Message Queue

Design a distributed message queue system like Apache Kafka — supporting high-throughput publish/subscribe messaging, topic-based partitioning with ordering guarantees, consumer groups for parallel processing, configurable delivery semantics (at-least-once, at-most-once, exactly-once), durable message retention, and horizontal scalability across thousands of brokers.

Hard Messaging Asked at: LinkedIn, Uber, Confluent

1. Requirements

Functional Requirements

  • Producers publish messages to topics — Producers send messages to named topics. Each message consists of a key, value, optional headers, and an optional target partition. The system assigns an offset (monotonically increasing sequence number) to each message upon acceptance.
  • Consumers subscribe to topics — Consumers subscribe to one or more topics and read messages in order. They track their position (offset) in each partition and can seek to any historical offset within the retention window.
  • Consumer groups for parallel processing — Multiple consumers form a consumer group. Each partition in a topic is assigned to exactly one consumer in the group, enabling parallel consumption. When consumers join or leave, partitions are rebalanced across the remaining group members.
  • Message ordering within a partition — Messages within a single partition are strictly ordered by offset. Messages with the same key are always routed to the same partition, guaranteeing per-key ordering. No global ordering across partitions.
  • Configurable delivery semantics — Support at-least-once (default: consumer may see duplicates on failure), at-most-once (consumer may miss messages on failure), and exactly-once (idempotent producer + transactional API, no duplicates and no loss).
  • Message retention — Messages are retained for a configurable duration (e.g., 7 days) or until a size limit is reached, regardless of whether they have been consumed. Consumers can replay historical messages by seeking to an earlier offset.

Non-Functional Requirements

  • High throughput: Support millions of messages per second across the cluster. Individual partitions should sustain 10–50 MB/sec write throughput. The system must handle bursty traffic without backpressure degrading producers.
  • Low latency: End-to-end produce latency under 10 ms at p99 for acks=1 (leader acknowledgment). Consume latency under 5 ms for caught-up consumers tailing the log.
  • Durability: No message loss once acknowledged. Messages are replicated to multiple brokers before acknowledgment (when acks=all). Survive single-broker failures without data loss.
  • Horizontal scalability: Add brokers to increase capacity linearly. Topics can be repartitioned (with care) to distribute load. No single bottleneck — metadata, data, and coordination all scale independently.
  • Fault tolerance: Automatic leader election when a broker fails. Consumers rebalance when group members crash. No single point of failure. The system continues operating with degraded capacity during failures.
Interview Tip: Start by clarifying: “Are we designing a message queue (like RabbitMQ — point-to-point, messages deleted after consumption) or a distributed log (like Kafka — append-only, retained for days, replayable)?” This distinction is critical. A traditional message queue deletes messages after delivery; a distributed log retains them. Kafka’s log-based design enables consumer replay, multiple consumer groups reading independently, and stream processing — which is why it dominates modern architectures. This design follows the Kafka model.

2. Capacity Estimation

Assumptions

Parameter Value Notes
Write throughput 1 million messages/sec Aggregate across all topics and partitions
Average message size 1 KB Includes key, value, headers, and metadata
Write bandwidth 1 GB/sec 1M msgs/sec × 1 KB = 1 GB/sec
Retention period 7 days Configurable per topic
Replication factor 3 Each message stored on 3 brokers
Consumer groups per topic ~3 (average) Multiple independent consumers reading same data
Read throughput 3 GB/sec 3 consumer groups × 1 GB/sec = 3 GB/sec reads

Storage Calculation

Raw data per day:
  1 GB/sec × 86,400 sec/day = 86.4 TB/day

7-day retention:
  86.4 TB/day × 7 days = 604.8 TB ≈ 605 TB

With 3x replication:
  605 TB × 3 = 1,815 TB ≈ 1.8 PB total storage

Storage per broker (assuming 50 brokers):
  1.8 PB / 50 brokers = 36 TB per broker
  → Each broker needs ~36 TB of disk (4–6 SSDs or HDDs)

Disk I/O per broker:
  Write: 1 GB/sec / 50 brokers × 3 (replication) = 60 MB/sec writes
  Read: 3 GB/sec / 50 brokers = 60 MB/sec reads
  Total: ~120 MB/sec per broker (well within SSD/HDD capabilities)

Network Bandwidth

Inbound (producers → brokers):
  1 GB/sec from producers to leader brokers

Replication traffic (broker → broker):
  Each message replicated to 2 followers
  1 GB/sec × 2 = 2 GB/sec inter-broker traffic

Outbound (brokers → consumers):
  3 consumer groups × 1 GB/sec = 3 GB/sec

Total network throughput:
  1 + 2 + 3 = 6 GB/sec = 48 Gbps cluster-wide

Per broker (50 brokers):
  48 Gbps / 50 = ~1 Gbps per broker
  → Each broker needs a 10 Gbps NIC (standard in data centers)
Key Insight: The numbers reveal that a distributed message queue is a storage and I/O problem, not a compute problem. The CPU cost of routing messages is trivial — the bottlenecks are disk throughput (sequential writes), network bandwidth (replication + consumer reads), and storage capacity (1.8 PB for 7-day retention). This is why Kafka’s design is obsessed with sequential I/O, zero-copy transfers, and page cache utilization — these optimizations directly address the real bottlenecks.

3. API Design

Producer API

PRODUCE produce(topic, key, value, partition?, headers?)

Send a message to a topic. If partition is specified, the message goes to that partition directly. Otherwise, the partition is determined by hash(key) % numPartitions. If key is null, round-robin assignment is used. Returns the assigned partition and offset on success.

// Synchronous produce (waits for ack)
ProduceResult result = producer.send(
  new ProducerRecord("orders", orderId, orderJson)
).get();
// result: {topic: "orders", partition: 7, offset: 284619}

// Asynchronous produce (fire-and-callback)
producer.send(
  new ProducerRecord("events", userId, eventJson),
  (metadata, exception) -> {
    if (exception != null) handleError(exception);
    else log("Sent to partition " + metadata.partition());
  }
);
BATCH producer.send(records[]) — Batching & Compression

Producers batch multiple messages into a single network request for efficiency. Configurable via batch.size (bytes) and linger.ms (max wait time). Batches can be compressed (gzip, snappy, lz4, zstd) to reduce network and storage overhead.

// Producer config for batching
batch.size = 65536        // 64 KB batch buffer
linger.ms = 5             // Wait up to 5ms to fill batch
compression.type = "lz4"  // Compress each batch
acks = "all"              // Wait for all ISR to acknowledge
retries = 3               // Retry on transient failures
enable.idempotence = true // Prevent duplicate messages

Consumer API

SUBSCRIBE consumer.subscribe(topics[])

Subscribe to one or more topics. The consumer joins a consumer group (specified in config). The group coordinator assigns partitions to this consumer. When other consumers join/leave the group, a rebalance redistributes partitions.

consumer.subscribe(["orders", "payments"]);

// Poll loop — the core consumption pattern
while (true) {
  ConsumerRecords records = consumer.poll(Duration.ofMillis(100));
  for (ConsumerRecord record : records) {
    process(record.key(), record.value());
  }
  consumer.commitSync(); // Commit offsets after processing
}
POLL consumer.poll(timeout) → ConsumerRecords

Fetch messages from assigned partitions. Returns a batch of records (up to max.poll.records). The consumer tracks its position (offset) per partition. If no new messages are available, blocks for up to timeout milliseconds.

COMMIT consumer.commitSync(offsets?) / consumer.commitAsync()

Persist the consumer’s current offset for each partition. On restart, the consumer resumes from the last committed offset. commitSync blocks until the broker confirms; commitAsync returns immediately. Offsets are stored in a special internal topic (__consumer_offsets).

Admin API

ADMIN createTopic(name, partitions, replicationFactor, config?)

Create a new topic with the specified number of partitions and replication factor. Optional config overrides (retention.ms, segment.bytes, cleanup.policy). Partitions are distributed across brokers for load balancing.

admin.createTopic({
  name: "user-events",
  partitions: 32,
  replicationFactor: 3,
  config: {
    "retention.ms": 604800000,  // 7 days
    "segment.bytes": 1073741824, // 1 GB segments
    "cleanup.policy": "delete"   // or "compact"
  }
});

Segment Files on Disk

File Purpose Structure
.log The actual message data. Append-only. Sequential writes. Each segment is named by its base offset (e.g., 00000000000050000.log starts at offset 50,000). Concatenated record batches, written sequentially.
.index Sparse offset index. Maps logical offset → physical file position in the .log file. Sparse: not every offset is indexed (every Nth offset). Binary search to find nearest entry, then scan forward. Pairs of (relative_offset: 4B, position: 4B). Fixed 8-byte entries.
.timeindex Sparse timestamp index. Maps timestamp → offset. Used for time-based seeking (e.g., “replay from 2 hours ago”). Enables offsetsForTimes() API. Pairs of (timestamp: 8B, relative_offset: 4B). Fixed 12-byte entries.
Why segments? Splitting a partition into segments enables efficient retention management. When a segment’s oldest message exceeds the retention period, the entire segment file is deleted — a single unlink() syscall. Without segments, deleting old messages from the middle of a single file would require expensive rewriting. Segments also enable efficient binary search for offset lookups: find the right segment by base offset, then binary search the sparse index within that segment.

5. High-Level Design

The architecture consists of three main components: Producers that publish messages, a Broker Cluster that stores and replicates messages, and Consumers that read messages. A coordination layer (ZooKeeper or KRaft) manages metadata, leader election, and cluster membership.

Key Components

Broker

A broker is a single server in the cluster.
Each broker:
• Stores partition replicas on local disk
• Serves produce requests (if it's the leader)
• Serves fetch requests (from consumers
  and follower replicas)
• Participates in leader election
• Reports health to the controller

Typical capacity per broker:
• 10–50 MB/sec write throughput
• 100–200 MB/sec read throughput
• 1–10 TB storage
• 100K+ connections

Controller

One broker is elected as the CONTROLLER.
The controller:
• Manages partition leader assignments
• Detects broker failures (via heartbeats)
• Triggers leader election when a broker dies
• Handles topic creation/deletion
• Manages partition reassignment

In ZooKeeper mode:
  Controller watches ZK for broker changes.
  ZK stores all metadata.

In KRaft mode:
  Controller is a Raft leader.
  Metadata stored in an internal topic.
  No external dependency.

6. Deep Dive

6a. Partitioning — Parallelism and Ordering

Partitioning is the fundamental mechanism for achieving parallelism in a distributed message queue. A topic is divided into N partitions, each of which is an independent, ordered log. Partitions are distributed across brokers for load balancing.

    PARTITIONING STRATEGY
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    HOW PARTITION IS CHOSEN:
    ────────────────────────────────────────────────────────

    Case 1: Key is provided
      partition = hash(key) % numPartitions

      Example: key = "order-12345"
      hash("order-12345") = 2038471923
      2038471923 % 8 = 3
      → Message goes to Partition 3

      ALL messages with key "order-12345" go to Partition 3.
      This guarantees per-key ordering.

    Case 2: Key is null
      Round-robin across partitions (or sticky partitioner
      that fills one batch before moving to the next).

    Case 3: Partition explicitly specified
      Producer directly specifies partition number.
      Used for custom partitioning logic.


    ORDERING GUARANTEE:
    ────────────────────────────────────────────────────────

    Topic "orders" with 4 partitions:

    Partition 0: [msg1] [msg4] [msg8]  [msg12] →
    Partition 1: [msg2] [msg5] [msg9]  [msg13] →
    Partition 2: [msg3] [msg6] [msg10] [msg14] →
    Partition 3: [msg7] [msg11]                →

    • WITHIN a partition: strict ordering (msg1 before msg4)
    • ACROSS partitions: NO ordering guarantee
      (msg2 in P1 may be processed before msg1 in P0)

    • Per-key ordering: all messages with the same key
      go to the same partition, so they are ordered.
      Example: all events for user_id=42 go to P2.


    CHOOSING PARTITION COUNT:
    ────────────────────────────────────────────────────────

    More partitions = more parallelism, but also:
    • More file handles (3 files per segment per partition)
    • More memory (index buffers, page cache entries)
    • Longer leader election time (each partition needs
      a separate election)
    • Higher end-to-end latency (more partitions to
      replicate)

    Rule of thumb:
    • Target throughput per partition: 10 MB/sec
    • Desired total throughput: 100 MB/sec
    • Partitions needed: 100 / 10 = 10 partitions
    • Account for future growth: 2–3x = 20–30 partitions
    • Typical range: 6–64 partitions per topic
    • High-throughput topics: 100–256 partitions
Interview Tip: A common follow-up question is: “What happens if you need to increase the number of partitions?” Answer: You can add partitions, but messages with the same key may now hash to a different partition. This breaks per-key ordering for new messages (old messages stay in their original partition). For this reason, it’s better to over-provision partitions upfront. Reducing partitions is not supported — you must create a new topic and migrate data.

6b. Replication — Durability and Fault Tolerance

Each partition is replicated across multiple brokers. One replica is the leader (handles all reads and writes), and the others are followers (passively replicate from the leader). The set of replicas that are fully caught up is called the ISR (In-Sync Replica set).

Acks: The Durability vs. Performance Trade-off

acks=0 (Fire-and-Forget)

Producer does NOT wait for any
acknowledgment from the broker.

Flow:
  Producer → send → done (no wait)

Durability: NONE
  Message may be lost if broker crashes
  before writing to disk.

Latency: Lowest (~0.5 ms)
Performance: Highest throughput

Use case:
  Metrics, logs, clickstream data where
  occasional loss is acceptable.

acks=1 (Leader Only)

Producer waits for the LEADER to write
the message to its local log.

Flow:
  Producer → Leader writes → ack

Durability: MODERATE
  Message survives leader restart (on disk).
  Message LOST if leader dies before
  followers replicate.

Latency: Low (~2–5 ms)
Performance: Good throughput

Use case:
  Default for most applications.
  Good balance of durability and speed.

acks=all (All ISR)

Producer waits for ALL in-sync replicas
to write the message.

Flow:
  Producer → Leader writes →
  Followers replicate → all ack →
  Leader acks producer

Durability: HIGHEST
  Message survives any single broker failure.
  Combined with min.insync.replicas=2,
  guarantees message is on 2+ brokers.

Latency: Higher (~5–15 ms)
Performance: Lower throughput

Use case:
  Financial transactions, orders, payments.
  Any data that MUST NOT be lost.
Critical config: min.insync.replicas. With acks=all and min.insync.replicas=2 (replication factor 3), the producer’s write is acknowledged only when at least 2 replicas (including the leader) have the message. If only 1 replica is in the ISR, the producer receives an error rather than silently reducing durability. This prevents the degenerate case where acks=all with ISR={leader only} is equivalent to acks=1.

Leader Election

    LEADER ELECTION ON BROKER FAILURE
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    BEFORE: Broker 1 is leader for Partition 0
    ISR = {Broker 1 (L), Broker 2, Broker 3}

    ┌──────────┐  ┌──────────┐  ┌──────────┐
    │ Broker 1 │  │ Broker 2 │  │ Broker 3 │
    │ P0: L    │  │ P0: F    │  │ P0: F    │
    │ LEO: 100 │  │ LEO: 100 │  │ LEO: 99  │
    └──────────┘  └──────────┘  └──────────┘

    Broker 1 CRASHES! Controller detects via heartbeat timeout.

    AFTER: Controller elects Broker 2 as new leader
    (first ISR member that is alive)
    ISR = {Broker 2 (L), Broker 3}

    ┌──────────┐  ┌──────────┐  ┌──────────┐
    │ Broker 1 │  │ Broker 2 │  │ Broker 3 │
    │  DEAD    │  │ P0: L    │  │ P0: F    │
    │          │  │ LEO: 100 │  │ LEO: 99  │
    └──────────┘  └──────────┘  └──────────┘

    Broker 3 catches up: fetches offset 99 from new leader.
    ISR = {Broker 2 (L), Broker 3}

    When Broker 1 recovers:
    1. Truncates log to HW at time of crash
    2. Fetches missing messages from new leader
    3. Rejoins ISR once fully caught up
    ISR = {Broker 2 (L), Broker 1, Broker 3}

    UNCLEAN LEADER ELECTION:
    If ALL ISR members are dead, should we elect an
    out-of-sync replica? This risks data loss but
    restores availability.
    • unclean.leader.election.enable=true: availability > durability
    • unclean.leader.election.enable=false: durability > availability

6c. Consumer Groups — Parallel Consumption

A consumer group is a set of consumers that cooperatively consume a topic. Each partition is assigned to exactly one consumer in the group, ensuring no two consumers in the same group process the same message. Different consumer groups read the same data independently.

Consumer Rebalancing

    REBALANCING WHEN CONSUMERS JOIN/LEAVE
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    TRIGGER: Consumer 2 crashes (stops sending heartbeats)

    BEFORE:
    C1 ← P0, P1    C2 ← P2, P3    C3 ← P4, P5

    REBALANCE PROTOCOL:
    1. Group coordinator detects C2 is dead
       (no heartbeat for session.timeout.ms = 10s)
    2. Coordinator triggers rebalance
    3. All remaining consumers revoke their partitions
       and commit offsets
    4. Coordinator reassigns partitions:

    AFTER (Range Assignor):
    C1 ← P0, P1, P2    C3 ← P3, P4, P5

    AFTER (Sticky Assignor — preferred):
    C1 ← P0, P1, P2    C3 ← P4, P5, P3
    (P0,P1 stay with C1; P4,P5 stay with C3; only P2,P3 move)


    REBALANCE IMPACT:
    ────────────────────────────────────────────────────────

    During rebalance (Eager protocol):
    • ALL consumers stop processing (stop-the-world)
    • Duration: 1–30 seconds depending on group size
    • No messages are consumed during this window

    Cooperative Incremental Rebalance (modern):
    • Only affected partitions are revoked
    • Other consumers continue processing
    • Much shorter disruption
    • Two-phase: revoke → assign (no stop-the-world)

6d. Storage Engine — Why Kafka Is Fast

The storage engine is the heart of a distributed message queue. Kafka achieves extraordinary throughput not through exotic algorithms, but through a relentless focus on sequential I/O, OS page cache, and zero-copy transfers. Understanding why these matter is critical for the interview.

    WHY KAFKA IS FAST — FOUR KEY TECHNIQUES
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    1. APPEND-ONLY LOG (Sequential I/O)
    ────────────────────────────────────────────────────────

    Traditional DB:  Random writes to update rows in-place
    Kafka:           Append-only writes to end of log file

    Sequential write: 600 MB/sec (HDD), 2+ GB/sec (SSD)
    Random write:     100 IOPS × 4KB = 0.4 MB/sec (HDD)

    Sequential I/O is 1,500x faster than random I/O on HDD!

    Kafka NEVER modifies existing data. It only appends.
    This turns disk into a high-throughput medium.

    2. OS PAGE CACHE (No Application-Level Cache)
    ────────────────────────────────────────────────────────

    Kafka does NOT maintain its own in-memory cache.
    Instead, it relies on the OS page cache.

    When Kafka writes to a file:
    • Data goes to the OS page cache (RAM)
    • OS flushes to disk asynchronously
    • Subsequent reads hit the page cache (no disk I/O)

    Why this is brilliant:
    • No GC pressure (data is in OS memory, not JVM heap)
    • No cache invalidation complexity
    • Survives process restart (page cache persists)
    • OS is highly optimized for page cache management
    • Read-after-write is instant (data already in cache)

    For caught-up consumers (tailing the log):
    • Producer writes → data enters page cache
    • Consumer reads → served from page cache
    • ZERO disk reads for real-time consumption!

    ┌─────────────────────────────────────────────────┐
    │  JVM Heap (Kafka process)                       │
    │  • Minimal: metadata, connections, buffers      │
    │  • Typically 4–8 GB                             │
    └─────────────────────────────────────────────────┘
    ┌─────────────────────────────────────────────────┐
    │  OS Page Cache (managed by kernel)              │
    │  • ALL message data lives here                  │
    │  • Typically 20–100+ GB                        │
    │  • LRU eviction when memory is full             │
    │  • Caught-up consumers read from here           │
    └─────────────────────────────────────────────────┘
    ┌─────────────────────────────────────────────────┐
    │  Disk (persistent storage)                      │
    │  • Sequential writes from page cache flush      │
    │  • Only accessed for historical reads            │
    │    (consumers far behind the tail)              │
    └─────────────────────────────────────────────────┘


    3. ZERO-COPY TRANSFER (sendfile syscall)
    ────────────────────────────────────────────────────────

    Traditional data transfer (4 copies, 4 context switches):

    Disk → Kernel Buffer → App Buffer → Socket Buffer → NIC
         copy 1         copy 2        copy 3          copy 4

    Zero-copy transfer (2 copies, 2 context switches):

    Disk → Kernel Buffer ────────────────────────────→ NIC
         copy 1        (DMA from page cache to NIC)  copy 2

    The sendfile() syscall tells the OS to transfer data
    directly from the page cache to the network socket,
    bypassing the application entirely.

    Impact:
    • 2–4x improvement in throughput for consumer reads
    • Dramatically lower CPU usage
    • Kafka broker barely touches the data it serves


    4. BATCHING AND COMPRESSION
    ────────────────────────────────────────────────────────

    Messages are batched at every layer:

    Producer:
    • Accumulates messages in a batch buffer
    • Sends batch as single network request
    • Compresses entire batch (not individual messages)
    • Amortizes network round-trip over many messages

    Broker:
    • Writes entire batch to disk in one sequential write
    • Stores compressed batch as-is (no decompression)
    • Replication sends compressed batches

    Consumer:
    • Fetches large batches in single request
    • Decompresses on the consumer side

    End-to-end compression:
    Producer compresses → Broker stores compressed →
    Consumer decompresses
    Broker NEVER decompresses data (pass-through)!
This is the KEY section for interviews. When asked “Why is Kafka fast?”, the answer is: (1) append-only sequential I/O turns slow disks into high-throughput devices, (2) OS page cache eliminates application-level caching and GC overhead, (3) zero-copy (sendfile) bypasses the application for consumer reads, and (4) end-to-end batching and compression amortize overhead. These four techniques together allow a single broker to sustain 100+ MB/sec throughput on commodity hardware. The insight is that Kafka treats disk as a feature, not a bottleneck — sequential disk I/O is faster than random memory access.

6e. Offset Management — Tracking Consumer Progress

Each consumer tracks its position in each assigned partition via an offset — a monotonically increasing integer. The consumer periodically commits its current offset to the broker, so it can resume from the right position after a restart.

Key Insight: At-least-once delivery is the default and most common choice. The consumer commits offsets after processing, accepting the possibility of reprocessing on failure. The application must be idempotent — processing the same message twice should produce the same result. Common idempotency strategies: use a unique message ID as a database primary key (INSERT ... ON CONFLICT DO NOTHING), or maintain a processed-message set in Redis.

6f. Exactly-Once Semantics — The Holy Grail

Exactly-once semantics (EOS) means each message is processed exactly once — no loss, no duplicates. This is achieved through two mechanisms: idempotent producers (prevent duplicate writes) and the transactional API (atomic read-process-write).

Interview Tip: Exactly-once is often misunderstood. Clarify: “Exactly-once in Kafka means exactly-once within the Kafka ecosystem. If your consumer writes to an external database, Kafka cannot guarantee the external write is atomic with the offset commit. For true end-to-end exactly-once with external systems, you need either (a) an idempotent consumer (dedup on the external side) or (b) a two-phase commit protocol (which is complex and slow). Most production systems use at-least-once delivery with idempotent consumers.”

6g. ZooKeeper vs. KRaft — Metadata Management

Kafka historically relied on Apache ZooKeeper for cluster coordination. Starting with Kafka 3.3 (KIP-833), Kafka introduced KRaft (Kafka Raft) to replace ZooKeeper with a built-in Raft-based consensus protocol for metadata management.

ZooKeeper (Legacy)

External coordination service.
Kafka stores metadata in ZK:
• Broker registration (/brokers/ids)
• Topic config (/config/topics)
• Partition assignments
• Controller election
• Consumer group offsets (old API)

Problems:
• Separate system to deploy, monitor,
  and maintain
• Scalability bottleneck: ZK stores ALL
  metadata in memory
• Split-brain risk between Kafka and ZK
• Slow controller failover (10–30 sec)
• ZK watches are expensive at scale
  (100K+ partitions)
• Two different security models to manage
• Operational complexity: two clusters
  instead of one

KRaft (Modern)

Built-in Raft consensus protocol.
Metadata stored in an internal topic:
__cluster_metadata

3–5 dedicated controller nodes form a
Raft quorum. One is the active controller;
others are hot standbys.

Advantages:
• No external dependency (single system)
• Faster controller failover (<1 sec)
• Scales to millions of partitions
• Metadata replicated via Raft (strong
  consistency)
• Simpler operations: one cluster to
  deploy and monitor
• Unified security model
• Event-driven metadata propagation
  (no polling/watches)

Migration:
Kafka 3.3+: KRaft production-ready
Kafka 4.0: ZooKeeper removed entirely
Why the migration matters: ZooKeeper was Kafka’s biggest operational pain point and scalability bottleneck. With ZK, controller failover took 10–30 seconds (during which no leader elections could happen). With KRaft, failover is sub-second. ZK also limited Kafka to ~200K partitions per cluster; KRaft supports millions. In an interview, mention: “Kafka is moving from ZooKeeper to KRaft for metadata management. KRaft eliminates the external dependency, reduces operational complexity, and enables faster failover and higher partition counts. This is a major architectural evolution.”

7. Trade-offs

Decision Option A Option B Recommendation
Throughput vs. Latency (Batching) Large batches (linger.ms=50, batch.size=256KB): Higher throughput — fewer network round-trips, better compression ratio, more efficient disk writes. But higher latency: each message waits up to 50 ms to be batched. Small/no batches (linger.ms=0, batch.size=16KB): Lower latency — messages sent immediately. But lower throughput: more network overhead, worse compression, more small disk writes. Tune per use case. High-throughput pipelines (logs, analytics): linger.ms=50–100, batch.size=256KB. Low-latency applications (real-time alerts): linger.ms=0–5, batch.size=16KB. Most systems use linger.ms=5 as a good default.
Durability vs. Performance (Acks) acks=all + min.insync.replicas=2: Maximum durability — message survives any single broker failure. Higher latency (5–15 ms) due to replication wait. Lower throughput. Producer blocks until all ISR members acknowledge. acks=1: Good durability (survives leader restart) with lower latency (2–5 ms). Risk: message lost if leader dies before replication. acks=0: No durability guarantee, maximum throughput. Use acks=all for critical data (orders, payments, financial events). Use acks=1 for important but recoverable data (user activity, notifications). Use acks=0 only for truly disposable data (debug logs, metrics where occasional loss is acceptable).
Ordering vs. Parallelism Single partition: Global ordering of all messages. But zero parallelism — one consumer processes everything sequentially. Throughput limited to one broker’s capacity. Multiple partitions: Parallel consumption across consumers. But no global ordering — only per-partition ordering. Per-key ordering preserved via hash partitioning. Use multiple partitions with key-based routing. Per-key ordering (all events for user X go to the same partition) is sufficient for almost all use cases. True global ordering is rarely needed and doesn’t scale. If you need global ordering, use a single partition and accept the throughput limit.
Push vs. Pull Consumers Pull (Kafka model): Consumer controls the pace — fetches messages when ready. Natural backpressure: slow consumers don’t overwhelm the broker. Consumers can batch fetches for efficiency. Simpler broker (no per-consumer tracking). Push (RabbitMQ model): Broker pushes messages to consumers immediately. Lower latency for real-time use cases. But risk of overwhelming slow consumers. Broker must track consumer state and implement flow control. Use pull-based consumers for a Kafka-style system. Pull gives consumers control over their consumption rate, provides natural backpressure, and simplifies the broker. The latency difference is negligible (<5 ms) because caught-up consumers poll continuously with short timeouts. Push is better for traditional message queues (RabbitMQ) where messages are deleted after delivery.
Interview Tip: When discussing trade-offs, frame them as dials, not binary choices: “Batching is a dial between throughput and latency. At linger.ms=0, we get minimum latency but lower throughput. At linger.ms=100, we get maximum throughput but 100 ms added latency. The right setting depends on the use case — a real-time alerting system needs linger.ms=0, while a log aggregation pipeline benefits from linger.ms=100. Similarly, acks is a dial between durability and performance. We tune these per-topic based on the data’s criticality.”
