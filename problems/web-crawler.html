Design a Web Crawler

Design a distributed web crawler that systematically downloads and indexes 1 billion web pages per month — respecting robots.txt, handling redirects and malformed HTML, detecting spider traps, deduplicating content, and prioritizing important pages — all while being polite to web servers and extensible to new content types.

Medium Platform Asked at: Google, Amazon, Apple

1. Requirements

Functional Requirements

  • Crawl 1 billion pages per month — The crawler must systematically discover and download web pages at scale, starting from a set of seed URLs and following hyperlinks to discover new pages. It must sustain a throughput of approximately 400 pages per second on average.
  • Handle HTML content — Parse HTML pages to extract text content, metadata (title, description, keywords), and hyperlinks. The parser must handle malformed HTML gracefully (real-world HTML is rarely valid). Support for other content types (PDF, images) should be extensible.
  • Respect robots.txt — Before crawling any page on a domain, fetch and obey the site’s robots.txt file. Honor Disallow directives, Crawl-delay settings, and Sitemap references. Cache robots.txt per domain to avoid re-fetching it on every request.
  • Handle redirects — Follow HTTP 301 (permanent) and 302 (temporary) redirects, up to a configurable maximum depth (e.g., 10 hops). Record the redirect chain for URL canonicalization. Detect redirect loops and abort.
  • Detect and avoid spider traps — Identify pages that generate infinite URLs (e.g., calendar pages with endless date links, session ID parameters, URL query combinatorics). Enforce maximum URL depth, detect repetitive URL patterns, and cap pages crawled per domain.
  • Store crawled content — Persist the raw HTML, extracted text, metadata, and outgoing links for each crawled page. Support efficient retrieval by URL and by content hash. Storage must handle 500 TB/month of new data.

Non-Functional Requirements

  • Scalability: The system must scale horizontally. Adding more crawler nodes should linearly increase throughput. The architecture must support scaling from 1 billion to 10 billion pages/month without fundamental redesign.
  • Politeness: Do not overload web servers. Enforce per-domain rate limits (e.g., max 1 request per second per domain). Space out requests to the same domain. Identify the crawler via a descriptive User-Agent string. This is both an ethical requirement and a practical one — aggressive crawlers get IP-banned.
  • Robustness: Handle malformed HTML, broken links, server errors (5xx), timeouts, and unexpected content types without crashing. Individual page failures must not affect the overall crawl. The system must recover gracefully from crawler node failures.
  • Extensibility: The architecture should make it easy to add support for new content types (PDF, images, JavaScript-rendered pages), new crawl policies (priority adjustments, freshness requirements), and new output formats (search index, knowledge graph) without modifying the core crawl loop.
Interview Tip: Start by clarifying scope: “Are we building a general-purpose web crawler like Googlebot, or a focused crawler for a specific domain (e.g., crawling product pages for price comparison)?” A general-purpose crawler at 1B pages/month is the harder and more interesting problem. Also ask: “Do we need to render JavaScript? Many modern sites are SPAs that require headless browser rendering.” For a 45-minute interview, assume server-rendered HTML and call out JS rendering as an extension point.

  100 TB × 0.7 = 70 TB/month effective new storage

  Billions of discovered URLs × ~100 bytes/URL
  = hundreds of GB (fits in distributed storage)

  URL + content hash + timestamp + status = ~500 bytes
  1 billion pages × 500 bytes = 500 GB/month

Network Bandwidth

Download bandwidth:
  400 pages/sec × 500 KB/page = 200 MB/sec
  = 1.6 Gbps sustained

  Peak (3x): ~4.8 Gbps

DNS traffic:
  400 lookups/sec × ~200 bytes/lookup = negligible

Outbound (HTTP requests):
  400 requests/sec × ~500 bytes/request = negligible
Key Insight: The numbers reveal two critical bottlenecks: (1) DNS resolution — at 400 pages/sec, DNS lookups add up to 80 seconds of cumulative latency per second without caching. A local DNS cache with pre-fetching is essential. (2) URL frontier management — at 20,000 new URLs discovered per second, the URL deduplication system must handle extremely high write throughput. A Bloom filter is the right data structure here — it provides O(1) membership checks with minimal memory. The actual page download bandwidth (1.6 Gbps) is manageable with modern infrastructure.

3. High-Level Design

The web crawler follows a loop architecture: URLs are pulled from a frontier, pages are downloaded and parsed, new URLs are extracted and filtered, and novel URLs are fed back into the frontier. The key challenge is making this loop distributed, polite, and resilient to traps and duplicates.

Key Components

  • Seed URLs: The initial set of URLs that bootstrap the crawl. Typically high-authority domains (google.com, wikipedia.org, dmoz.org). The quality and diversity of seed URLs determines how quickly the crawler discovers the broader web.
  • URL Frontier: The most critical component. A two-level queue system that manages which URL to crawl next. The front queues handle priority (important pages first), and the back queues handle politeness (one queue per host, rate-limited). This is the brain of the crawler.
  • HTML Downloader: Multi-threaded HTTP client that fetches pages. Uses connection pooling, configurable timeouts, and retry logic. Checks robots.txt before every download. Handles redirects (up to 10 hops) and various HTTP status codes.
  • DNS Resolver: Resolves hostnames to IP addresses. DNS is a major bottleneck — each lookup takes 10–200 ms. Uses a local DNS cache and pre-fetches DNS for URLs in the frontier to eliminate lookup latency from the critical path.
  • Content Parser: Extracts text, metadata, and structure from HTML. Must handle malformed HTML gracefully (use a lenient parser like jsoup or BeautifulSoup, not a strict XML parser).
  • Content Deduplication: Uses SimHash or MinHash to detect near-duplicate pages. Exact duplicates are caught by content hash (SHA-256). Near-duplicates (e.g., same article with different ads) are caught by fingerprinting algorithms. Prevents wasting storage and crawl budget on redundant content.
  • Link Extractor: Extracts all hyperlinks from parsed HTML, normalizes them (resolve relative URLs, remove fragments, canonicalize query parameters), and passes them to the URL filter.
  • URL Filter: Removes unwanted URLs: blocklisted domains, non-HTTP schemes (mailto:, javascript:), known spider trap patterns, and URLs exceeding maximum depth.
  • URL Deduplication (Bloom Filter): A space-efficient probabilistic data structure that tracks which URLs have already been crawled or are in the frontier. At 1 billion URLs, a Bloom filter uses only ~1.2 GB of memory with a 1% false positive rate.
The URL Frontier Is the Key Component. In an interview, the URL Frontier is what separates a good answer from a great one. It must solve two competing goals simultaneously: (1) Priority — crawl important pages first (PageRank, freshness, domain authority). (2) Politeness — don’t hammer any single domain. These goals conflict: the highest-priority pages might all be on the same domain (e.g., wikipedia.org), but politeness requires spacing out requests to that domain. The two-level queue architecture (front queues for priority, back queues for politeness) elegantly resolves this tension.

4. Deep Dive

4a. URL Frontier — The Brain of the Crawler

The URL Frontier is a two-level queue system that determines the crawl order. The front queues manage priority (which URLs are most important) and the back queues manage politeness (rate limiting per domain). This is the most important component to get right in an interview.

Interview Tip: When explaining the URL Frontier, say: “The frontier has two levels. The front queues handle priority — I assign URLs to queues based on PageRank, freshness, and depth. The back queues handle politeness — each back queue maps to exactly one hostname and has a rate limiter. A router connects the two: when a URL is dequeued from a front queue, it is placed into the appropriate host’s back queue. The queue selector then picks the back queue whose rate limit has expired. This ensures we crawl important pages first while never hammering any single server.”

4c. DNS Resolver — Eliminating the Bottleneck

DNS resolution is one of the most underestimated bottlenecks in web crawling. Each lookup takes 10–200 ms, and at 400 pages/sec, this adds up fast. Without caching, DNS alone would consume more time than the actual page downloads.

4d. Content Deduplication — SimHash and MinHash

The web is full of duplicate and near-duplicate content: syndicated articles, scraped content, boilerplate pages, and pages that differ only in ads or navigation. Crawling and storing duplicates wastes both crawl budget and storage. Content deduplication catches these at two levels.

4e. URL Deduplication — Bloom Filter

With 20,000 new URLs discovered per second, the crawler needs a fast, space-efficient way to check if a URL has already been crawled or is already in the frontier. A Bloom filter is the ideal data structure for this.

graph TD NewURL["New URL discovered"] Hash["Apply k=7 hash functions\nh1, h2, ..., h7"] BitSet["Bloom Filter\nBit array: ~9.6 billion bits (1.2 GB)\nm = -(n × ln(p)) / (ln 2)²"] Check{"All k bits\nset to 1?"} Skip["PROBABLY seen\nSkip URL"] Insert["Definitely NOT seen\nSet k bits to 1\nAdd URL to frontier"] NewURL --> Hash --> Check Check -- Yes --> Skip Check -- No --> Insert Insert --> BitSet
Key Insight: The Bloom filter’s false positives mean that ~1% of genuinely new URLs will be incorrectly skipped. For a web crawler, this is perfectly acceptable — the web is highly interconnected, and any important page will be discovered via multiple link paths. The 80x memory savings (1.2 GB vs. 100 GB) far outweigh the cost of occasionally missing a URL. If zero false positives are required, use a hash set backed by disk (e.g., RocksDB), but this is slower and unnecessary for most crawlers.

4f. Spider Trap Detection — Avoiding Infinite Crawls

Spider traps are pages that generate an infinite (or near-infinite) number of URLs, causing the crawler to waste resources crawling the same site endlessly. They can be malicious (designed to trap crawlers) or accidental (poorly designed websites).

4g. Crawl Priority — What to Crawl First

Not all pages are equally important. The crawler must prioritize pages that are more valuable to the downstream consumers (search engine, analytics, etc.). Priority determines which front queue a URL is assigned to.

Priority Signals

1. PageRank / Domain Authority
   High-authority domains (wikipedia.org,
   github.com) get higher priority.
   Computed offline from the link graph.

2. Freshness / Change Frequency
   Pages that change often (news sites,
   stock prices) need frequent recrawling.
   Track last-modified headers and
   historical change rates.

3. Depth from Seed URL
   Pages closer to seed URLs (fewer hops)
   tend to be more important. Homepage
   (depth 0) > subpage (depth 3).

4. Content Type
   HTML pages > PDF > images > other.
   Prioritize content that yields the
   most links for further discovery.

5. Recrawl Scheduling
   Previously crawled pages are re-added
   to the frontier with priority based on
   their expected change frequency:
   • News sites: recrawl every hour
   • Blogs: recrawl every day
   • Static pages: recrawl every week

Priority Assignment

Priority score = weighted combination:

score = w1 × pagerank_score
      + w2 × freshness_score
      + w3 × depth_score
      + w4 × content_type_score

Example weights:
  w1 = 0.4  (PageRank is most important)
  w2 = 0.3  (freshness matters for news)
  w3 = 0.2  (prefer shallow pages)
  w4 = 0.1  (prefer HTML over other)

Front queue assignment:
  score > 0.8  → Queue F1 (highest)
  score > 0.5  → Queue F2 (high)
  score > 0.2  → Queue F3 (medium)
  score ≤ 0.2  → Queue F4 (low)

Queue selection uses weighted
round-robin:
  F1 gets 40% of dequeue operations
  F2 gets 30%
  F3 gets 20%
  F4 gets 10%

This ensures low-priority pages are
still crawled, just less frequently.

4h. Distributed Crawling — Scaling Horizontally

A single machine cannot crawl 400 pages/sec sustainably. The crawler must be distributed across multiple nodes, with each node responsible for a subset of domains. Consistent hashing ensures even distribution and graceful handling of node failures.

Interview Tip: When discussing distributed crawling, emphasize why domain-based partitioning is the right choice: “We partition URLs by domain hash so that all URLs for a given domain go to the same crawler node. This gives us three things for free: (1) politeness enforcement is local to each node — no distributed coordination needed for rate limiting, (2) robots.txt and DNS caches are per-node with high hit rates, and (3) HTTP connections to the same host can be reused via keep-alive. We use consistent hashing so that when a node fails, only its domains are redistributed, and the other nodes are unaffected.”

5. Trade-offs

Decision Option A Option B Recommendation
BFS vs. DFS traversal BFS (Breadth-First): Explores all pages at depth N before moving to depth N+1. Discovers high-level pages first (homepages, category pages). More URLs in the frontier at any time (higher memory). Better for general-purpose crawling — finds the most important pages quickly. DFS (Depth-First): Follows links deeply into a single site before backtracking. Lower memory usage (smaller frontier). Risk of getting trapped in deep link chains. Better for focused crawling of a single site. Misses breadth of the web. Use BFS for general-purpose crawling. BFS naturally discovers high-authority pages first (homepages are at depth 0-1) and provides better coverage of the web. The higher memory cost is manageable with the URL Frontier’s disk-backed queues. DFS is only appropriate for focused crawlers targeting a single domain.
Politeness vs. speed Aggressive crawling: No per-domain rate limits. Maximum throughput. Risks getting IP-banned by web servers. Violates web etiquette. Can cause denial-of-service on small servers. Faster crawl completion. Polite crawling: Strict per-domain rate limits (1 req/sec). Slower overall throughput per domain. Respects server capacity. Maintains good reputation. Required for long-term crawling operations. Always be polite. Rate limit to 1 request per second per domain (or respect Crawl-delay in robots.txt). Compensate for per-domain slowness by crawling many domains in parallel. With 10M domains and 1 req/sec/domain, the theoretical max is 10M pages/sec — far more than our 400 pages/sec target. Politeness does not limit aggregate throughput.
Bloom filter false positives Low false positive rate (0.1%): Uses ~1.8 GB for 1B URLs. Very few URLs incorrectly skipped. Higher memory cost. 10 hash functions per lookup (more CPU). Higher false positive rate (1%): Uses ~1.2 GB for 1B URLs. ~1% of new URLs incorrectly skipped. Lower memory cost. 7 hash functions per lookup (less CPU). Use 1% false positive rate. The web is highly interconnected — any important page will be discovered via multiple link paths. Losing 1% of URLs is negligible. The 600 MB memory savings and reduced CPU per lookup are worthwhile. If a critical page is missed, it will be found on the next crawl cycle or via a different link path.
Store raw HTML vs. parsed content Raw HTML: Store the complete HTML as downloaded. Preserves all information. Allows re-parsing with improved parsers later. Higher storage cost (500 KB/page avg). Useful for debugging and auditing. Parsed content only: Store only extracted text, metadata, and links. Much smaller storage footprint (~50 KB/page). Loses original HTML structure. Cannot re-parse if parser improves. Faster downstream processing. Store both. Raw HTML goes to cold storage (S3 with infrequent access tier, compressed). Parsed content goes to hot storage for immediate use by downstream systems (search indexer, analytics). The raw HTML is insurance — when you improve your parser (and you will), you can re-process the raw HTML without re-crawling. Storage is cheap; re-crawling is expensive.
URL dedup: Bloom filter vs. hash set Bloom filter: 1.2 GB for 1B URLs. O(1) lookup. Probabilistic (1% false positives). Cannot enumerate stored URLs. Cannot delete entries. Simple and fast. Disk-backed hash set (RocksDB): ~100 GB for 1B URLs. O(1) amortized lookup. Exact (zero false positives). Can enumerate and delete entries. More complex, slower (disk I/O). Use Bloom filter for the primary URL dedup check (fast, memory-efficient). Supplement with a disk-backed store (RocksDB) for the canonical URL set if you need to enumerate crawled URLs or support URL deletion. The Bloom filter handles the hot path (20,000 URL checks/sec); the disk store handles cold queries.
Interview Tip: When discussing trade-offs, connect them to the requirements: “We chose BFS over DFS because our goal is general-purpose crawling of 1 billion pages across the entire web, not deep crawling of a single site. BFS discovers high-authority pages first, which aligns with our priority system. We chose polite crawling because aggressive crawling gets us IP-banned, which would reduce our effective throughput to zero for those domains. Politeness is not just ethical — it is a practical requirement for sustained crawling. We chose a 1% Bloom filter false positive rate because the web’s link redundancy means any important page will be discovered via multiple paths.”
