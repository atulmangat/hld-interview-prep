Design Rate Limiter

Design a distributed rate limiting system that controls the rate of requests clients can send to an API, protecting services from abuse and ensuring fair resource allocation.

Medium Core Infrastructure Asked at: Stripe, Cloudflare, Amazon

1. Requirements

Functional Requirements

  • Limit by identifier: Throttle requests based on client IP address, authenticated user ID, or API key. Support multiple identification strategies simultaneously.
  • Return 429: When a client exceeds the allowed rate, return HTTP 429 Too Many Requests with appropriate headers indicating when the client can retry.
  • Per-API limits: Support different rate limits for different API endpoints (e.g., /api/login may allow 5 req/min while /api/search allows 100 req/min).
  • Configurable rules: Rate limiting rules should be configurable at runtime without redeploying services. Rules define the limit, time window, and grouping key.
  • Distributed rate limiting: Rate limits must be enforced consistently across multiple server instances. A client cannot bypass limits by having requests routed to different servers.
  • Rate limit headers: Every response must include standard rate limit headers so clients can self-regulate.

Non-Functional Requirements

  • Low latency: The rate limiter adds <10ms overhead per request. It sits in the critical path of every API call, so it must be extremely fast.
  • High availability: The rate limiter must be 99.99% available. If it goes down, the entire API becomes either unprotected or unavailable.
  • Fault tolerance: Define a clear policy for when the rate limiter is unreachable — fail-open (allow all requests) or fail-closed (reject all requests).
  • Accurate counting: Minimize race conditions in distributed environments. Slight over-counting is acceptable; significant under-counting (allowing abuse) is not.
  • Scalability: Handle millions of unique clients and hundreds of thousands of requests per second without degradation.
  • Minimal memory footprint: Efficiently track state for millions of clients without excessive memory consumption.
Interview Tip: Always clarify whether the rate limiter is client-side or server-side. In interviews, the focus is almost always on server-side rate limiting. Also clarify the failure mode early — fail-open vs fail-closed is a critical design decision that affects the entire architecture.

Middleware Placement: The rate limiter sits between the load balancer and the application server. It intercepts the request, checks the rate, and either forwards it to the app server or returns 429 directly — the application code never sees rate-limited requests.

4. Data Model

The rate limiter's state lives primarily in Redis. Each algorithm uses a different Redis data structure. The key pattern follows a consistent convention:

rate_limit:{client_id}:{endpoint}:{window_id}

Redis Key Patterns by Algorithm

Algorithm Redis Key Redis Type Value TTL
Token Bucket rl:tb:{client}:{endpoint} Hash { tokens: 8, last_refill: 1713100000 } Window size + buffer
Leaking Bucket rl:lb:{client}:{endpoint} List Queue of request timestamps Window size + buffer
Fixed Window rl:fw:{client}:{endpoint}:{window} String (counter) 27 (request count) Window size
Sliding Window Log rl:sl:{client}:{endpoint} Sorted Set Timestamps as scores and members Window size + buffer
Sliding Window Counter rl:sw:{client}:{endpoint}:{window} String (counter) Count per window (current + previous) 2 × window size

Rate Limit Rules (Configuration Store)

Rules are stored in a persistent database (PostgreSQL or DynamoDB) and cached in Redis or loaded into memory on each rate limiter instance at startup.

Column Type Description
rule_id VARCHAR(64) Primary key
endpoint_pattern VARCHAR(256) URL pattern (e.g., /api/v1/login, /api/v1/*)
key_type ENUM ip, user_id, api_key
max_requests INT Maximum requests allowed in the window
window_seconds INT Time window in seconds
algorithm ENUM token_bucket, sliding_window, etc.
action ENUM reject, throttle, log_only
enabled BOOLEAN Toggle rule on/off without deleting
updated_at TIMESTAMP Last modification time
Why Redis? Rate limiting requires sub-millisecond read-modify-write operations on counters. Redis provides atomic operations (INCR, EXPIRE, Lua scripts), in-memory speed (~0.1ms per operation), and built-in TTL for automatic key expiration. No disk-based database can match this latency profile.

Request Flow

1
Client sends an API request. The load balancer routes it to one of the API gateway / rate limiter middleware instances.
2
Extract identity: The middleware extracts the client identifier — IP address from X-Forwarded-For, user ID from the auth token, or API key from the header.
3
Match rule: Look up the applicable rate limit rule for this endpoint and client type from the in-memory rules cache.
4
Check Redis: Query Redis with the constructed key (e.g., rl:sw:{client_id}:{endpoint}:{window}). Execute the rate limiting algorithm atomically using a Lua script.
5a
Under limit: Redis returns the updated count. The middleware sets X-RateLimit-* headers and forwards the request to the app server.
5b
Over limit: Redis indicates the limit is exceeded. The middleware immediately returns 429 Too Many Requests with Retry-After header. The request never reaches the app server.
6
Fallback (Redis unreachable): If Redis is down, apply the configured failure policy — fail-open (allow the request) or fail-closed (reject with 503).
Critical Design Decision: The rate limiter must execute its check-and-update operation atomically. Without atomicity, two concurrent requests could both read the same counter value, both decide they are under the limit, and both increment — allowing the client to exceed the limit. Redis Lua scripts guarantee atomicity because Redis is single-threaded and executes Lua scripts without interruption.

6. Deep Dive

6a. Rate Limiting Algorithms

There are five major rate limiting algorithms. Each makes different trade-offs between accuracy, memory usage, burst tolerance, and implementation complexity. Understanding all five is essential for system design interviews.

Algorithm 1: Token Bucket

The most widely used algorithm. Used by Amazon API Gateway, Stripe, and most cloud providers.

How It Works
  1. A bucket holds tokens, with a maximum capacity of B tokens (the burst size).
  2. Tokens are added to the bucket at a fixed rate of R tokens per second (the refill rate).
  3. When a request arrives, it consumes 1 token from the bucket.
  4. If the bucket has ≥1 token, the request is allowed and the token count decreases by 1.
  5. If the bucket has 0 tokens, the request is rejected (429).
  6. The bucket never exceeds capacity B — excess tokens are discarded.
Step-by-Step Example
Config: capacity B = 4, refill rate R = 2 tokens/sec

Time 0.0s: Bucket = [4 tokens] (full)
Time 0.0s: Request 1 arrives → allowed, bucket = 3
Time 0.0s: Request 2 arrives → allowed, bucket = 2
Time 0.0s: Request 3 arrives → allowed, bucket = 1
Time 0.0s: Request 4 arrives → allowed, bucket = 0
Time 0.0s: Request 5 arrives → REJECTED (0 tokens)
Time 0.5s: Refill +1 token → bucket = 1
Time 0.5s: Request 6 arrives → allowed, bucket = 0
Time 1.0s: Refill +1 token → bucket = 1
Time 1.0s: Request 7 arrives → allowed, bucket = 0
Redis Implementation (Lua Script)
-- Token Bucket Lua Script
local key = KEYS[1]
local capacity = tonumber(ARGV[1])     -- max tokens (burst)
local refill_rate = tonumber(ARGV[2])  -- tokens per second
local now = tonumber(ARGV[3])          -- current timestamp (ms)
local requested = tonumber(ARGV[4])    -- tokens to consume (usually 1)

local data = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(data[1]) or capacity
local last_refill = tonumber(data[2]) or now

-- Calculate tokens to add based on elapsed time
local elapsed = (now - last_refill) / 1000
local new_tokens = math.min(capacity, tokens + elapsed * refill_rate)

local allowed = 0
if new_tokens >= requested then
  new_tokens = new_tokens - requested
  allowed = 1
end

redis.call('HMSET', key, 'tokens', new_tokens, 'last_refill', now)
redis.call('EXPIRE', key, math.ceil(capacity / refill_rate) + 1)

return { allowed, math.floor(new_tokens) }
Pros
  • Memory efficient: Only 2 values per client (token count + last refill timestamp).
  • Allows controlled bursts: A client that has been idle accumulates tokens up to B, allowing a short burst of requests.
  • Smooth long-term rate: Over time, the average rate converges to R requests/second regardless of bursts.
  • Simple to understand: Intuitive mental model.
Cons
  • Two parameters to tune (B and R) — choosing the right burst size requires understanding traffic patterns.
  • Bursts can temporarily overwhelm downstream services if B is set too high.

Algorithm 2: Leaking Bucket

Processes requests at a fixed, constant rate. Used when you need smooth, predictable output regardless of input burstiness.

How It Works
  1. Incoming requests are placed into a FIFO queue with a maximum size of B (the bucket size).
  2. Requests are pulled from the queue and processed at a fixed rate of R requests per second — like water leaking from a bucket at a constant drip rate.
  3. If the queue is full when a new request arrives, the request is rejected (429).
  4. The output rate is always exactly R, regardless of how bursty the input is.
Step-by-Step Example
Config: queue size B = 3, outflow rate R = 1 req/sec

Time 0.0s: Queue = []
Time 0.0s: Req 1 arrives → queued. Queue = [R1]
Time 0.0s: Req 2 arrives → queued. Queue = [R1, R2]
Time 0.0s: Req 3 arrives → queued. Queue = [R1, R2, R3]
Time 0.0s: Req 4 arrives → REJECTED (queue full)
Time 0.0s: R1 processed (leaked out). Queue = [R2, R3]
Time 1.0s: R2 processed. Queue = [R3]
Time 1.0s: Req 5 arrives → queued. Queue = [R3, R5]
Time 2.0s: R3 processed. Queue = [R5]
Pros
  • Smooth output rate: Downstream services receive requests at a perfectly constant rate, preventing overload.
  • Memory efficient: Bounded queue size.
  • Simple implementation: Just a FIFO queue with a fixed drain rate.
Cons
  • No burst tolerance: Even legitimate traffic spikes are queued and delayed, increasing latency for users.
  • Starvation risk: If the queue fills with old requests during a burst, newer (potentially more important) requests are rejected while old ones are still waiting.
  • Not ideal for APIs: Users experience unpredictable latency because their request sits in a queue. Most API rate limiters prefer immediate accept/reject over queuing.

Algorithm 3: Fixed Window Counter

The simplest algorithm. Divides time into fixed windows and counts requests per window.

How It Works
  1. Time is divided into fixed windows of size W seconds (e.g., 60-second windows).
  2. Each window has a counter starting at 0.
  3. When a request arrives, increment the counter for the current window.
  4. If the counter exceeds the limit L, reject the request.
  5. When the window expires, the counter resets to 0.
Redis Implementation
-- Fixed Window Counter
local key = KEYS[1]                    -- e.g., rl:fw:user123:/api:1713100800
local limit = tonumber(ARGV[1])        -- max requests per window
local window_seconds = tonumber(ARGV[2])

local current = redis.call('INCR', key)
if current == 1 then
  redis.call('EXPIRE', key, window_seconds)
end

if current > limit then
  return { 0, 0 }  -- rejected, 0 remaining
end

return { 1, limit - current }  -- allowed, remaining
The Boundary Burst Problem

This is the critical flaw of fixed window counters:

Limit: 100 requests per minute

Window 1: [12:00:00 — 12:00:59]
Window 2: [12:01:00 — 12:01:59]

Scenario:
  12:00:30 — 12:00:59: Client sends 100 requests (allowed, fills window 1)
  12:01:00 — 12:01:30: Client sends 100 requests (allowed, new window 2)

Result: 200 requests in a 60-second span (12:00:30 — 12:01:30)
        That's 2x the intended limit!
Boundary Burst: A client can send up to 2x the rate limit by concentrating requests at the boundary between two windows. This is the primary reason fixed window counters are not used in production for strict rate limiting.
Pros
  • Extremely simple: Just INCR + EXPIRE in Redis.
  • Memory efficient: One counter per client per window.
  • Fast: O(1) per request.
Cons
  • Boundary burst problem: Allows up to 2x the limit at window edges.
  • Not suitable for strict rate limiting where accuracy matters.

Algorithm 4: Sliding Window Log

Maintains an exact log of all request timestamps. The most accurate algorithm but the most memory-intensive.

How It Works
  1. For each client, maintain a sorted set of request timestamps.
  2. When a request arrives at time T:
    1. Remove all entries older than T - W (outside the window).
    2. Count the remaining entries.
    3. If count < limit, add the new timestamp and allow the request.
    4. If count ≥ limit, reject the request (do not add the timestamp).
Redis Implementation (Lua Script)
-- Sliding Window Log using Sorted Set
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window_ms = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local window_start = now - window_ms

-- Remove expired entries
redis.call('ZREMRANGEBYSCORE', key, '-inf', window_start)

-- Count requests in current window
local count = redis.call('ZCARD', key)

if count < limit then
  -- Allow: add this request's timestamp
  redis.call('ZADD', key, now, now .. ':' .. math.random(1000000))
  redis.call('EXPIRE', key, math.ceil(window_ms / 1000) + 1)
  return { 1, limit - count - 1 }  -- allowed, remaining
end

return { 0, 0 }  -- rejected
Step-by-Step Example
Limit: 3 requests per 60 seconds

Time 12:00:10: Request → Log = [12:00:10]. Count=1 ≤ 3 → ALLOWED
Time 12:00:25: Request → Log = [12:00:10, 12:00:25]. Count=2 ≤ 3 → ALLOWED
Time 12:00:40: Request → Log = [12:00:10, 12:00:25, 12:00:40]. Count=3 ≤ 3 → ALLOWED
Time 12:00:50: Request → Count=3 ≥ 3 → REJECTED
Time 12:01:11: Remove entries before 12:00:11 → Log = [12:00:25, 12:00:40]. Count=2 ≤ 3 → ALLOWED
Pros
  • Perfectly accurate: No boundary burst problem. The window slides precisely with each request.
  • No approximation: Every request is tracked individually.
Cons
  • Memory intensive: Stores every timestamp. A client with a limit of 10,000 req/hour stores 10,000 entries. At scale (1M clients), this is 10 billion entries.
  • Slower: ZREMRANGEBYSCORE and ZCARD are O(log N) + O(1), but the constant factors and memory overhead are significant compared to a simple counter.
  • Rejected requests still consume cleanup cost: Even rejected requests trigger the removal of expired entries.

Algorithm 5: Sliding Window Counter

A hybrid of fixed window counter and sliding window log. Provides near-perfect accuracy with the memory efficiency of a simple counter. This is the recommended algorithm for most production systems.

How It Works
  1. Maintain counters for the current window and the previous window.
  2. When a request arrives, compute a weighted count using the overlap between the sliding window and the fixed windows:
weighted_count = (prev_window_count × overlap_percentage) + current_window_count

Where:
  overlap_percentage = (window_size - elapsed_time_in_current_window) / window_size
  1. If weighted_count < limit, allow the request and increment the current window counter.
  2. If weighted_count ≥ limit, reject the request.
Step-by-Step Example
Limit: 100 requests per 60-second window

Previous window [12:00:00 - 12:00:59]: 84 requests
Current window  [12:01:00 - 12:01:59]: 36 requests so far

Current time: 12:01:15 (15 seconds into current window)

overlap_percentage = (60 - 15) / 60 = 0.75

weighted_count = (84 × 0.75) + 36
               = 63 + 36
               = 99

99 < 100 → ALLOWED (1 remaining)

Next request at 12:01:16:
  weighted_count = (84 × 0.733) + 37 = 61.6 + 37 = 98.6 → ALLOWED

This smoothly transitions between windows without the boundary burst problem!
Redis Implementation
-- Sliding Window Counter
local current_key = KEYS[1]   -- rl:sw:user123:/api:1713100860
local prev_key = KEYS[2]      -- rl:sw:user123:/api:1713100800
local limit = tonumber(ARGV[1])
local window_size = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- Calculate position in current window
local current_window_start = now - (now % window_size)
local elapsed = now - current_window_start
local overlap = (window_size - elapsed) / window_size

local prev_count = tonumber(redis.call('GET', prev_key) or '0')
local curr_count = tonumber(redis.call('GET', current_key) or '0')

local weighted = math.floor(prev_count * overlap) + curr_count

if weighted >= limit then
  return { 0, 0 }  -- rejected
end

-- Allow: increment current window
redis.call('INCR', current_key)
redis.call('EXPIRE', current_key, window_size * 2)

return { 1, limit - weighted - 1 }  -- allowed, remaining
Pros
  • Memory efficient: Only 2 counters per client (current + previous window) — same as fixed window.
  • Near-perfect accuracy: Cloudflare's experiments show only 0.003% of requests are incorrectly allowed or rejected compared to a perfect sliding window.
  • No boundary burst: The weighted formula smoothly handles window transitions.
  • Fast: O(1) per request — just GET + INCR.
Cons
  • Approximation: Assumes requests in the previous window were evenly distributed. In practice, this is a very good assumption for high-traffic APIs.
  • Slightly more complex than fixed window (but much simpler than sliding window log).

Algorithm Comparison Summary

Algorithm Memory per Client Accuracy Burst Handling Complexity Best For
Token Bucket ~16 bytes Good Allows controlled bursts Low APIs needing burst tolerance (AWS, Stripe)
Leaking Bucket ~8 bytes + queue Good No bursts (smooth output) Low Smoothing bursty traffic (message queues)
Fixed Window ~8 bytes Poor (2x burst at edges) Boundary burst problem Very Low Non-critical, approximate limiting
Sliding Window Log ~8 bytes × N requests Perfect Exact enforcement Medium Low-volume, strict limits (login attempts)
Sliding Window Counter ~16 bytes Near-perfect (99.997%) Smooth transitions Low High-volume APIs (Cloudflare, general use)
Interview Recommendation: Lead with Token Bucket or Sliding Window Counter. Token Bucket is the industry standard (used by AWS, Stripe, most API gateways). Sliding Window Counter is the best balance of accuracy and efficiency. Mention the others to show breadth, and explain the fixed window boundary burst problem to demonstrate depth.

6b. Distributed Rate Limiting

When multiple rate limiter instances run behind a load balancer, they must share state. Otherwise, a client could send N requests to each of M servers, effectively getting M × N requests through.

Centralized Store (Redis)

The standard approach: all rate limiter instances read/write to a shared Redis cluster.

1
Request arrives at any rate limiter instance.
2
Instance sends a Lua script to Redis that atomically checks and updates the counter.
3
Redis executes the script in a single-threaded context — no race conditions.
4
Redis returns the result (allowed/rejected + remaining count).
5
Instance either forwards the request or returns 429.

Race Conditions and Atomicity

The most dangerous race condition in distributed rate limiting:

WITHOUT atomicity (broken):
  Server A: reads counter = 99 (limit is 100)
  Server B: reads counter = 99 (limit is 100)
  Server A: counter < 100, allows request, writes counter = 100
  Server B: counter < 100, allows request, writes counter = 100
  Result: 101 requests allowed! Limit violated.

WITH Redis Lua script (correct):
  Server A: sends Lua script → Redis executes atomically → counter 99→100, allowed
  Server B: sends Lua script → Redis executes atomically → counter 100→100, REJECTED
  Result: Exactly 100 requests allowed. Limit enforced.
Never use separate GET + SET: The pattern GET counter → check → INCR counter as separate Redis commands is NOT atomic. Between the GET and INCR, another instance can interleave. Always use either: (1) Lua scripts, (2) MULTI/EXEC transactions, or (3) Redis INCR with post-check (increment first, then check if over limit and roll back).

Synchronization Strategies

Strategy How It Works Trade-off
Centralized Redis All instances share one Redis cluster. Every request hits Redis. Perfectly accurate but adds ~1ms network latency per request. Redis becomes a single point of failure.
Local + Sync Each instance keeps a local counter and periodically syncs with Redis (e.g., every 100ms). Lower latency (local check is ~0.01ms) but allows temporary over-limit during sync gaps. Good for soft limits.
Sticky Sessions Load balancer routes all requests from the same client to the same server. Local counter is sufficient. Simple but breaks if a server goes down (client gets a fresh counter on the new server). Not truly distributed.
Split Limit Divide the global limit by the number of instances. Each instance enforces limit/N locally. No coordination needed, but uneven traffic distribution wastes capacity. If 1 of 4 servers gets all traffic, the effective limit is 25% of intended.

6c. Where to Place the Rate Limiter

Option 1: API Gateway (Recommended)

Rate limiting is built into the API gateway layer (e.g., Kong, AWS API Gateway, Envoy).

  • Centralized enforcement — all traffic passes through the gateway.
  • Decoupled from application code — developers don't need to implement rate limiting.
  • Can enforce limits before authentication, reducing load on auth services.
  • Supports multiple rate limiting strategies per route.

Option 2: Application Middleware

Rate limiting logic is embedded in the application as middleware (e.g., Express middleware, Spring filter).

  • More control — can rate limit based on business logic (e.g., user tier, subscription plan).
  • No additional infrastructure component.
  • But: every service must implement it, leading to inconsistency.
  • Rate limiting happens after TLS termination and routing — more work is done before rejection.

Option 3: Sidecar Proxy (Service Mesh)

Rate limiting runs as a sidecar (e.g., Envoy in Istio) alongside each service instance.

  • Language-agnostic — works with any service regardless of tech stack.
  • Consistent enforcement across all services in the mesh.
  • But: adds operational complexity (service mesh infrastructure).
  • Sidecar-to-Redis latency is the same as application-to-Redis.

6d. Client-Side vs Server-Side Rate Limiting

Aspect Client-Side Server-Side
Enforcement Client voluntarily limits its own request rate Server enforces limits regardless of client behavior
Security Easily bypassed — client can ignore limits Cannot be bypassed — server has final authority
Use case Well-behaved SDK clients (e.g., AWS SDK with exponential backoff) Protecting APIs from all clients, including malicious ones
Implementation Read Retry-After header, implement backoff Middleware with Redis-backed counters
Verdict Complementary — reduces unnecessary 429s Required — the actual enforcement layer
Best Practice: Always implement server-side rate limiting as the source of truth. Client-side rate limiting is a courtesy optimization — well-behaved clients read the X-RateLimit-Remaining header and slow down before hitting 429, reducing wasted requests and improving user experience.

6e. Redis High Availability for Rate Limiting

  • Redis Cluster: Shard rate limit keys across multiple Redis nodes using hash slots. Each client's keys consistently map to the same shard.
  • Redis Sentinel: For smaller deployments, use Sentinel for automatic failover. A replica is promoted to primary if the primary fails.
  • Replication lag: During failover, the new primary may have slightly stale data. This means a few extra requests may be allowed during the failover window (~1-2 seconds). This is acceptable for most use cases.
  • Multi-region: For global rate limiting, either use a single Redis cluster in one region (adds cross-region latency) or use per-region Redis with periodic sync (allows temporary over-limit across regions).

7. Trade-offs

Decision Option A Option B Recommendation
Fail-open vs Fail-closed Fail-open: if Redis is down, allow all requests. Availability over protection. Fail-closed: if Redis is down, reject all requests. Protection over availability. Fail-open for most APIs. Availability is usually more important than temporary loss of rate limiting. Fail-closed only for security-critical endpoints (login, payment).
Accuracy vs Performance Sliding window log: perfect accuracy but high memory and O(log N) per request. Sliding window counter: 99.997% accuracy with O(1) per request and minimal memory. Sliding window counter. The 0.003% inaccuracy is negligible, and the performance gain is massive at scale.
Centralized vs Distributed counters Centralized Redis: perfectly accurate, but adds ~1ms latency and Redis is a dependency. Local counters with periodic sync: faster but temporarily inaccurate during sync gaps. Centralized Redis for hard limits. Local + sync for soft limits where slight over-counting is acceptable.
Hard vs Soft rate limiting Hard: strictly reject all requests over the limit. No exceptions. Soft: allow a small percentage of over-limit requests (e.g., 110% of limit) to handle edge cases gracefully. Hard limits for abuse prevention and billing. Soft limits for general API protection where occasional bursts are acceptable.
Gateway vs Application placement API Gateway: centralized, consistent, but less context about business logic. Application middleware: more context (user tier, subscription), but inconsistent across services. Both. Gateway for global IP-based limits and DDoS protection. Application for business-logic-aware limits (per-tier, per-plan).
Single vs Multi-key limiting Single key (e.g., just IP): simple but can't differentiate between users behind the same NAT. Multi-key (IP + user ID + API key): more granular but more Redis lookups per request. Multi-key with hierarchical evaluation. Check API key first (most specific), fall back to user ID, then IP. Use Redis pipeline to batch lookups.
Synchronous vs Asynchronous limiting Synchronous: check Redis before every request. Accurate but adds latency. Asynchronous: allow request immediately, update counter in background. Fast but may over-allow. Synchronous for enforcement. The ~1ms Redis latency is acceptable. Asynchronous only for analytics/monitoring (counting without blocking).
