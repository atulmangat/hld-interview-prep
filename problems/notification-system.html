Design a Notification System

Design a scalable, multi-channel notification system that delivers push notifications (iOS APNs, Android FCM), SMS (Twilio), and email (SendGrid/SES) — supporting user preferences, scheduling, templating, rate limiting, and reliable at-least-once delivery at scale.

Medium Messaging Asked at: Apple, Google, Uber

1. Requirements

Functional Requirements

  • Push notifications — Send push notifications to iOS devices via APNs (Apple Push Notification service) and Android devices via FCM (Firebase Cloud Messaging).
  • SMS — Send text messages via third-party providers such as Twilio or Vonage.
  • Email — Send transactional and marketing emails via SendGrid, Amazon SES, or Mailgun.
  • User preferences — Users can opt in/out of specific notification types and channels (e.g., “marketing emails: off, order updates via push: on”).
  • Scheduling — Support scheduled notifications (e.g., “send this reminder at 9 AM in the user’s timezone”).
  • Templating — Notifications use pre-defined templates with variable substitution for personalization (e.g., “Hi {{first_name}}, your order #{{order_id}} has shipped”).
  • Rate limiting — Enforce per-user rate limits to prevent notification fatigue (e.g., max 5 push notifications per hour per user).

Non-Functional Requirements

  • Soft real-time: Notifications delivered within 30 seconds of being triggered for non-scheduled messages.
  • At-least-once delivery: Every notification must be delivered at least once. Duplicates are acceptable but should be minimized.
  • High throughput: Handle 10 million notifications per day across all channels.
  • Pluggable providers: The system should support swapping or adding third-party providers without changing core logic (e.g., switch from Twilio to Vonage for SMS).
  • Observability: Track delivery status, open rates, click rates, and failure reasons for every notification.
  • Fault tolerance: No single point of failure. The system continues operating if a provider is temporarily unavailable.
Interview Tip: Clarify the notification types early. “Are we designing for transactional notifications (order confirmations, OTPs), marketing notifications (promotions, re-engagement), or both?” Transactional notifications have stricter latency and reliability requirements. Also ask about scale: 10M/day is moderate; 1B/day (like Facebook or WhatsApp) requires a fundamentally different architecture.

2. Capacity Estimation

Assumptions

Parameter Value Notes
Total notifications/day 10 million Across all channels (push, SMS, email)
Channel breakdown Push: 50%, Email: 35%, SMS: 15% Push is cheapest; SMS is most expensive
Average notification size ~1 KB Includes metadata, template-rendered body, recipient info
Peak-to-average ratio ~10x Spikes during flash sales, breaking news, scheduled campaigns
Retention period 90 days For notification history and analytics

Throughput Calculation

Average throughput = 10M / 86,400 sec
                   ≈ 115 notifications/sec

Peak throughput    = 115 × 10
                   ≈ 1,150 notifications/sec (~1,000/sec)

Per channel (average):
  Push:  ~58/sec  (5M/day)
  Email: ~40/sec  (3.5M/day)
  SMS:   ~17/sec  (1.5M/day)

Storage Calculation

Per notification   = ~1 KB (payload + metadata + status)

Daily storage      = 10M × 1 KB
                   = 10 GB/day

90-day retention   = 10 GB × 90
                   = 900 GB (~1 TB with indexes and logs)

Notification log   = ~2 KB per entry (includes delivery attempts, timestamps)
                   = 20 GB/day → 1.8 TB for 90 days
Key Insight: At 10M notifications/day (~115/sec average), the throughput challenge is modest. The real engineering challenges are (1) handling peak bursts (1,000/sec) without dropping messages, (2) managing third-party provider rate limits and failures, (3) ensuring at-least-once delivery with retries, and (4) preventing notification spam through rate limiting. Message queues are essential for absorbing traffic spikes.

3. API Design

POST /api/v1/notifications

Send a notification to one or more users. The system determines the delivery channel(s) based on user preferences and the notification type.

Request:
  POST /api/v1/notifications
  Headers:
    Content-Type: application/json
    Authorization: Bearer <service-api-key>
    X-Idempotency-Key: "order-shipped-12345"   // prevent duplicate sends
  Body:
  {
    "type": "transactional",
    "template_id": "order_shipped_v2",
    "recipients": [
      { "user_id": "u_98765" },
      { "user_id": "u_11223" }
    ],
    "channels": ["push", "email"],             // optional override
    "priority": "high",                        // high | normal | low
    "data": {
      "first_name": "Alice",
      "order_id": "ORD-12345",
      "tracking_url": "https://track.example.com/ORD-12345"
    },
    "schedule_at": null                        // null = send immediately
  }

Response (202 Accepted):
{
  "notification_id": "ntf_abc123",
  "status": "queued",
  "recipients_count": 2,
  "estimated_delivery": "2025-04-14T10:00:30Z",
  "idempotency_key": "order-shipped-12345"
}

Update a user’s notification preferences. Controls which channels and notification types the user wants to receive.

Request:
  PUT /api/v1/preferences/u_98765
  Headers:
    Content-Type: application/json
    Authorization: Bearer <user-token>
  Body:
  {
    "channels": {
      "push": { "enabled": true, "quiet_hours": { "start": "22:00", "end": "08:00" } },
      "email": { "enabled": true },
      "sms": { "enabled": false }
    },
    "categories": {
      "order_updates": { "push": true, "email": true, "sms": false },
      "marketing": { "push": false, "email": true, "sms": false },
      "security_alerts": { "push": true, "email": true, "sms": true }
    },
    "timezone": "America/Los_Angeles"
  }

Response (200 OK):
{
  "user_id": "u_98765",
  "preferences_updated": true,
  "updated_at": "2025-04-14T10:05:00Z"
}
Idempotency is Critical: Without idempotency keys, retries from upstream services can cause duplicate notifications. The notification service must deduplicate using the X-Idempotency-Key header. Store processed idempotency keys in a cache (Redis) with a TTL (e.g., 24 hours). If a duplicate request arrives, return the original response without re-sending.

Append-only log of every delivery attempt for auditing and debugging.

Column Type Description
log_id UUID (PK) Unique log entry identifier
notification_id UUID (FK, indexed) Reference to the notification
attempt_number INT Retry attempt (1, 2, 3, ...)
provider VARCHAR Provider used (apns, fcm, twilio, sendgrid)
status ENUM sent, delivered, failed, bounced, dropped
provider_response JSON Raw response from the third-party provider
error_code VARCHAR Error code if failed (e.g., INVALID_TOKEN, RATE_LIMITED)
latency_ms INT Time taken for the provider call
created_at TIMESTAMP When this attempt was made
Storage Strategy: The notifications table is the primary source of truth and lives in a relational database (PostgreSQL) for transactional integrity. The notification_log table is append-heavy and grows fast — consider using a time-series database (TimescaleDB) or columnar store (ClickHouse) for efficient analytics queries. Partition both tables by created_at for efficient retention and purging.

5. High-Level Design

The architecture follows a fan-out on write pattern: when a notification is triggered, it is validated, enriched with user preferences and templates, then routed to channel-specific message queues. Dedicated worker pools consume from each queue and deliver via third-party providers.

Key Components

  • Notification Service: Stateless API layer that validates requests, checks idempotency keys, looks up user preferences, renders templates, applies rate limiting, and routes messages to the appropriate channel queue.
  • Message Queues (per channel): Separate queues for push, email, and SMS decouple the ingestion rate from the delivery rate. This absorbs traffic spikes and allows independent scaling of each channel’s worker pool.
  • Channel Workers: Dedicated worker pools consume from each queue and call the corresponding third-party provider API. Workers handle retries, circuit breaking, and status callbacks.
  • Third-Party Providers: APNs/FCM for push, Twilio/Vonage for SMS, SendGrid/SES for email. Each has its own rate limits, payload formats, and delivery semantics.
  • Scheduler: A separate service that polls for scheduled notifications and enqueues them when their schedule_at time arrives. Can use a delay queue (SQS delay) or a scheduled job framework.
Why Separate Queues Per Channel? Each channel has vastly different throughput characteristics and failure modes. APNs supports ~10K pushes/sec per connection, while Twilio SMS may be rate-limited to 100/sec. A slow SMS provider should not block push delivery. Separate queues allow independent scaling, backpressure handling, and retry policies per channel.

6. Deep Dive

6a. Notification Channels — How Each Works

Each delivery channel has unique protocols, payload constraints, and delivery semantics that the worker must handle.

Push Notifications (APNs / FCM)

Protocol: HTTP/2 persistent connections to Apple/Google servers. Device tokens are obtained when the user installs the app and grants notification permission.

  • APNs (iOS): Max payload 4 KB. Uses JWT or certificate auth. Provides delivery receipts. Tokens expire when user uninstalls.
  • FCM (Android): Max payload 4 KB. Uses server key auth. Supports topics (broadcast to groups). Token refresh on app update.
  • Failure modes: Invalid token (user uninstalled), rate limited, payload too large, expired certificate.
  • Latency: Typically <1 second for delivery.

SMS (Twilio / Vonage)

Protocol: REST API calls to the SMS provider. Messages are routed through carrier networks. Delivery is best-effort.

  • Payload: 160 characters (GSM-7) or 70 characters (Unicode). Longer messages are split into segments.
  • Cost: $0.0075–$0.05 per message (most expensive channel).
  • Failure modes: Invalid number, carrier filtering, rate limits, opt-out (STOP keyword).
  • Latency: 1–30 seconds depending on carrier.

Email (SendGrid / SES)

Protocol: SMTP or REST API. Emails pass through sender authentication (SPF, DKIM, DMARC) and spam filters before reaching the inbox.

  • Payload: HTML + plain text. Attachments supported. No strict size limit (typically <25 MB).
  • Cost: $0.0001–$0.001 per email (cheapest channel at scale).
  • Failure modes: Bounce (hard/soft), spam folder, rate limits, domain reputation issues.
  • Latency: 1–60 seconds. Spam filtering can add delay.

6b. Reliability — Retry, DLQ, and Idempotency

At-least-once delivery requires robust retry logic. Not all failures are retryable, and unbounded retries can overwhelm providers.

Retry with Exponential Backoff

Dead Letter Queue (DLQ)

Messages that exhaust all retry attempts are moved to a Dead Letter Queue. The DLQ serves as a safety net — no message is silently lost. An on-call engineer or automated process can inspect DLQ messages, fix the underlying issue, and replay them.

Idempotency

graph TD REQ[Request arrives with Idempotency Key] --> CHK[Check Redis for key] CHK -->|Key EXISTS| CACHED[Return cached response - HTTP 200] CHK -->|Key NOT EXISTS| PROC[Process notification] PROC --> STORE[Store in Redis with TTL 24h] STORE --> RESP[Return new response - HTTP 202]
Interview Tip: Mention that idempotency protects against two distinct scenarios: (1) upstream service retries (the Order Service sends the same “order shipped” event twice due to a timeout), and (2) internal retries (a worker crashes after sending to the provider but before acknowledging the queue message, causing the message to be redelivered).

6c. Notification Priority & Rate Limiting

Not all notifications are equal. A 2FA OTP code is more urgent than a marketing email. Rate limiting prevents notification fatigue and protects users from spam.

Per-User Rate Limiting

Rate Limiting Rules (configurable per notification type):

  Push notifications:
    - Max 5 per hour per user (marketing)
    - Max 20 per hour per user (transactional)
    - No limit for security alerts (OTP, password reset)

  SMS:
    - Max 3 per day per user (most expensive channel)
    - No limit for OTP/2FA

  Email:
    - Max 10 per day per user (marketing)
    - No limit for transactional

Implementation: Sliding window counter in Redis
  Key:   rate:{user_id}:{channel}:{type}:{window}
  Value: count
  TTL:   window duration

  Example:
    INCR rate:u_98765:push:marketing:2025-04-14-10
    → Returns 4 (under limit of 5/hour)
    → Allow notification

    INCR rate:u_98765:push:marketing:2025-04-14-10
    → Returns 6 (over limit of 5/hour)
    → DROP notification, log as "rate_limited"
Don’t Spam Your Users: Notification fatigue is a real problem. Users who receive too many notifications disable them entirely or uninstall the app. Rate limiting is not just a technical safeguard — it directly impacts user retention. Uber, for example, limits promotional push notifications to 2–3 per week per user.

6f. User Preference Management

The preference system acts as a gatekeeper — every notification is checked against user preferences before being enqueued for delivery.

Regulatory Compliance: User preferences are not just a feature — they are a legal requirement. GDPR (EU), CAN-SPAM (US), and TCPA (US) mandate that users can opt out of marketing communications. Transactional notifications (order confirmations, security alerts) are generally exempt, but SMS requires explicit opt-in in most jurisdictions. Always include an unsubscribe mechanism.

7. Trade-offs

Decision Option A Option B Recommendation
At-Least-Once vs Exactly-Once Delivery At-least-once: Simpler implementation. Retry on failure. May send duplicates. Requires idempotency keys for dedup on the consumer side. Exactly-once: No duplicates. Requires distributed transactions or two-phase commit between queue and provider. Significantly more complex and slower. Use at-least-once with idempotency keys. Exactly-once is impractical when third-party providers are involved — you cannot transactionally coordinate with APNs or Twilio. Occasional duplicate notifications are acceptable; missing notifications are not.
Push vs Pull for Mobile Push (APNs/FCM): Server pushes to device via persistent connection maintained by the OS. Low latency. Battery-efficient (OS manages connection). Requires device token management. Pull (Polling): Device periodically polls server for new notifications. Simpler server-side. Higher latency. Battery drain from frequent polling. Wastes bandwidth on empty polls. Use push via APNs/FCM for real-time notifications. This is the industry standard — Apple and Google maintain the persistent connections and handle battery optimization. Polling is only appropriate for in-app notification feeds (pull on app open).
Third-Party Providers vs In-House Third-party (Twilio, SendGrid): Fast to integrate. Handles carrier/ISP relationships, deliverability, compliance. Pay-per-message pricing. Vendor lock-in risk. In-house: Full control. No per-message cost at scale. Requires building SMTP infrastructure, carrier relationships, deliverability monitoring. Months of engineering effort. Start with third-party providers and design a pluggable provider interface. At very high scale (100M+ emails/day), consider bringing email in-house. SMS and push almost always use third-party providers because carrier/OS relationships are impractical to build.
Real-Time vs Batched Delivery Real-time: Send immediately when triggered. Best for transactional (OTP, order updates). Higher infrastructure cost. Each notification is an individual API call to the provider. Batched: Aggregate notifications and send in batches (e.g., daily digest email). Lower cost. Reduces notification fatigue. Higher latency. Better for marketing and low-priority updates. Use real-time for transactional and batched for marketing. Implement a digest system that aggregates low-priority notifications into a single daily/weekly summary. This reduces cost and improves user experience.
Single Queue vs Per-Channel Queues Single queue: Simpler architecture. Workers pick any message. One slow channel blocks all channels (head-of-line blocking). Harder to scale independently. Per-channel queues: Independent scaling per channel. No cross-channel blocking. More queues to manage. Slightly more complex routing logic. Use per-channel queues. The operational complexity is minimal (3 queues), and the benefits are significant: independent scaling, isolated failure domains, and channel-specific retry policies.
Synchronous vs Asynchronous API Synchronous: API blocks until notification is delivered. Caller knows delivery status immediately. High latency (seconds). Ties up caller resources. Asynchronous: API returns immediately with “queued” status (HTTP 202). Delivery happens in background. Caller must poll or use webhooks for status. Low latency for the caller. Use asynchronous (HTTP 202). Notification delivery inherently involves third-party APIs with unpredictable latency. Blocking the caller for seconds is unacceptable. Provide a status callback webhook or a polling endpoint for delivery confirmation.
Interview Tip: The strongest answer connects trade-offs to real-world constraints. “We use at-least-once because exactly-once is impossible when the delivery endpoint is a third-party API like APNs — if our worker sends the push but crashes before ACKing the queue, the message will be redelivered and sent again. We mitigate this with idempotency keys, but the user might still see a duplicate push notification — which is far better than missing a critical OTP code.”
