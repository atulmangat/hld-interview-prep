Design Metrics Monitoring & Alerting

Design a scalable metrics monitoring and alerting system like Datadog or Prometheus — supporting collection of infrastructure and application metrics (CPU, memory, disk, network, custom business metrics), time-series storage with long-term retention and downsampling, flexible querying and dashboard visualization, and configurable alerting with threshold-based and anomaly detection rules.

Medium Platform Asked at: Datadog, Amazon, Google

1. Requirements

Functional Requirements

  • Collect metrics from servers, services, and applications — Support infrastructure metrics (CPU utilization, memory usage, disk I/O, network throughput) and custom business metrics (request count, error rate, checkout conversions). Agents running on each host collect and forward metrics at a configurable interval.
  • Store time-series data efficiently — Each data point is a (metric_name, tags, timestamp, value) tuple. The system must handle extremely high write throughput and store data for long retention periods with automatic downsampling to manage storage costs.
  • Query and visualize metrics via dashboards — Users create dashboards with panels that query metrics over time ranges. Support time-range queries, aggregation functions (avg, sum, min, max, count, p50, p95, p99), GROUP BY tags (e.g., by host, region, service), and a query language (PromQL-like).
  • Configurable alerting — Define alert rules based on metric thresholds (e.g., CPU > 90% for 5 minutes), rate of change, or anomaly detection. Alerts transition through states: pending → firing → resolved. Notifications sent via PagerDuty, Slack, email, or webhooks.
  • Support aggregation over time windows — Compute rolling aggregations: avg, sum, p99, count over configurable time windows (1 min, 5 min, 1 hr). Support both real-time streaming aggregation and historical batch aggregation for dashboard queries.

Non-Functional Requirements

  • Scale: 100K servers, each emitting 1,000 metrics, collected every 10 seconds. This produces 10 million data points per second sustained write throughput.
  • Retention: 1 year of data. Raw resolution (10s) kept for 7 days, 1-minute aggregates for 30 days, 1-hour aggregates for 1 year. Automatic downsampling reduces storage by ~99%.
  • Write throughput: The system must ingest 10M data points/sec (~1 GB/sec) with no backpressure on agents. Writes must be durable — no silent data loss.
  • Query latency: Dashboard queries must return within 1 second for typical time ranges (last 1 hour, last 24 hours). Queries over longer ranges (30 days) may take 2–5 seconds using pre-aggregated data.
  • High availability: The monitoring system must be more reliable than the systems it monitors. Target 99.99% uptime. Alerting pipeline must have no single point of failure — a missed alert can cause an outage to go undetected.
Interview Tip: Start by clarifying the scope: “Are we designing a metrics system (numerical time-series data like CPU, latency, request count) or a logging system (unstructured text logs)?” These are fundamentally different. Metrics are fixed-schema numerical values sampled at regular intervals — they compress well and support mathematical aggregation. Logs are variable-length text events — they require full-text indexing and different storage strategies. This design focuses on metrics. Also clarify: “Is this a pull-based system (like Prometheus, where the server scrapes targets) or push-based (like Datadog/StatsD, where agents push to the server)?” We will discuss both approaches.

Storage Calculation

RAW DATA (10-second resolution, 7-day retention):
  10M points/sec × 86,400 sec/day = 864 billion points/day
  864B points × 7 days = 6.05 trillion points

  Uncompressed: 6.05T × 100 bytes = 605 TB
  With TSDB compression (12x, Gorilla encoding): 605 TB / 12 ≈ 50 TB

1-MINUTE AGGREGATES (30-day retention):
  Raw points reduced by 6x (60s / 10s = 6 samples → 1 aggregate)
  10M / 6 = 1.67M points/sec at 1-min resolution
  1.67M × 86,400 × 30 days = 4.3 trillion points
  With compression: 4.3T × 16 bytes / 12 ≈ 5.7 TB

1-HOUR AGGREGATES (1-year retention):
  1-min points reduced by 60x (60 min → 1 aggregate)
  1.67M / 60 = 27.8K points/sec at 1-hr resolution
  27.8K × 86,400 × 365 days = 877 billion points
  With compression: 877B × 16 bytes / 12 ≈ 1.2 TB

TOTAL STORAGE:
  Raw (7d):     ~50 TB
  1-min (30d):  ~5.7 TB
  1-hr (1yr):   ~1.2 TB
  ────────────────────────
  Total:        ~57 TB (vs. ~31 PB without downsampling!)

Downsampling reduces 1-year storage from 31 PB to 57 TB — a 99.8% reduction.

Throughput Requirements

WRITE PATH:
  10M data points/sec ingestion
  With batching and compression: ~100 MB/sec effective write I/O
  Across 20 TSDB nodes: ~5 MB/sec per node (very manageable)

READ PATH (QUERIES):
  Assume 1,000 dashboard queries/sec (across all users)
  Each query scans ~10K–1M data points
  With pre-aggregated rollups: most queries hit 1-min or 1-hr data
  Target: <1 second per query

ALERTING:
  10,000 alert rules evaluated every 60 seconds
  Each rule queries 1–10 time series
  ~100K time-series evaluations per minute
Key Insight: The numbers reveal that a metrics system is a write-heavy, read-light workload. 10M writes/sec but only ~1K queries/sec. This is the opposite of most web applications. The storage engine must be optimized for high write throughput and time-range scans, not random reads or point lookups. This is exactly why purpose-built time-series databases (not general-purpose RDBMS or key-value stores) are essential. Downsampling is the single most impactful optimization — it reduces storage by 99.8% and makes long-range queries fast by reading pre-aggregated data instead of billions of raw points.

3. Data Model

Time-Series Data Structure

Every metric data point consists of four components: a metric name, a set of key-value tags (labels), a timestamp, and a numeric value. Tags enable multi-dimensional querying — you can filter, group, and aggregate by any combination of tags.

    │  tags        │  {                                   │

    A TIME SERIES is a unique combination of metric_name + tags:
    ────────────────────────────────────────────────────────

    Time Series A:
      metric: "cpu.utilization"
      tags: {host: "web-01", region: "us-east-1"}
      data: [(t1, 45.2), (t2, 47.8), (t3, 52.1), (t4, 48.9), ...]

    Time Series B:
      metric: "cpu.utilization"
      tags: {host: "web-02", region: "us-east-1"}
      data: [(t1, 62.3), (t2, 58.1), (t3, 61.7), (t4, 59.4), ...]

    Same metric name, different tags = different time series.

    Total unique time series = metrics × unique tag combinations
    100K hosts × 1,000 metrics = 100 million unique time series


    METRIC TYPES:
    ────────────────────────────────────────────────────────

    GAUGE:     A value that goes up and down (CPU %, memory %)
               Represents a snapshot at a point in time.
               Query: avg, min, max over time window.

    COUNTER:   A monotonically increasing value (total requests)
               Resets to 0 on process restart.
               Query: rate() to compute per-second change.

    HISTOGRAM: Distribution of values (request latency)
               Pre-computed buckets: [0-10ms, 10-50ms, 50-100ms, ...]
               Query: p50, p95, p99 percentiles.

    SUMMARY:   Similar to histogram but computed client-side.
               Streams pre-calculated quantiles (p50, p99).
               Cannot be aggregated across instances.

Time-Series Database Internals

    TSDB STORAGE ENGINE — COLUMNAR + COMPRESSION
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    WHY REGULAR DATABASES DON'T WORK:
    ────────────────────────────────────────────────────────

    PostgreSQL / MySQL:
    • Row-oriented storage: each row stored contiguously
    • B-tree indexes: optimized for point lookups, not range scans
    • 10M inserts/sec would overwhelm write-ahead log
    • Time-range queries scan entire table (no time partitioning)
    • No built-in compression for time-series patterns
    • Storage: ~200 bytes/point (row overhead, indexes)

    Time-Series DB (e.g., Prometheus TSDB, InfluxDB, TimescaleDB):
    • Columnar storage: timestamps and values stored separately
    • Time-partitioned: data split into time blocks (2-hour chunks)
    • Specialized compression: 16 bytes/point → ~1.4 bytes/point
    • Append-only: no random updates, no write amplification
    • Optimized for time-range scans: sequential reads within block
    • 140x less storage than a general-purpose RDBMS


    GORILLA COMPRESSION (Facebook, 2015):
    ────────────────────────────────────────────────────────

    Key insight: consecutive timestamps and values in a time
    series are highly correlated. Exploit this with delta encoding.

    TIMESTAMP COMPRESSION (Delta-of-Delta):
    ┌─────────────────────────────────────────────────────┐
    │  Raw timestamps:     1000, 1010, 1020, 1030, 1040  │
    │  Deltas:                   10,   10,   10,   10    │
    │  Delta-of-deltas:               0,    0,    0     │
    │                                                     │
    │  Most delta-of-deltas are 0 (regular intervals)!    │
    │  Encode 0 as a single bit: '0'                      │
    │                                                     │
    │  Result: 8-byte timestamp → 1 bit (64x compression) │
    │                                                     │
    │  For irregular intervals, use variable-length encoding│
    │  based on the magnitude of the delta-of-delta.       │
    └─────────────────────────────────────────────────────┘

    VALUE COMPRESSION (XOR Encoding):
    ┌─────────────────────────────────────────────────────┐
    │  Raw values (float64): 45.2, 45.3, 45.1, 45.4      │
    │                                                     │
    │  XOR consecutive values:                            │
    │    45.2 XOR 45.3 = 00000...0010110  (few bits set)  │
    │    45.3 XOR 45.1 = 00000...0011010  (few bits set)  │
    │                                                     │
    │  Key insight: XOR of similar floats has mostly 0s.   │
    │  Encode only the position and length of the          │
    │  non-zero bits (leading zeros + meaningful bits).    │
    │                                                     │
    │  Result: 8-byte float → ~1–3 bytes average          │
    │                                                     │
    │  If values are identical (common for counters at 0): │
    │    XOR = 0 → encode as single bit '0'               │
    └─────────────────────────────────────────────────────┘

    OVERALL COMPRESSION:
    ────────────────────────────────────────────────────────

    Uncompressed: 16 bytes/point (8B timestamp + 8B value)
    Gorilla compressed: ~1.37 bytes/point (Facebook's result)
    Compression ratio: ~12x

    For 10M points/sec:
      Uncompressed: 160 MB/sec
      Compressed:    13 MB/sec  (very manageable!)

Storage Layout

    TSDB BLOCK LAYOUT (Prometheus-style)
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    Data is organized into time-partitioned BLOCKS:

    data/
    ├── block-01HQRS.../          (2-hour block: 00:00–02:00)
    │   ├── meta.json             (time range, stats, version)
    │   ├── index                 (inverted index: label → series IDs)
    │   ├── chunks/
    │   │   ├── 000001            (compressed time-series chunks)
    │   │   └── 000002
    │   └── tombstones            (deletion markers)
    │
    ├── block-01HQRT.../          (2-hour block: 02:00–04:00)
    │   ├── meta.json
    │   ├── index
    │   ├── chunks/
    │   └── tombstones
    │
    ├── wal/                      (Write-Ahead Log for in-flight data)
    │   ├── 00000001
    │   ├── 00000002
    │   └── checkpoint.00000001
    │
    └── head                      (in-memory block for current data)


    WRITE PATH:
    ────────────────────────────────────────────────────────

    1. Data point arrives
    2. Written to WAL (durability)
    3. Appended to in-memory HEAD block
    4. HEAD block compressed and flushed to disk every 2 hours
    5. Older blocks compacted (merged) for query efficiency
    6. Blocks beyond retention period deleted


    INVERTED INDEX (for tag-based lookups):
    ────────────────────────────────────────────────────────

    Given query: cpu.utilization{region="us-east-1", service="api"}

    Index structure:
      "region=us-east-1"  →  [series_1, series_5, series_42, ...]
      "service=api"       →  [series_1, series_7, series_42, ...]

    Intersection: [series_1, series_42, ...]

    Then fetch compressed chunks for those series IDs
    within the requested time range.
Key Insight: The combination of time-partitioned blocks, Gorilla compression, and inverted indexes is what makes a TSDB handle 10M writes/sec and sub-second queries. Time partitioning means queries only touch relevant blocks (a 1-hour query reads 1 block, not the entire dataset). Gorilla compression reduces storage by 12x. The inverted index enables fast tag-based filtering without scanning all series. This is fundamentally different from how a relational database would approach the problem.

Key Components

Metrics Agent

Lightweight daemon on every host.
Responsibilities:
• Collect system metrics (CPU, mem, disk,
  network) from /proc, /sys, OS APIs
• Scrape application metrics from
  /metrics HTTP endpoints
• Buffer locally (survive brief network
  outages)
• Batch and compress before sending
• Add host-level tags (hostname, region,
  availability zone)

Examples: Datadog Agent, Telegraf,
  Prometheus Node Exporter,
  collectd, StatsD

Ingestion & Storage

Kafka absorbs 10M points/sec burst.
Stream processors (Flink/Spark):
• Validate data (reject malformed points)
• Normalize metric names and tags
• Compute real-time aggregations
• Route to appropriate TSDB shard

TSDB cluster (20+ nodes):
• Sharded by metric_name + tags hash
• Each node handles a subset of series
• Gorilla compression (12x)
• Time-partitioned blocks (2-hour chunks)
• Automatic downsampling jobs
• Replication factor 2–3 for durability
Interview Tip: Emphasize why Kafka sits between agents and the TSDB. Without Kafka, a TSDB outage or slowdown would cause agents to buffer indefinitely and eventually drop data. Kafka provides: (1) decoupling — agents and TSDB scale independently, (2) buffering — absorbs traffic spikes without backpressure, (3) durability — data is safe in Kafka even if TSDB is temporarily down, (4) fan-out — multiple consumers (TSDB writer, alerting pipeline, anomaly detection) can read the same data independently.

5. Deep Dive

5a. Data Collection — Pull vs. Push

There are two fundamental approaches to collecting metrics: pull-based (the monitoring server scrapes targets) and push-based (agents push metrics to the server). Each has distinct trade-offs.

Pull-Based (Prometheus Model)

HOW IT WORKS:
The monitoring server periodically scrapes
HTTP endpoints on each target.

  Prometheus ──HTTP GET /metrics──▶ Target
  Prometheus ◀── metric data ──── Target

Each target exposes a /metrics endpoint:
  # HELP http_requests_total Total requests
  # TYPE http_requests_total counter
  http_requests_total{method="GET"} 1234
  http_requests_total{method="POST"} 567

  # TYPE cpu_usage gauge
  cpu_usage{core="0"} 45.2
  cpu_usage{core="1"} 62.8

ADVANTAGES:
• Server controls scrape frequency
• Easy to detect if a target is down
  (scrape fails = target unhealthy)
• No agent needed (app exposes /metrics)
• Simple debugging: curl the endpoint
• No firewall issues (server initiates)

DISADVANTAGES:
• Doesn't scale well beyond ~100K targets
  (server must track all targets)
• Requires service discovery (which
  targets to scrape?)
• Short-lived jobs may be missed between
  scrape intervals
• Targets must be network-reachable from
  the monitoring server

Push-Based (Datadog/StatsD Model)

HOW IT WORKS:
Agents on each host push metrics to a
central collection service.

  Agent ──push metrics──▶ Collection API
                          (load balanced)

Agent batches metrics locally, compresses,
and sends via HTTP/gRPC every 10 seconds:
  POST /api/v1/metrics
  {
    "series": [
      {
        "metric": "cpu.utilization",
        "tags": ["host:web-01", "region:us-east"],
        "points": [[1702483200, 45.2],
                    [1702483210, 47.8]]
      }
    ]
  }

ADVANTAGES:
• Scales to millions of hosts (stateless
  collection API behind load balancer)
• Works behind firewalls/NATs (agent
  initiates outbound connection)
• Short-lived jobs can push final metrics
  before exiting
• Agent can buffer during network outages
• Better for cloud/ephemeral environments

DISADVANTAGES:
• Can't easily detect if a host is down
  (absence of data vs. network issue)
• Risk of overwhelming the collection
  service (need rate limiting)
• Requires agent installation on every host
• Agent adds resource overhead on hosts
Aspect Pull (Prometheus) Push (Datadog/StatsD)
Scale ~100K targets per server (limited by scrape capacity) Millions of hosts (stateless collection tier)
Health detection Built-in (failed scrape = target down) Requires separate liveness tracking
Firewall/NAT Server must reach targets (problematic behind NAT) Agent initiates outbound (works behind NAT)
Short-lived jobs May miss data between scrapes (use Pushgateway) Agent pushes final metrics before exit
Agent required No (app exposes /metrics endpoint) Yes (agent daemon on every host)
Used by Prometheus, Thanos, Cortex, Victoria Metrics Datadog, Graphite, StatsD, InfluxDB, New Relic
Hybrid approach: In practice, large-scale systems use both. Prometheus pulls from service endpoints within a cluster, while a push-based agent handles infrastructure metrics and cross-network collection. Datadog’s agent, for example, both pushes its own collected metrics and can scrape Prometheus-format endpoints locally, then pushes everything to Datadog’s backend. For this design at 100K servers, a push-based architecture is more appropriate because it scales horizontally with a stateless collection tier and works across network boundaries.

5b. Time-Series Database — Why Regular DBs Don’t Work

A time-series database is purpose-built for the unique access patterns of metrics data: extremely high write throughput, append-only workload, time-range scans, and mathematical aggregation. General-purpose databases fail at this scale.

Characteristic General-Purpose DB (PostgreSQL) Time-Series DB (Prometheus TSDB)
Write pattern Random writes (B-tree updates, WAL) Append-only sequential writes (LSM-tree / log-structured)
Write throughput ~50K inserts/sec (single node) ~2M+ inserts/sec (single node, compressed)
Storage per point ~200 bytes (row overhead, indexes, MVCC) ~1.4 bytes (Gorilla compression)
Compression Generic (TOAST, LZ4 on pages) Domain-specific (delta-of-delta, XOR float encoding)
Time-range queries B-tree index scan (random I/O) Sequential scan of time-partitioned blocks
Retention management DELETE + VACUUM (expensive, locks) Drop entire time block (instant, no fragmentation)
Downsampling Manual (custom jobs, materialized views) Built-in (automatic rollup to lower resolutions)

5c. Downsampling — The 99% Storage Reduction

Downsampling is the process of reducing data resolution over time. Raw 10-second data is aggregated into 1-minute summaries, which are further aggregated into 1-hour summaries. This is the single most impactful optimization in a metrics system.

Why store min/max/sum/count in aggregates, not just avg? If you only store the average, you lose information. You cannot compute the average of averages correctly (it ignores different sample counts). By storing sum and count, you can compute the correct weighted average over any time range. By storing min and max, you preserve extreme values that would be lost in averaging. For percentiles (p95, p99), you need to store histogram bucket counts or use approximate data structures like t-digest or DDSketch.

5d. Query Engine — PromQL-Like Query Language

The query engine translates human-readable queries into efficient scans over the TSDB. It supports time-range selection, mathematical operations, aggregation functions, and GROUP BY on tags.

    QUERY LANGUAGE EXAMPLES (PromQL-style)
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    BASIC QUERIES:
    ────────────────────────────────────────────────────────

    # Current CPU utilization for all hosts
    cpu_utilization

    # CPU utilization for a specific host
    cpu_utilization{host="web-01"}

    # CPU utilization in us-east-1 region
    cpu_utilization{region="us-east-1"}

    # Request rate (per-second) over last 5 minutes
    rate(http_requests_total[5m])

    # Error rate as percentage
    rate(http_requests_total{status="5xx"}[5m])
    /
    rate(http_requests_total[5m])
    * 100


    AGGREGATION QUERIES:
    ────────────────────────────────────────────────────────

    # Average CPU across all hosts in a region
    avg by (region) (cpu_utilization)

    # 99th percentile request latency by service
    histogram_quantile(0.99,
      rate(http_request_duration_bucket[5m])
    ) by (service)

    # Total requests per second by endpoint
    sum by (endpoint) (
      rate(http_requests_total[5m])
    )

    # Top 10 hosts by memory usage
    topk(10, memory_usage_bytes)


    QUERY EXECUTION PLAN:
    ────────────────────────────────────────────────────────

    Query: avg by (region) (cpu_utilization{service="api"})
    Time range: last 1 hour

    1. RESOLVE: Find all time series matching
       metric="cpu_utilization" AND tag service="api"
       → Use inverted index: 500 matching series

    2. FETCH: For each series, read compressed data
       from the appropriate time block (last 1 hour)
       → Read from in-memory HEAD block (recent data)

    3. DECOMPRESS: Apply Gorilla decompression to get
       raw (timestamp, value) pairs

    4. AGGREGATE: Group by "region" tag, compute avg
       → us-east-1: avg of 200 series = 52.3%
       → us-west-2: avg of 150 series = 48.7%
       → eu-west-1: avg of 150 series = 55.1%

    5. RETURN: Time series result for each region

Resolution matching is a subtle but important optimization. A dashboard panel that is 1,000 pixels wide can display at most 1,000 data points. If the time range is 24 hours, there is no visual benefit to fetching 8,640 raw data points (one per 10 seconds) — 1,440 one-minute aggregates look identical on screen but require 6x less data transfer and TSDB I/O. The query engine automatically selects the coarsest resolution that still provides more points than pixels, ensuring fast rendering without visible quality loss.

6. Trade-offs

Decision Option A Option B Recommendation
Pull vs. Push Collection Pull (Prometheus): Server scrapes targets. Built-in health detection (failed scrape = target down). No agent required. But limited to ~100K targets per server and requires targets to be network-reachable. Push (Datadog/StatsD): Agents push to collection API. Scales to millions of hosts via stateless load-balanced API tier. Works behind firewalls/NATs. But requires agent on every host and can’t easily detect silent host failures. Use push-based for large-scale infrastructure (>10K hosts). The stateless collection tier scales horizontally, and agents can buffer during network outages. Use pull for smaller deployments or within a single Kubernetes cluster where Prometheus excels.
TSDB vs. Regular Database Purpose-built TSDB: Gorilla compression (12x), time-partitioned blocks, built-in downsampling, optimized for append-only writes and time-range scans. But specialized — limited ecosystem, operational learning curve. General-purpose DB (PostgreSQL + TimescaleDB): Familiar SQL interface, rich ecosystem, ACID transactions. But 140x more storage per point, lower write throughput, no built-in compression for time-series patterns. Use a purpose-built TSDB at this scale (10M points/sec). The 140x storage difference alone makes a general-purpose DB impractical (57 TB vs. 8 PB). TimescaleDB is a reasonable middle ground for smaller deployments (<1M points/sec) where SQL familiarity matters.
Retention vs. Storage Cost Long retention, high resolution: Keep raw 10-second data for months. Enables detailed historical analysis. But storage grows linearly — 50 TB per week of raw data at this scale. Aggressive downsampling: Raw data for 7 days, 1-min for 30 days, 1-hr for 1 year. 99.8% storage reduction. But loses fine-grained detail for historical queries — can’t see 10-second spikes from 2 months ago. Use aggressive downsampling as the default. Most historical queries (“what was CPU last month?”) don’t need 10-second resolution. For critical metrics where detail matters, allow per-metric retention overrides (e.g., keep raw latency data for 30 days for SLO tracking).
Alerting Accuracy vs. Noise Sensitive alerts (low thresholds, short “for” duration): Catches issues quickly. But generates many false positives from transient spikes, causing alert fatigue. On-call engineers start ignoring alerts. Conservative alerts (higher thresholds, longer “for” duration): Fewer false positives, less noise. But may miss real issues or detect them late. A 5-minute “for” duration means 5 minutes of impact before the alert fires. Start conservative and tune down. Alert fatigue is more dangerous than slightly delayed detection — if engineers ignore alerts, the system is useless. Use the “for” duration (e.g., 5 minutes) to filter transient spikes. Combine with anomaly detection for metrics where static thresholds are insufficient (e.g., request rate varies by time of day).
Interview Tip: When discussing trade-offs, connect them to real-world consequences. For example: “Alert fatigue is one of the biggest operational risks. If we set CPU threshold at 80% with a 1-minute ‘for’ duration, we might get 50 alerts per day from normal traffic spikes. Engineers start ignoring alerts, and when a real incident happens, the alert is buried in noise. This is why the ‘for’ duration, grouping, and inhibition in the Alert Manager are not nice-to-haves — they’re essential for the system to be useful.”
