Design Nearby Friends

Design a real-time system that shows users which of their friends are nearby (within 5 miles) — updating locations every 30 seconds, computing proximity efficiently across millions of concurrent users, managing WebSocket connections at scale, and respecting user privacy through opt-in controls.

Medium Social & Feed Asked at: Meta, Uber, Lyft

1. Requirements

Functional Requirements

  • See nearby friends in real-time — Users should be able to see a list of friends who are currently within a 5-mile (8 km) radius. The list updates in real-time as friends move closer or farther away. Only friends who have opted in to location sharing are visible.
  • Update location every 30 seconds — The mobile client sends the user’s GPS coordinates to the server every 30 seconds. The server uses this to recompute which friends are nearby and pushes updates to affected users.
  • Show distance and last update time — For each nearby friend, display the approximate distance (e.g., “0.5 miles away”) and the time of their last location update (e.g., “2 minutes ago”). Distance does not need to be precise — rounding to the nearest 0.1 mile is sufficient.
  • Respect privacy (opt-in) — Location sharing is strictly opt-in. Users must explicitly enable the “Nearby Friends” feature. They can disable it at any time, which immediately stops sharing their location and removes them from all friends’ nearby lists. Users can also choose to share location only with specific friend lists.

Non-Functional Requirements

  • Scale: 100 million DAU, with 10% concurrent at peak = 10 million concurrent users actively sharing their location. The system must handle this load without degradation.
  • Low latency: When a user’s location changes, their nearby friends should see the update within 500 ms. This requires a push-based architecture (not polling) and efficient proximity computation.
  • Location update frequency: Each user sends a location update every 30 seconds. At 10M concurrent users, this means 333K location updates per second that must be ingested, stored, and propagated.
  • Availability: The system should be highly available. A brief delay in location updates is acceptable (soft real-time), but the system should not go down entirely. Eventual consistency is acceptable — a friend’s location being 30–60 seconds stale is fine.
Interview Tip: Start by clarifying the problem scope: “Are we building this for a social network like Facebook where users have a friends list, or for a ride-sharing app like Uber where we need to find nearby strangers (drivers)?” The friends-based model is fundamentally different — we only need to check proximity against a user’s friend list (hundreds of people), not against all users (millions). This dramatically simplifies the problem. Also ask: “What is the radius? Is 5 miles fixed or configurable?” and “Do we need to show friends on a map, or just a list with distances?”

Throughput Calculation

Location updates per second:
  10M concurrent users / 30 sec update interval
  = 333,333 updates/sec
  ≈ 333K updates/sec

Data ingestion rate:
  333K updates/sec × 32 bytes/update
  = 10.67 MB/sec
  ≈ 10 MB/sec (very manageable)

Nearby friend checks per update:
  Each location update triggers proximity checks
  against the user's online friends.

  333K updates/sec × 40 online friends/user
  = 13.3M proximity checks/sec

  Each check: compute distance between two lat/lng pairs
  (Haversine formula or simplified Euclidean approximation)
  = ~1 microsecond per check

  Total CPU for proximity: 13.3M × 1 μs = 13.3 seconds of CPU/sec
  = ~14 CPU cores dedicated to distance computation

WebSocket Connection Estimate

WebSocket connections:
  10M concurrent users = 10M persistent WebSocket connections

  Each WebSocket connection uses ~10 KB of memory
  (TCP buffers, connection state, user metadata)

  Total memory: 10M × 10 KB = 100 GB

  Single server capacity: ~100K WebSocket connections
  (limited by file descriptors, memory, and CPU)

  WebSocket servers needed: 10M / 100K = 100 servers

Push messages per second:
  When a user's location updates, we push to nearby friends.
  Assume 5% of friends are actually nearby (within 5 miles):
  333K updates/sec × 40 friends × 5% nearby = 666K pushes/sec

  Each push message: ~50 bytes (friend_id, distance, timestamp)
  Push bandwidth: 666K × 50B = 33 MB/sec outbound
Key Insight: The numbers reveal that this is primarily a fan-out problem, not a storage problem. The data volume is tiny (10 MB/sec of location updates), but each update fans out to 40 friends for proximity checks, generating 13.3M distance computations per second. The critical challenge is efficiently determining which friends are nearby without doing a brute-force check against all 10M users. Since we only check against a user’s friend list (not all users), the problem is tractable — 40 distance computations per update is trivial. The real engineering challenge is the WebSocket infrastructure: maintaining 10M persistent connections and routing 666K push messages/sec to the correct servers.

3. High-Level Design

The system has two main flows: (1) ingesting location updates from users and caching them, and (2) computing which friends are nearby and pushing updates to them in real-time. We use WebSocket connections for bidirectional communication and Redis for both location caching and pub/sub message routing.

Two Architectural Approaches

There are two main ways to determine which friends are nearby. Each has different trade-offs for our scale.

Approach A: Pub/Sub per User

Each user has a dedicated pub/sub channel.
When User A opts in, their WebSocket server
subscribes to the channels of all of A's
online friends.

When Friend B sends a location update:
1. Update B's location in Redis cache
2. Publish B's new location to B's channel
3. A's WebSocket server receives the update
   (because it subscribed to B's channel)
4. Compute distance(A, B)
5. If distance < 5 miles, push to A's client

Pros:
• Simple mental model
• No polling — pure event-driven
• Only computes distance when a friend
  actually moves

Cons:
• Each user subscribes to ~40 channels
• 10M users × 40 channels = 400M subscriptions
• Redis Pub/Sub memory overhead is significant
• Channel management when friends come
  online/offline adds complexity

Approach B: Pub/Sub per Geohash

Divide the world into geohash grid cells.
Each cell has a pub/sub channel.

When User A opts in, their WebSocket server
subscribes to A's geohash channel + 8
neighboring channels (9 total).

When Friend B sends a location update:
1. Update B's location in Redis cache
2. Publish B's update to B's geohash channel
3. All users in the same/neighboring cells
   receive the update
4. Filter: is B in my friend list?
5. If yes, compute distance(A, B)
6. If distance < 5 miles, push to A's client

Pros:
• Far fewer channels (millions of cells vs
  billions of user pairs)
• Natural spatial grouping
• Efficient for dense areas

Cons:
• Receives updates from non-friends (noise)
• Must filter by friend list on each update
• Channel switching when user moves to a
  new geohash cell
Recommended: Approach A (Pub/Sub per User). For a friends-based system, Approach A is simpler and more efficient. The key insight is that we only care about a user’s friends (40 online friends on average), not all nearby users. With Approach B (geohash channels), a user in a dense area like Manhattan would receive thousands of location updates from strangers, only to discard 99% of them after the friend-list filter. Approach A sends zero wasted messages — every update received is from a friend. The 400M subscription count is manageable with a Redis cluster. If you were building “find nearby strangers” (like Uber finding drivers), Approach B would be the right choice.

4. Deep Dive

4a. Geohash — Spatial Indexing for Location Data

A geohash encodes a latitude/longitude pair into a short alphanumeric string. Points that are geographically close share a common prefix. This property makes geohashes invaluable for spatial queries, even though we use Pub/Sub per user for the primary flow — geohashes are still useful for the initial “bootstrap” query (finding which friends are nearby when a user first opens the app).

    HOW GEOHASH WORKS
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    Geohash recursively subdivides the Earth's surface into
    a grid of cells. Each additional character in the geohash
    string narrows the cell to a smaller area.

    ENCODING EXAMPLE: (37.7749, -122.4194) → "9q8yyk"
    ────────────────────────────────────────────────────────

    Step 1: Divide world into 32 cells (base-32 encoding)
            Longitude range [-180, 180] → binary bits
            Latitude range [-90, 90] → binary bits
            Interleave bits: lon, lat, lon, lat, ...

    Step 2: Convert binary to base-32 character
            Each 5 bits → one character (0-9, a-z minus a,i,l,o)

    Step 3: More characters = higher precision

    ┌──────────────────────────────────────────────────────┐
    │  GEOHASH PRECISION LEVELS                            │
    │                                                      │
    │  Length │ Cell Width  │ Cell Height │ Area            │
    │  ──────┼─────────────┼─────────────┼──────────────── │
    │    1   │ 5,000 km    │ 5,000 km    │ ~25,000,000 km²│
    │    2   │ 1,250 km    │ 625 km      │ ~781,000 km²   │
    │    3   │ 156 km      │ 156 km      │ ~24,000 km²    │
    │    4   │ 39.1 km     │ 19.5 km     │ ~763 km²       │
    │    5   │ 4.9 km      │ 4.9 km      │ ~24 km²        │
    │    6   │ 1.2 km      │ 0.61 km     │ ~0.73 km²      │
    │    7   │ 153 m       │ 153 m       │ ~0.023 km²     │
    │    8   │ 38.2 m      │ 19.1 m      │ ~730 m²        │
    │                                                      │
    │  For "nearby friends within 5 miles (8 km)":         │
    │  Use geohash length 4 (39 km cells) or 5 (4.9 km)   │
    │                                                      │
    │  Length 4: cells are larger than our radius           │
    │    → fewer cells to check, but more false positives │
    │  Length 5: cells closely match our 8 km radius        │
    │    → good balance of precision and coverage         │
    └──────────────────────────────────────────────────────┘


    THE NEIGHBORING GEOHASH PROBLEM
    ────────────────────────────────────────────────────────

    A user near the EDGE of a geohash cell might have
    friends in the ADJACENT cell who are within 5 miles
    but have a completely different geohash prefix.

    ┌───────────┬───────────┐
    │           │           │
    │  9q8yy    │  9q8yz    │
    │           │           │
    │       A ● │ ● B       │  A and B are 0.5 miles apart
    │           │           │  but in different geohash cells!
    │           │           │
    └───────────┴───────────┘

    SOLUTION: Always check the 8 neighboring cells too.

    ┌───────────┬───────────┬───────────┐
    │  NW       │  N        │  NE       │
    │  9q8yw    │  9q8yx    │  9q8yz    │
    ├───────────┼───────────┼───────────┤
    │  W        │  CENTER   │  E        │
    │  9q8yt    │  9q8yy    │  9q8yz    │
    ├───────────┼───────────┼───────────┤
    │  SW       │  S        │  SE       │
    │  9q8yq    │  9q8yr    │  9q8ys    │
    └───────────┴───────────┴───────────┘

    For any user in cell "9q8yy", check all 9 cells
    (center + 8 neighbors) to find nearby friends.
    Then compute exact distance to filter out false positives.
Key Insight: Geohash is a coarse filter, not a precise distance calculator. It quickly narrows down candidates to a small geographic area, but you must always compute the exact Haversine distance to confirm whether a candidate is truly within the 5-mile radius. The neighboring cell problem means you must always check 9 cells (center + 8 neighbors), not just the user’s own cell.

4b. QuadTree vs. Geohash — Alternative Spatial Index

A QuadTree is another spatial index that recursively subdivides a 2D space into four quadrants. Each node either contains data points or has four children. It adapts to data density — dense areas get more subdivisions, sparse areas stay coarse.

Geohash

Structure:
  Fixed grid of cells at each precision level.
  All cells at the same level have the same size.

Encoding:
  Lat/lng → base-32 string (e.g., "9q8yyk")
  Prefix sharing = spatial proximity.

Strengths:
  • Simple string-based encoding
  • Easy to store in Redis/databases
    (string prefix queries)
  • Fixed cell sizes = predictable behavior
  • Easy to compute neighboring cells
  • Works well with key-value stores

Weaknesses:
  • Fixed grid doesn't adapt to density
  • Dense areas (NYC) and sparse areas
    (Sahara) get same-sized cells
  • Edge/boundary problem requires
    checking 9 cells instead of 1

Best for:
  • Database-backed spatial queries
  • Redis/cache-based proximity
  • Pub/Sub channel naming

QuadTree

Structure:
  Recursive tree. Each node splits into 4
  quadrants when it exceeds a threshold
  (e.g., max 100 points per leaf).

Encoding:
  Tree traversal from root to leaf.
  No simple string representation.

Strengths:
  • Adapts to data density automatically
  • Dense areas get fine granularity
  • Sparse areas stay coarse (efficient)
  • Natural for range queries
  • No edge/boundary problem

Weaknesses:
  • In-memory tree structure (harder to
    distribute across servers)
  • More complex to implement
  • Harder to persist/serialize
  • Rebalancing needed as data changes
  • Not natively supported by Redis/DBs

Best for:
  • In-memory spatial indexing
  • Finding nearest N points
  • Density-adaptive applications
  • Game engines, collision detection
Interview Tip: For “Nearby Friends,” geohash is the better choice because it integrates naturally with Redis (string keys, prefix queries, pub/sub channel names). QuadTree would be better for a system like “find the nearest 10 drivers” where density adaptation matters. In an interview, mention both and explain why you chose geohash: “Geohash gives us a simple string encoding that works natively with Redis for both caching and pub/sub. The fixed grid size is fine for our use case because our radius is fixed at 5 miles.”

4e. Channel Management — Handling Online/Offline and Movement

The subscription graph is dynamic: friends come online and go offline, and users move between geohash cells. The WebSocket servers must manage these transitions efficiently to avoid stale subscriptions and missed updates.

    CHANNEL LIFECYCLE MANAGEMENT
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    EVENT 1: USER COMES ONLINE (opens app with feature on)
    ────────────────────────────────────────────────────────

    1. Client connects via WebSocket
    2. WS Server fetches friend list from Friend Service
    3. WS Server checks which friends are online:
       - Check Redis for existence of user:{friend_id}:location
       - If key exists with valid TTL → friend is online
    4. Subscribe to online friends' channels:
       - SUBSCRIBE user:friend1:location
       - SUBSCRIBE user:friend2:location
       - ...
    5. Fetch current locations of online friends from Redis
    6. Compute initial nearby list and push to client
    7. Publish own presence to a "user_online" channel
       so friends' WS servers can subscribe to this user


    EVENT 2: FRIEND COMES ONLINE
    ────────────────────────────────────────────────────────

    When Friend F comes online:
    1. F's WS server publishes to "user_online" channel:
       {user_id: F, status: "online"}
    2. All WS servers with users who are friends of F
       receive this notification
    3. Those WS servers subscribe to user:F:location
    4. Fetch F's current location and check proximity


    EVENT 3: USER GOES OFFLINE (app backgrounded / closed)
    ────────────────────────────────────────────────────────

    1. WebSocket connection closes (detected by WS server)
    2. WS Server unsubscribes from all friend channels:
       - UNSUBSCRIBE user:friend1:location
       - UNSUBSCRIBE user:friend2:location
       - ...
    3. Delete user's location from Redis cache:
       - DEL user:{user_id}:location
       (or let TTL expire naturally in 60 seconds)
    4. Publish offline status:
       {user_id: A, status: "offline"}
    5. Friends' WS servers unsubscribe from A's channel
    6. Friends' clients receive "friend_left" event


    EVENT 4: USER MOVES TO NEW GEOHASH CELL
    ────────────────────────────────────────────────────────
    (Only relevant if using geohash-based Pub/Sub — Approach B)

    1. User's new location has a different geohash prefix
       Old: "9q8yy" → New: "9q8yz"
    2. WS Server detects the geohash change
    3. Unsubscribe from old cell + neighbors (9 channels)
    4. Subscribe to new cell + neighbors (9 channels)
    5. Some channels overlap (only 3-6 actually change)

    Optimization: compute the symmetric difference between
    old and new neighbor sets. Only unsubscribe/subscribe
    the channels that actually changed.

    ┌───────────┬───────────┬───────────┐
    │  OLD      │  OLD      │  OLD      │
    │  unsub    │  unsub    │  unsub    │
    ├───────────┼───────────┼───────────┤
    │  OLD      │  OLD→NEW  │  NEW      │
    │  unsub    │  (keep)   │  sub      │
    ├───────────┼───────────┼───────────┤
    │           │  NEW      │  NEW      │
    │           │  sub      │  sub      │
    └───────────┴───────────┴───────────┘

    In this example, user moved from center to the east cell.
    3 old channels are unsubscribed, 3 new channels are
    subscribed, and 6 channels overlap (kept).

4f. Scaling WebSocket Servers — Connection Registry

With 10M concurrent WebSocket connections spread across 100 servers, we need a way to know which user is connected to which server. This is essential for routing push messages and handling server failures.

    WEBSOCKET SERVER SCALING
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    CONNECTION REGISTRY
    ────────────────────────────────────────────────────────

    A distributed hash map that tracks:
      user_id → {ws_server_id, connection_id, connected_at}

    Stored in Redis (separate from location cache):
      HSET connections user:A "ws-server-7"
      HSET connections user:B "ws-server-3"
      HSET connections user:C "ws-server-7"

    Used for:
    • Routing: when we need to push to User A, look up
      which WS server holds A's connection
    • Presence: check if a user is online (key exists?)
    • Load balancing: count connections per server


    WHY PUB/SUB ELIMINATES MOST ROUTING NEEDS
    ────────────────────────────────────────────────────────

    With Redis Pub/Sub, we don't need to look up which
    server a user is on for location updates. The Pub/Sub
    system handles routing automatically:

    ┌──────────────────────────────────────────────────────┐
    │                                                      │
    │  WITHOUT Pub/Sub (direct routing):                   │
    │  1. User B updates location                          │
    │  2. Look up all B's friends: [A, C, D, ...]          │
    │  3. For each friend, look up their WS server         │
    │  4. Send message to each WS server                   │
    │  → N lookups + N network calls per update           │
    │  → 333K updates/sec × 40 friends = 13.3M lookups/sec│
    │  → Extremely expensive!                              │
    │                                                      │
    │  WITH Pub/Sub (channel routing):                     │
    │  1. User B updates location                          │
    │  2. PUBLISH to user:B:location channel               │
    │  3. Redis delivers to all subscribed WS servers       │
    │  → 1 publish per update (Redis handles fan-out)     │
    │  → 333K publishes/sec                               │
    │  → Much more efficient!                              │
    │                                                      │
    └──────────────────────────────────────────────────────┘


    SERVER FAILURE HANDLING
    ────────────────────────────────────────────────────────

    When a WS server crashes:
    1. All WebSocket connections on that server drop
    2. Clients detect disconnection and reconnect
       (to a different server via load balancer)
    3. New server re-establishes subscriptions for
       each reconnected user
    4. Connection registry is updated automatically
    5. Brief gap in location updates (~5-10 seconds)
       while clients reconnect

    Heartbeat mechanism:
    • WS servers send heartbeats to Redis every 10 seconds
    • If a server misses 3 heartbeats, it's considered dead
    • A cleanup worker removes stale connection entries
      and publishes "offline" events for affected users

4g. Privacy — Opt-In, Precision Reduction, and Friend Filtering

Location data is extremely sensitive. The system must be designed with privacy as a first-class concern, not an afterthought. Every component must respect the user’s privacy settings.

    PRIVACY CONTROLS
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    LAYER 1: OPT-IN / OPT-OUT
    ────────────────────────────────────────────────────────

    • Feature is OFF by default. User must explicitly enable.
    • When disabled:
      - Client stops sending location updates
      - Server deletes cached location immediately
      - Server unsubscribes from all friend channels
      - Server publishes "offline" event to friends
      - User disappears from all friends' nearby lists
    • Toggle is instant — no delay in removing location data.


    LAYER 2: FRIEND-LIST FILTERING
    ────────────────────────────────────────────────────────

    Users can choose WHO sees their location:

    • If User A shares only with "Close Friends",

    LAYER 4: DATA RETENTION
    ────────────────────────────────────────────────────────

    • Location cache TTL: 60 seconds (auto-expires)
    • Location history: retained for 30 days, then deleted
    • User can request full deletion of location history
      (GDPR/CCPA compliance)
    • Location data is encrypted at rest and in transit
    • Access logs track who accessed whose location data
Privacy is a system design requirement, not a feature. In an interview, proactively discuss privacy before the interviewer asks. Say: “Location data is extremely sensitive. I want to highlight three privacy measures: (1) the feature is strictly opt-in with instant opt-out that deletes all cached location data, (2) users control which friends can see their location via friend-list filtering, and (3) we never share exact coordinates with friends — we compute distance server-side and only send distance buckets to the client. The server stores precise coordinates temporarily (60s TTL) for distance computation, but friends never see raw lat/lng.”

5. Trade-offs

Decision Option A Option B Recommendation
Geohash vs. QuadTree Geohash: Simple string encoding. Works natively with Redis keys and Pub/Sub channel names. Fixed grid size. Easy to compute neighbors. Well-suited for database/cache-backed systems. QuadTree: Adaptive to data density. Better for variable-density scenarios (cities vs. rural). In-memory tree structure. Harder to distribute. More complex implementation. Use Geohash for this system. Our radius is fixed (5 miles), so density adaptation is unnecessary. Geohash integrates naturally with Redis for caching and channel naming. QuadTree is better for “find nearest N drivers” where density varies wildly.
Pub/Sub per user vs. per geohash Per-user channels: Each user has a dedicated channel. Friends subscribe to each other’s channels. Zero wasted messages — every received update is from a friend. 400M total subscriptions at scale. Per-geohash channels: Each geohash cell has a channel. Users subscribe to their cell + 8 neighbors. Receives updates from ALL users in the area, not just friends. Must filter by friend list. High noise in dense areas. Use per-user channels for a friends-based system. The friend list is small (40 online friends), so 40 subscriptions per user is efficient. Per-geohash channels would flood users in Manhattan with thousands of irrelevant updates from strangers. Per-geohash is better for “find nearby strangers” use cases.
Pub/Sub vs. polling Pub/Sub (push-based): Updates are pushed to friends instantly when a location changes. Low latency (~100 ms). Efficient — no wasted requests. Requires persistent WebSocket connections and subscription management. Polling: Each client periodically requests friends’ locations (e.g., every 10 seconds). Simpler architecture — stateless HTTP servers. Higher latency (up to 10 seconds stale). Wasteful — most polls return no changes. 10M users × 6 polls/min = 1M requests/sec. Use Pub/Sub. The 500 ms latency requirement rules out polling. Pub/Sub delivers updates in ~100 ms and only sends data when something changes. The WebSocket infrastructure adds complexity but is essential for real-time UX. Polling would generate 1M wasted requests/sec.
Update frequency: 30s vs. 10s vs. 60s 10 seconds: More responsive. 1M updates/sec (3x load). Higher battery drain on mobile. More precise tracking. Better UX for fast-moving users. 60 seconds: Lower load (167K updates/sec). Better battery life. Acceptable for walking-speed movement. Stale data for driving-speed users. Use 30 seconds as the default with adaptive frequency. If the user is stationary (GPS delta < 50m), reduce to 60s. If moving fast (driving), increase to 10s. This balances battery life, server load, and UX. The client should skip updates when stationary to save bandwidth.
Precision vs. privacy Exact coordinates: Share precise lat/lng with friends. Enables accurate distance display and map pinpointing. Privacy risk: friends know your exact location (home address, workplace). Distance buckets only: Compute distance server-side, share only buckets (“nearby”, “a few miles away”). Friends cannot pinpoint exact location. Less useful for “meet up” scenarios. Better privacy. Use distance buckets by default with an option to share precise location with specific friends. The server computes exact distance using raw coordinates (stored with 60s TTL), but only sends distance buckets to clients. Users who want to share exact location for meetups can enable “precise sharing” for individual friends.
Interview Tip: When discussing trade-offs, tie them back to the requirements: “We chose per-user Pub/Sub over per-geohash because our system is friends-based — we only care about 40 online friends, not millions of strangers. Per-geohash would be the right choice for Uber (finding nearby drivers), but for a social network, per-user channels eliminate all wasted messages. We chose push over polling because our 500 ms latency requirement makes polling impractical — even 5-second polling would miss the target half the time. We chose 30-second updates with adaptive frequency because it balances battery life (critical for mobile) with freshness.”
