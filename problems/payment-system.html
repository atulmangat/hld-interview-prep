Design a Payment System

Design a scalable and reliable payment processing system — supporting multiple payment methods (credit card, debit card, UPI, digital wallets), refund processing, real-time payment status tracking, transaction history, multi-currency support, and integration with external payment gateways like Stripe and PayPal. The system must guarantee exactly-once payment processing to prevent double charges.

Hard Platform Asked at: Stripe, PayPal, Square

1. Requirements

Functional Requirements

  • Accept payments via multiple methods — Support credit cards, debit cards, UPI, and digital wallets (Apple Pay, Google Pay). The system must route each payment to the appropriate payment gateway based on method and region.
  • Process refunds — Support full and partial refunds. Refunds must be idempotent and traceable back to the original payment. Refund status must be tracked independently from the original payment.
  • Payment status tracking — Provide real-time status updates for every payment: created → processing → authorized → captured → settled (or failed/cancelled). Clients can poll or receive webhooks for status changes.
  • Transaction history — Maintain a complete, immutable history of all payment events for every transaction. Support querying by user, merchant, date range, status, and payment method.
  • Multi-currency support — Accept payments in 100+ currencies. Perform currency conversion at the time of payment using real-time exchange rates. Display amounts in both the payer’s and merchant’s currencies.
  • Integration with payment gateways — Integrate with multiple external gateways (Stripe, PayPal, Adyen, etc.). Abstract gateway-specific APIs behind a unified internal interface. Support failover to a secondary gateway if the primary is unavailable.

Non-Functional Requirements

  • Exactly-once payment processing: The single most critical requirement. A customer must never be charged twice for the same payment, even if the client retries due to network timeouts. This is achieved through idempotency keys and transactional guarantees.
  • Availability: 99.99% uptime (52 minutes of downtime per year). Payment systems are revenue-critical — every minute of downtime directly translates to lost sales.
  • PCI DSS compliance: Never store raw credit card numbers. Use tokenization via the payment gateway. Encrypt all sensitive data at rest and in transit. Maintain audit trails for all access to payment data.
  • Latency: <500ms for payment processing (from request to gateway response). <100ms for payment status queries. Users abandon checkout if payment takes too long.
  • Throughput: 1 million transactions per day (~12 TPS average, ~120 TPS peak during flash sales). The system must handle 10x traffic spikes without degradation.
  • Audit trail: Every state change, every retry, every gateway interaction must be logged immutably. Financial regulators require the ability to reconstruct the complete history of any transaction.
Interview Tip: Start by asking: “Are we building a payment gateway (like Stripe) or a payment service that uses existing gateways?” These are very different systems. A payment gateway directly interfaces with card networks (Visa, Mastercard) and banks — this requires PCI Level 1 certification and is extremely complex. A payment service (what most companies build) orchestrates payments through existing gateways. This design focuses on the payment service. Also clarify: “Do we need to support subscriptions and recurring payments, or just one-time payments?” We focus on one-time payments here.

Key Insight: Unlike systems like metrics monitoring or video streaming, a payment system is NOT a scale problem. 12 TPS average is trivial for any modern database. The real challenge is correctness: ensuring exactly-once processing, maintaining a consistent ledger, handling partial failures gracefully, and complying with financial regulations. In an interview, don’t spend too much time on scaling — focus on idempotency, the ledger, and failure handling. These are what interviewers at Stripe and PayPal care about.

3. API Design

Initiate Payment

POST /api/v1/payments 
Headers:
  Authorization: Bearer <token>
  Idempotency-Key: "a1b2c3d4-e5f6-7890-abcd-ef1234567890"   ← CRITICAL

Request Body:
{
  "amount": 4999,                    // Amount in smallest currency unit (cents)
  "currency": "USD",                 // ISO 4217 currency code
  "payment_method": {
    "type": "credit_card",
    "token": "tok_visa_4242"         // Tokenized card (never raw card number!)
  },
  "merchant_id": "merch_abc123",
  "description": "Order #12345",
  "metadata": {
    "order_id": "order_12345",
    "customer_email": "user@example.com"
  },
  "capture": true                    // true = auth+capture, false = auth only
}

Response (201 Created):
{
  "id": "pay_9x8y7z6w5v4u",
  "status": "captured",              // or "authorized" if capture=false
  "amount": 4999,
  "currency": "USD",
  "payment_method": "credit_card",
  "gateway": "stripe",
  "gateway_transaction_id": "ch_3MqBL...",
  "idempotency_key": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "created_at": "2024-01-15T10:30:00Z"
}
Idempotency-Key header is the most important design decision in this API. The client generates a unique key (UUID) for each payment intent and sends it in the header. If the same key is sent again (due to retry after timeout), the server returns the cached response from the first request instead of processing a new payment. This prevents double charging. The key is stored in the database alongside the payment record. Without this, a network timeout followed by a client retry would charge the customer twice.

  "amount": 4999,
  "currency": "USD",
  "merchant_name": "Acme Store",
  "payment_method_last4": "4242",

Interview Tip: Notice that amounts are in the smallest currency unit (cents, not dollars). This avoids floating-point precision issues. $49.99 is stored as 4999 (integer). This is how Stripe, PayPal, and every serious payment system handles money. Never use floating-point for currency — 0.1 + 0.2 = 0.30000000000000004 in IEEE 754 floating point. Also note: the card token (tok_visa_4242) is provided instead of raw card numbers. The client collects card details via a gateway-hosted form (Stripe Elements) and receives a token. Our server never sees or stores raw card numbers — this is essential for PCI DSS compliance.

Key Insight: The idempotency_key column with a UNIQUE constraint is the database-level enforcement of exactly-once processing. When a duplicate request arrives, the INSERT fails with a unique constraint violation, and the server returns the existing payment record instead of creating a new one. This works even if the application server crashes and restarts — the constraint is enforced by the database, not application memory. The payment_events table provides event sourcing: the payments table holds the current state, but the events table holds the complete history. You can always derive the current state from the events, but not vice versa.

5. High-Level Design

The architecture follows a layered pattern: Client → Payment Service → Payment Gateway → Bank/Card Network. Supporting services handle ledger bookkeeping, reconciliation, and notifications. The Payment Service is the orchestrator that coordinates the entire payment flow.

Key Components

Payment Service (Orchestrator)

The central coordinator for all payments.

Responsibilities:
• Receive payment requests from clients
• Check idempotency key in DB
• Validate amount, currency, merchant
• Select gateway via Gateway Router
• Call gateway API (authorize/capture)
• Persist payment record in DB
• Publish payment events to Kafka
• Return response to client

Stateless — can scale horizontally.
All state is in the database.
Multiple instances behind a load balancer.

Ledger Service

Maintains the financial truth of the system.

Responsibilities:
• Create double-entry ledger records
  for every payment and refund
• Debit buyer account, credit seller
• Track running balances per account
• Enforce invariant:
  SUM(debits) = SUM(credits)
• Provide balance queries for merchants
• Support settlement calculations

Consumes payment events from Kafka.
Writes to ledger_entries table.
Critical for financial correctness.
Interview Tip: Emphasize the separation between the Payment Service and the Ledger Service. The Payment Service handles the mechanics of processing a payment (talking to gateways). The Ledger Service handles the accounting (who owes what to whom). This separation is important because: (1) the ledger is the source of financial truth and must be independently auditable, (2) the ledger can be updated asynchronously after the payment succeeds, and (3) different teams (engineering vs. finance) own these services. At Stripe, these are separate systems with different consistency requirements.

6. Deep Dive

6a. Idempotency — The Most Important Concept

Idempotency ensures that performing the same operation multiple times produces the same result as performing it once. In a payment system, this means: if a client sends the same payment request twice (due to retry after timeout), the customer is charged exactly once. This is the single most critical design concept in any payment system.

sequenceDiagram participant C as Client participant PS as Payment Service participant GW as Gateway Note over C,GW: Problem - Without Idempotency C->>PS: POST /payments charge $49.99 PS->>GW: charge $49.99 GW-->>PS: success PS--xC: TIMEOUT response lost C->>PS: Retry POST /payments charge $49.99 PS->>GW: charge $49.99 AGAIN GW-->>PS: success PS-->>C: 201 Created Note over C,GW: Customer charged $99.98 - DOUBLE CHARGE! Note over C,GW: Solution - With Idempotency Key C->>PS: POST /payments Idempotency-Key abc PS->>PS: Check DB key abc exists NO PS->>PS: Insert payment status processing PS->>GW: charge $49.99 GW-->>PS: success PS->>PS: Update status captured PS--xC: TIMEOUT C->>PS: Retry POST /payments Idempotency-Key abc PS->>PS: Check DB key abc exists YES PS-->>C: 200 OK cached response Note over C,GW: Customer charged exactly $49.99 - Correct! 
    IDEMPOTENCY IMPLEMENTATION DETAIL
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    def process_payment(request):
        idempotency_key = request.headers["Idempotency-Key"]

        # Step 1: Check if this key already exists
        existing = db.query(
            "SELECT * FROM payments WHERE idempotency_key = %s",
            idempotency_key
        )

        if existing:
            # Duplicate request — return cached response
            if existing.status == "processing":
                # Original request still in progress
                return 409 Conflict ("Payment in progress")
            else:
                # Original request completed
                return 200 OK (existing)   # ← cached response

        # Step 2: Insert new payment (atomically with key)
        try:
            payment = db.insert("""
                INSERT INTO payments (id, idempotency_key, amount,
                    currency, status, ...)
                VALUES (%s, %s, %s, %s, 'processing', ...)
            """, new_uuid(), idempotency_key, amount, currency)
        except UniqueConstraintViolation:
            # Race condition: another thread inserted first
            # Retry Step 1
            return process_payment(request)

        # Step 3: Call payment gateway
        try:
            gateway_response = gateway.charge(amount, currency, token)
            db.update(payment.id, status="captured",
                      gateway_response=gateway_response)
            return 201 Created (payment)
        except GatewayError:
            db.update(payment.id, status="failed")
            return 500 Error

    KEY DESIGN DECISIONS:
    ────────────────────────────────────────────────────────

    1. The idempotency key is stored in the DB with a UNIQUE
       constraint — not in application memory or Redis.
       This survives server restarts and works across
       multiple application instances.

    2. The payment is inserted with status "processing"
       BEFORE calling the gateway. This ensures the key is
       claimed even if the server crashes after the gateway
       call but before the DB update.

    3. The UNIQUE constraint handles race conditions: if two
       threads try to insert the same key simultaneously,
       one will fail with a constraint violation and retry.

    4. Idempotency keys should expire after 24–48 hours.
       This prevents the table from growing indefinitely
       and allows clients to reuse keys after expiry.
This is the #1 topic interviewers test at Stripe, PayPal, and Square. If you can explain idempotency clearly — the problem it solves, how the key works, where it’s stored, how race conditions are handled, and what happens when the server crashes mid-payment — you’ve demonstrated deep understanding of payment systems. Practice drawing the sequence diagram from memory.

6b. Payment Flow — Authorize vs. Capture

Payments typically follow a two-phase approach: authorization (verify the customer has funds and place a hold) and capture (actually transfer the funds). Some merchants use a combined auth+capture in a single step.

6c. Double-Entry Ledger — The Financial Truth

Every payment system needs a ledger that follows double-entry bookkeeping: every transaction creates exactly two entries — a debit from one account and a credit to another. The sum of all debits must always equal the sum of all credits. This 700-year-old accounting principle is how you detect errors, fraud, and system bugs.

          Money doesn't appear or disappear — it moves.

    WITH PLATFORM FEE (e.g., marketplace takes 10%):
    ────────────────────────────────────────────────────────

    Customer pays $49.99 for a product on a marketplace.
    Platform takes 10% fee ($5.00). Merchant receives $44.99.

    ┌────────┬──────────────────┬────────┬────────┐
    │ Entry  │ Account          │ Type   │ Amount │
    ├────────┼──────────────────┼────────┼────────┤
    │ LE-1   │ Customer         │ DEBIT  │ $49.99 │
    │ LE-2   │ Merchant         │ CREDIT │ $44.99 │
    │ LE-3   │ Platform Revenue │ CREDIT │ $5.00  │
    └────────┴──────────────────┴────────┴────────┘

    Debits:  $49.99
    Credits: $44.99 + $5.00 = $49.99  ✓ Balanced!

    If debits ≠ credits at ANY point, you have a bug.
    Run this check daily. It's your financial safety net.

6d. Reconciliation — Trust but Verify

Reconciliation is the process of comparing your internal ledger with the payment gateway’s settlement reports to ensure they match. Discrepancies indicate bugs, failed callbacks, or fraud. This runs as a daily batch job.

    RECONCILIATION PROCESS
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    DAILY RECONCILIATION FLOW:
    ────────────────────────────────────────────────────────

    1. Download settlement report from gateway
       (Stripe sends daily CSV/API with all settled transactions)

    2. For each transaction in the settlement report:
       a. Look up the corresponding payment in our DB
          (match by gateway_txn_id)
       b. Compare amounts, currencies, statuses

    3. Classify each transaction:

    ┌──────────────────┬───────────────────────────────────┐
    │  Classification  │  Description                      │
    ├──────────────────┼───────────────────────────────────┤
    │  MATCHED         │  Our record matches gateway's     │
    │                  │  record. Amount, currency, status  │
    │                  │  all agree. No action needed.      │
    ├──────────────────┼───────────────────────────────────┤
    │  AMOUNT MISMATCH │  We show $49.99, gateway shows    │
    │                  │  $48.99. Could be currency         │
    │                  │  conversion or a bug. Flag for     │
    │                  │  manual review.                    │
    ├──────────────────┼───────────────────────────────────┤
    │  MISSING IN      │  Gateway settled a payment we     │
    │  OUR SYSTEM      │  don't have. Possibly a missed    │
    │                  │  webhook callback. Create the      │
    │                  │  record and investigate.            │
    ├──────────────────┼───────────────────────────────────┤
    │  MISSING IN      │  We show a captured payment, but  │
    │  GATEWAY         │  gateway didn't settle it. The    │
    │                  │  capture may have failed silently. │
    │                  │  Investigate and potentially       │
    │                  │  refund the customer.              │
    ├──────────────────┼───────────────────────────────────┤
    │  STATUS MISMATCH │  We show "captured", gateway      │
    │                  │  shows "refunded". A refund was    │
    │                  │  processed outside our system.     │
    │                  │  Update our records.               │
    └──────────────────┴───────────────────────────────────┘

    4. Generate reconciliation report:
       • Total transactions: 1,000,000
       • Matched: 999,950 (99.995%)
       • Mismatches: 50 (flagged for review)
       • Total discrepancy amount: $1,234.56

    5. Alert finance team if discrepancy exceeds threshold.

    At scale, 99.99% match rate is good. The remaining
    0.01% (100 transactions/day at 1M/day) are investigated
    manually or auto-resolved by the reconciliation service.

6e. Handling Failures — What Can Go Wrong

Payment systems must handle a wide variety of failure scenarios gracefully. The key principle is: when in doubt, don’t charge the customer. It’s better to fail a payment and ask the customer to retry than to charge them and not be able to confirm it.

    FAILURE SCENARIOS AND HANDLING
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    SCENARIO 1: Gateway timeout
    ────────────────────────────────────────────────────────

    Payment Service ── charge $49.99 ──▶ Gateway
                                           │
                   ✗ TIMEOUT (no response) │
                   ◀── ✗ ─────────────────┘

    Did the charge go through? WE DON'T KNOW.

    Solution:
    1. Mark payment as "unknown" in our DB
    2. Query gateway for transaction status (GET /charges/{id})
    3. If gateway confirms success → mark as captured
    4. If gateway confirms failure → mark as failed
    5. If gateway also doesn't know → wait and retry query
    6. NEVER retry the charge — use the idempotency key
       to query, not to re-submit

    SCENARIO 2: Our server crashes after gateway success
    ────────────────────────────────────────────────────────

    Payment Service ── charge $49.99 ──▶ Gateway
    Payment Service ◀── success ────────┘
    Payment Service ── update DB ──▶ DB
                    ✗ SERVER CRASHES ✗

    The customer was charged, but our DB doesn't know.

    Solution:
    1. Payment was inserted with status "processing" BEFORE
       the gateway call (Step 2 in idempotency flow)
    2. A background job scans for "processing" payments
       older than 5 minutes
    3. For each, query the gateway for actual status
    4. Update our DB to match gateway's truth
    5. This is called "payment recovery" or "stuck payment
       resolution"

    SCENARIO 3: Gateway is completely down
    ────────────────────────────────────────────────────────

    Payment Service ── charge ──▶ Stripe
                    ✗ CONNECTION REFUSED ✗

    Solution:
    1. Circuit breaker detects Stripe is down
       (after N consecutive failures in M seconds)
    2. Circuit breaker OPENS — stop sending to Stripe
    3. Gateway Router fails over to secondary gateway (Adyen)
    4. Process payment through Adyen instead
    5. Circuit breaker periodically tests Stripe (half-open)
    6. When Stripe recovers, circuit breaker CLOSES
    7. Resume sending to Stripe

    Circuit Breaker States:
    ┌────────┐  N failures  ┌────────┐  test    ┌───────────┐
    │ CLOSED │─────────────▶│  OPEN  │─────────▶│ HALF-OPEN │
    │(normal)│              │(reject)│          │ (test 1)  │
    └────────┘              └────────┘          └───────────┘
         ▲                                          │
         │              success                     │
         └──────────────────────────────────────────┘
              failure → back to OPEN

    SCENARIO 4: Database is down
    ────────────────────────────────────────────────────────

    Solution:
    1. Cannot check idempotency key → REJECT the payment
    2. Return 503 Service Unavailable to client
    3. Client retries with exponential backoff
    4. NEVER process a payment without DB access —
       you can't guarantee idempotency without the DB

6f. Exactly-Once Processing — Transactional Outbox Pattern

Ensuring exactly-once processing requires more than just idempotency keys. When the Payment Service needs to both update the database AND publish an event to Kafka, these two operations must be atomic. The transactional outbox pattern solves this.

graph TD subgraph SingleTXN[Single Database Transaction] UPD[UPDATE payments SET status captured] INS[INSERT INTO outbox_events published false] UPD --> INS end subgraph OutboxPublisher[Outbox Publisher Process] POLL[SELECT unpublished events LIMIT 100] PUB[Publish to Kafka topic] MARK[UPDATE outbox_events SET published true] POLL --> PUB --> MARK end subgraph Downstream[Downstream Consumers] Ledger[Ledger Service] Notif[Notification Service] Recon[Reconciliation Service] end SingleTXN --> POLL PUB --> Ledger PUB --> Notif PUB --> Recon MARK -.retry on failure.-> POLL
Key Insight: The transactional outbox pattern converts a distributed transaction (DB + Kafka) into a local transaction (DB only) plus an eventually-consistent relay. This is a fundamental pattern in microservices architecture, not just payment systems. The trade-off is slightly increased latency (events are published with a small delay) and the requirement that downstream consumers be idempotent. An alternative is Change Data Capture (CDC) using tools like Debezium, which reads the database’s transaction log and publishes changes to Kafka automatically — no outbox table needed.

6g. Security — PCI DSS Compliance

Payment systems handle sensitive financial data and must comply with the Payment Card Industry Data Security Standard (PCI DSS). The core principle is: minimize the scope of sensitive data in your system.

    PCI DSS COMPLIANCE STRATEGY
    ≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡≡

    TOKENIZATION — Never Touch Raw Card Numbers
    ────────────────────────────────────────────────────────

    Without tokenization (BAD — PCI Level 1 required):

    Browser ── card: 4242-4242-4242-4242 ──▶ Your Server
    Your Server ── card: 4242-4242-4242-4242 ──▶ Gateway

    Your server sees and transmits raw card numbers.
    You must comply with ALL 300+ PCI DSS requirements.
    Annual audit costs $50K–$500K. One breach = game over.


    With tokenization (GOOD — PCI SAQ-A):

    Browser ── card: 4242-4242-4242-4242 ──▶ Stripe.js
                                              (hosted by Stripe)
    Browser ◀── token: tok_visa_4242 ──────── Stripe.js

    Browser ── token: tok_visa_4242 ──▶ Your Server
    Your Server ── token: tok_visa_4242 ──▶ Stripe API

    Your server NEVER sees the raw card number.
    Stripe handles PCI compliance for card data.
    You only need SAQ-A (simplest PCI questionnaire).


    WHAT YOU MUST STILL DO:
    ────────────────────────────────────────────────────────

    • HTTPS everywhere (TLS 1.2+ for all API communication)
    • Encrypt sensitive data at rest (AES-256)
      — gateway_response may contain partial card info
      — customer PII (email, address)
    • Access controls: least privilege, role-based access
    • Audit logging: who accessed what payment data, when
    • Network segmentation: payment services in isolated VPC
    • Regular security scans and penetration testing
    • Key rotation for encryption keys (every 90 days)
    • Never log sensitive data (card tokens, amounts in
      plain text in application logs)


    DATA CLASSIFICATION:
    ────────────────────────────────────────────────────────

    ┌──────────────────┬───────────────┬──────────────────┐
    │  Data            │  Sensitivity  │  Storage Rule    │
    ├──────────────────┼───────────────┼──────────────────┤
    │  Raw card number │  PROHIBITED   │  Never store     │
    │  CVV / CVC       │  PROHIBITED   │  Never store     │
    │  Card token      │  High         │  Encrypted, DB   │
    │  Last 4 digits   │  Medium       │  OK for display  │
    │  Transaction amt │  Medium       │  Encrypted at    │
    │                  │               │  rest             │
    │  Payment status  │  Low          │  Standard DB     │

7. Trade-offs

Decision Option A Option B Recommendation
Synchronous vs. Async Payment Processing Synchronous: Client waits for the gateway response. Simple flow, immediate feedback. But the client is blocked for 200–500ms. If the gateway is slow, the client times out and retries (risking double charges without idempotency). Asynchronous: Return 202 Accepted immediately, process payment in background, notify via webhook. Better UX for slow gateways. But more complex: client must poll or listen for webhooks, harder to show instant confirmation. Use synchronous for standard card payments (<500ms). Use asynchronous for bank transfers, UPI, and methods that inherently take longer. Most users expect instant confirmation for card payments — async adds unnecessary complexity for fast gateways.
Single vs. Multiple Payment Gateways Single gateway: Simpler integration, one contract, one dashboard. But single point of failure — if Stripe goes down, all payments fail. No cost optimization across gateways. Multiple gateways: Failover capability, cost optimization (route to cheapest gateway per region/method). But more complex: must abstract gateway APIs, handle different response formats, reconcile across multiple sources. Start with a single gateway and add a second when you reach scale where downtime cost exceeds integration cost. Abstract the gateway interface from day one so adding a second gateway is a configuration change, not a rewrite. Most companies add a second gateway at ~$10M+ GMV/month.
Event Sourcing vs. CRUD for Payment State CRUD: Simple — update the payment row’s status field directly. Easy to query current state. But loses history: you can’t tell when a payment transitioned from authorized to captured, or if it was ever in a failed state. Event sourcing: Append-only event log. Current state derived from events. Complete audit trail. But more complex: must replay events to get current state, eventual consistency between event store and read models. Use a hybrid approach: CRUD for the payments table (fast reads of current state) PLUS an append-only payment_events table (audit trail). This gives you the simplicity of CRUD for queries and the auditability of event sourcing for compliance. This is what Stripe does internally.
Strong vs. Eventual Consistency for Ledger Strong consistency: Ledger entries created in the same transaction as the payment update. Ledger is always in sync. But adds latency to the payment path and creates tight coupling between payment and ledger services. Eventual consistency: Ledger entries created asynchronously via events. Payment path is faster. But there’s a window where the ledger is behind — balance queries may be stale. Reconciliation catches discrepancies. Use eventual consistency for the ledger. The payment response to the customer should not wait for ledger entries to be created. The ledger is an internal accounting system — a few seconds of delay is acceptable. Use the transactional outbox pattern to guarantee the event is eventually processed. Run reconciliation daily to catch any gaps.
Interview Tip: When discussing trade-offs, connect them to business impact. For example: “We chose synchronous processing for card payments because checkout conversion drops 7% for every additional second of latency. An async flow that shows ‘payment pending’ instead of ‘payment confirmed’ would hurt conversion rates. However, for bank transfers in India (UPI), the flow is inherently async — the user must approve in their banking app — so async is the natural fit there.” This shows you think about system design in the context of business outcomes, not just technical elegance.
