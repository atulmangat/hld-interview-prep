Design a Chat System

Design a scalable real-time chat system (like WhatsApp or Facebook Messenger) that supports 1:1 messaging, group chats with up to 500 members, online/offline presence indicators, read receipts, media sharing, and message history — all with sub-100ms delivery latency, end-to-end encryption, and at-least-once delivery guarantees at the scale of 50 million daily active users.

Hard Messaging Asked at: Meta, Microsoft, Slack

1. Requirements

Functional Requirements

  • 1:1 chat — Users can send and receive text messages in real time with any other user. Messages are persisted and available across devices.
  • Group chat — Users can create group conversations with up to 500 members. Any member can send a message visible to all other members of the group.
  • Online/offline presence — Users can see whether their contacts are currently online, offline, or were “last seen” at a specific time. Presence updates propagate in near real time.
  • Read receipts — Messages transition through delivery states: sent → delivered → read. Senders see visual indicators (single check, double check, blue check) reflecting the current state.
  • Media sharing — Users can send images, videos, audio messages, and documents. Media is uploaded to object storage and a reference URL is sent as part of the message payload.
  • Message history — Users can scroll back through their full conversation history. Messages are persisted indefinitely and paginated with cursor-based navigation.

Non-Functional Requirements

  • Real-time delivery: Messages must be delivered end-to-end in under 100ms (p99) when both users are online. The system must feel instantaneous.
  • Massive scale: Support 50 million daily active users (DAU), each sending an average of 40 messages per day, totaling 2 billion messages per day.
  • Message ordering: Messages within a single conversation must be displayed in a consistent, causally correct order across all participants. No message should appear “before” a message it was a reply to.
  • At-least-once delivery: Every message must be delivered at least once. The system must handle network partitions, server crashes, and client disconnects without losing messages. Clients handle deduplication.
  • End-to-end encryption (E2E): Message content is encrypted on the sender’s device and decrypted only on the recipient’s device. The server never sees plaintext message content.
  • High availability: The system must be available 99.99% of the time. Chat is a core communication tool — downtime is unacceptable.
Interview Tip: Start by clarifying scope: “Should we support 1:1 only, or also group chat? What’s the max group size?” Group chat fundamentally changes the fan-out strategy. Also ask: “Do we need E2E encryption?” E2E encryption means the server stores only ciphertext and cannot index or search message content, which affects many design decisions. Finally, clarify the delivery guarantee: “Is at-least-once acceptable, or do we need exactly-once?” Exactly-once is significantly harder and usually unnecessary — clients can deduplicate using message IDs.

2. Capacity Estimation

Assumptions

Parameter Value Notes
Daily Active Users (DAU) 50 million WhatsApp-lite scale
Messages per user per day 40 Mix of 1:1 and group messages
Average message size 100 bytes Text content + metadata (media stored separately)
Concurrent connections ~10 million ~20% of DAU online at any given time
Average group size 10 members Most groups are small; max is 500
Messages with media ~10% Average media size ~200 KB (compressed images)

Throughput Calculation

Message throughput:
  Total messages/day    = 50M users × 40 msgs = 2 billion messages/day
  Messages per second   = 2B / 86,400 ≈ 23,000 msg/sec
  Peak (3x)             ≈ 70,000 msg/sec

WebSocket connections:
  Concurrent connections = 50M × 20% = 10 million persistent connections
  At ~50K connections per server = 200 WebSocket servers

Presence updates:
  Heartbeat interval    = every 30 seconds
  Heartbeat rate        = 10M online users / 30s ≈ 333,000 heartbeats/sec

Storage Calculation

Message storage:
  Per message           = ~100 bytes (text + metadata)
  Daily                 = 2B × 100 bytes = 200 GB/day
  Yearly                = 200 GB × 365 = ~73 TB/year
  5-year retention      = ~365 TB

Media storage:
  Messages with media   = 2B × 10% = 200M media files/day
  Average media size    = 200 KB
  Daily media storage   = 200M × 200 KB = 40 TB/day
  Yearly media storage  = ~14.6 PB/year

Connection state (Redis):
  Per connection        = ~200 bytes (user_id, server_id, last_active)
  Total                 = 10M × 200 bytes = 2 GB (fits in a single Redis node)
Key Insight: The numbers reveal two critical design drivers. First, 10 million concurrent WebSocket connections require a stateful connection layer — unlike REST APIs, you cannot simply load-balance across stateless servers because each connection is persistent. Second, at 23K messages/sec, the write throughput is moderate, but the storage grows relentlessly (365 TB over 5 years). This demands a storage engine optimized for sequential writes and time-range reads — exactly the pattern wide-column stores like Cassandra excel at.

3. API Design

The chat system uses a dual-protocol approach: WebSocket for real-time bidirectional communication (sending/receiving messages, presence updates, typing indicators) and REST for non-real-time operations (fetching message history, uploading media, managing groups).

WebSocket Events

Why WebSocket? Chat requires the server to push messages to clients instantly. HTTP is request-response only — the server cannot initiate communication. WebSocket provides a persistent, full-duplex TCP connection where both client and server can send data at any time, enabling sub-100ms message delivery.
WS wss://chat.example.com/ws?token={auth_token}

Establish a persistent WebSocket connection. The client authenticates via a JWT token in the query string. Once connected, the client can send and receive the following event types:

GET /api/v1/presence/{user_id}

Get the online/offline status and last-seen timestamp for a specific user. Used to display presence indicators in the chat UI.

Request:
  GET /api/v1/presence/u_44556
  Headers:
    Authorization: Bearer <user-token>

Response (200 OK):
{
  "user_id": "u_44556",
  "status": "online",
  "last_seen": "2026-04-14T10:30:00Z"
}
local_id for Deduplication: The client generates a unique local_id (UUID) for every message before sending. If the network drops after the server receives the message but before the client gets the ACK, the client will retry. The server uses local_id to detect and discard duplicate submissions. This is how at-least-once delivery works without showing duplicate messages to recipients. The local_id is also echoed back in the server ACK so the client can match the server-assigned message_id to its local pending message.

4. Data Model

users

Core user table. Stored in a relational database (PostgreSQL).

Column Type Description
user_id UUID (PK) Unique user identifier
username VARCHAR (unique) Display handle
phone_number VARCHAR (unique) Phone number (primary identifier for WhatsApp-style)
avatar_url VARCHAR Profile picture URL on CDN
public_key TEXT E2E encryption public key
created_at TIMESTAMP Account creation time

channels

Represents a conversation — either a 1:1 direct message or a group chat. Every conversation is a “channel.”

Column Type Description
channel_id UUID (PK) Unique channel identifier
type ENUM direct (1:1) or group
name VARCHAR Group name (null for direct channels)
creator_id UUID (FK) User who created the group
max_members INT Maximum allowed members (default 500 for groups)
created_at TIMESTAMP Channel creation time

channel_members

Maps users to channels. For a 1:1 chat, there are exactly 2 rows. For a group of 200, there are 200 rows.

Column Type Description
channel_id UUID (PK, part 1) The channel
user_id UUID (PK, part 2) The member
role ENUM admin, member
last_read_message_id UUID Last message the user has read in this channel (for read receipts)
joined_at TIMESTAMP When the user joined the channel

messages (Cassandra)

The messages table is the highest-volume table in the system. Stored in Cassandra (or HBase) — a wide-column store optimized for this exact access pattern.

Column Type Description
channel_id UUID (Partition Key) All messages in a channel are co-located on the same partition
message_id Snowflake ID (Sort Key, DESC) Time-ordered unique ID; messages sorted by creation time within a partition
sender_id UUID User who sent the message
content BLOB Encrypted message content (ciphertext with E2E encryption)
type ENUM text, image, video, audio, file
media_url VARCHAR CDN URL for media attachments (null for text-only)
seq_num BIGINT Per-channel monotonically increasing sequence number for ordering
reply_to UUID message_id of the parent message (null if not a reply)
created_at TIMESTAMP Server-assigned creation timestamp
Why Cassandra / HBase for Messages? The message access pattern is almost exclusively: “Get the most recent N messages for channel X” — a classic time-series query. With channel_id as the partition key and message_id (a Snowflake ID encoding timestamp) as the sort key, Cassandra stores all messages for a channel contiguously on disk, sorted by time. A query for the latest 50 messages is a single sequential disk read from one partition — no joins, no index lookups, no scatter-gather. This is why chat systems at scale (Discord, Facebook Messenger) use wide-column stores rather than relational databases for message storage. 
Cassandra CQL schema:

CREATE TABLE messages (
    channel_id  UUID,
    message_id  TIMEUUID,          -- Time-based UUID (sorted by time)
    sender_id   UUID,
    content     BLOB,              -- Encrypted content
    type        TEXT,
    media_url   TEXT,
    seq_num     BIGINT,
    reply_to    UUID,
    created_at  TIMESTAMP,
    PRIMARY KEY (channel_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
-- DESC ordering: most recent messages first (optimized for "load latest")

-- Query: Get latest 50 messages for a channel
SELECT * FROM messages
  WHERE channel_id = ?
  ORDER BY message_id DESC
  LIMIT 50;

-- Query: Paginate older messages (cursor = last message_id seen)
SELECT * FROM messages
  WHERE channel_id = ?
    AND message_id < ?
  ORDER BY message_id DESC
  LIMIT 50;

5. High-Level Design

The chat system architecture centers around a stateful WebSocket layer for real-time message delivery, backed by a message queue for reliable routing and a wide-column store for persistent message storage. A separate Presence Service tracks online/offline status using Redis with TTL-based heartbeats.

Key Components

  • WebSocket Servers: Stateful servers that maintain persistent connections with clients. Each server handles ~50K concurrent connections. When a message arrives, it is forwarded to the message queue. When a message needs to be delivered, the Chat Service looks up the recipient’s WS server in the connection registry and pushes the message to it.
  • Message Queue (Kafka): Decouples message ingestion from processing. Provides durability (messages are not lost if the Chat Service crashes), ordering (per-channel partition), and backpressure handling. Each channel maps to a Kafka partition for ordered processing.
  • Chat Service: Stateless workers that consume from the message queue, assign per-channel sequence numbers, persist messages to Cassandra, and route them to the correct WebSocket server for delivery. If the recipient is offline, the message is stored for later delivery and a push notification is sent.
  • Connection Registry (Redis): Maps each online user to the WebSocket server holding their connection. When the Chat Service needs to deliver a message, it looks up user:{recipient_id} in Redis to find which WS server to forward to.
  • Presence Service (Redis): Tracks online/offline status using TTL-based keys. Each client sends a heartbeat every 30 seconds, refreshing a Redis key with a 60-second TTL. If the key expires, the user is considered offline.
  • Push Notification Service: Sends APNs (iOS) or FCM (Android) push notifications to offline users when they receive a message. The notification contains a preview of the message to prompt the user to open the app.
Why a Message Queue Between WS Server and Chat Service? Without a queue, if the Chat Service is down or slow, the WS server would have to buffer messages in memory — risking data loss on crash. The message queue (Kafka) provides: (1) durability — messages survive server crashes, (2) ordering — messages within a channel are processed in order, (3) backpressure — if the Chat Service falls behind, messages queue up safely instead of being dropped, and (4) decoupling — WS servers and Chat Service can scale independently.

6. Deep Dive

6a. Communication Protocols: Polling vs. Long Polling vs. WebSocket vs. SSE

Choosing the right communication protocol is the most fundamental architectural decision for a chat system. The protocol determines latency, resource usage, and scalability.

Protocol How It Works Latency Server Resources Bidirectional? Best For
HTTP Polling Client sends GET every N seconds asking “any new messages?” High (up to N seconds) Very high — most requests return empty No Simple dashboards, low-frequency updates
Long Polling Client sends GET; server holds the connection open until new data is available or timeout Medium (~1-2s) High — one thread per waiting client No Notifications, fallback for WebSocket
Server-Sent Events (SSE) Server pushes events to client over a persistent HTTP connection Low (~100ms) Medium — persistent connection, but unidirectional No (server → client only) Live feeds, stock tickers, notifications
WebSocket Full-duplex persistent TCP connection; both sides can send data at any time Very low (<50ms) Low per connection — no HTTP overhead after handshake Yes Chat, gaming, collaborative editing

HTTP Polling (Bad for Chat)

Client: Any new messages? (GET /messages)
Server: No.
Client: Any new messages? (GET /messages)
Server: No.
Client: Any new messages? (GET /messages)
Server: Yes! Here's 1 message.
Client: Any new messages? (GET /messages)
Server: No.

Problem: 75% of requests are wasted.
At 10M users polling every 2s:
= 5M requests/sec of pure waste.

WebSocket (Ideal for Chat)

Client: [Opens WS connection]
Server: [Connection established]
  ... (silence, no traffic) ...
Server: New message! {data: "Hi!"}
  ... (silence, no traffic) ...
Client: Sending message {data: "Hey!"}
Server: ACK.
Server: New message! {data: "What's up?"}

No wasted requests. Zero overhead
when idle. Instant delivery.
10M users = 10M open connections
(~200 WS servers at 50K each).
Why WebSocket Wins for Chat: Chat requires bidirectional real-time communication. The client needs to both send and receive messages instantly. SSE is server-to-client only — the client would still need a separate HTTP request to send messages, adding latency and complexity. WebSocket provides a single persistent connection for both directions, with minimal overhead (just 2-byte frame headers vs. ~800 bytes for HTTP headers on every request). The trade-off is statefulness — each connection is pinned to a specific server, requiring a connection registry for routing.

6b. 1:1 Message Flow — Online and Offline Recipients

The message delivery flow differs depending on whether the recipient is currently online (has an active WebSocket connection) or offline.

S->>S: Enqueue to Kafka S->>S: Chat Service consumes S->>S: Assign seq_num 1042 S->>S: Persist to Cassandra S->>S: Lookup B WS server in Redis S-->>A: message.ack status sent S->>B: message.new msg_xyz seq 1042 B-->>S: delivery.ack msg_xyz S-->>A: message.ack status delivered Note over A,B: Total latency 50 to 100ms end to end Note over A,B: Case 2 - Recipient is Offline A->>S: message.send - Hi! Store and Forward: The “store and forward” pattern ensures no messages are lost when a recipient is offline. Messages are persisted to Cassandra immediately (durable storage) and also placed in an offline delivery queue. When the recipient reconnects, the system drains their offline queue and delivers all pending messages. The push notification serves as a “nudge” to prompt the user to open the app — it is not the delivery mechanism itself.

6c. Group Chat — Fan-out on Write vs. Fan-out on Read

Group chat introduces a fan-out problem: when one member sends a message, all other members must receive it. The strategy depends on group size.

Fan-out on Write (Small Groups)

  • Write to each member’s inbox when message is sent
  • Instant delivery — inbox is pre-populated
  • Write cost: O(N) per message where N = group size
  • Acceptable when N ≤ 50 (50 writes per message)
  • Used by: WhatsApp, iMessage

Fan-out on Read (Large Groups)

  • Only persist to Cassandra; no inbox writes
  • Members pull unread messages when they open the group
  • Write cost: O(1) per message regardless of group size
  • Read cost: one Cassandra query per group open
  • Used by: Slack, Discord, Telegram (large groups)

6d. Online Presence — Heartbeat Mechanism

Presence tracking answers the question: “Is this user currently online?” This seems simple but becomes challenging at scale due to the volume of status changes and the need to propagate updates to interested parties.

6e. Message Ordering — Sequence Numbers and Snowflake IDs

Message ordering is critical for chat — messages must appear in the correct causal order. If User A says “Want to grab lunch?” and User B replies “Sure!”, the reply must always appear after the question, on every device, for every participant.

Snowflake IDs for Global Uniqueness

graph LR SIGN["Sign Bit\n1 bit"] TS["Timestamp\n41 bits\n~69 years"] MID["Machine ID\n10 bits\n1024 nodes"] SEQ["Sequence\n12 bits\n4096/ms"] SIGN --> TS --> MID --> SEQ style SIGN fill:#e74c3c,color:#fff style TS fill:#3498db,color:#fff style MID fill:#2ecc71,color:#fff style SEQ fill:#f39c12,color:#fff
Handling Out-of-Order Delivery: Even with server-assigned sequence numbers, messages can arrive at the client out of order due to network jitter (message 1043 arrives before 1042). The client must buffer incoming messages and re-sort by seq_num before displaying. If a gap is detected (received 1042, then 1044 — missing 1043), the client should request the missing message from the server via REST: GET /api/v1/messages?channel_id=X&after_seq=1042&before_seq=1044. This ensures the conversation is always displayed in the correct order.

6f. Message Storage — Cassandra with Caching

Message storage must handle 23K writes/sec with 365 TB over 5 years, while supporting fast reads for recent messages. The architecture uses Cassandra as the primary store with Redis caching for hot data.

6g. Read Receipts and Delivery Status

Messages transition through a state machine: sent → delivered → read. Each state change is communicated back to the sender as a visual indicator.

Optimization — Batched Read Receipts: Instead of sending a read receipt for every individual message, the client sends only the last_read_message_id when the user opens a chat. Since messages are ordered by sequence number, all messages with seq_num ≤ last_read_seq are implicitly marked as read. This reduces read receipt traffic from O(unread_messages) to O(1) per chat open. WhatsApp uses this approach — when you open a chat with 50 unread messages, only one read receipt event is sent.

7. Trade-offs

Decision Option A Option B Recommendation
WebSocket vs. SSE WebSocket: Full-duplex, both client and server can send data. Requires stateful connection management. More complex server infrastructure (connection registry, sticky sessions). SSE (Server-Sent Events): Server-to-client only. Client still uses HTTP POST to send messages. Simpler server-side (standard HTTP). Automatic reconnection built into the browser API. Use WebSocket. Chat is inherently bidirectional — both sending and receiving happen on the same connection. SSE would require a separate HTTP channel for sending, adding latency (~50ms extra per message) and complexity. WebSocket’s 2-byte frame overhead vs. SSE’s HTTP headers also matters at 23K msg/sec.
Push vs. Pull for Group Messages Push (fan-out on write): Write to each member’s inbox when a message is sent. Instant delivery. Write cost = O(group_size) per message. Works well for small groups (≤50 members). Pull (fan-out on read): Only persist to the channel’s message store. Members pull unread messages when they open the group. Write cost = O(1). Read cost = one Cassandra query per group open. Use push for small groups (≤50) and pull for large groups (50–500). Small groups have high engagement (most members read most messages), so pre-populating inboxes avoids redundant reads. Large groups have low per-member engagement (most are lurkers), so push would waste writes on members who never read.
Message Ordering Guarantees Total ordering: All messages across all channels are globally ordered. Requires a single sequencer (bottleneck). Unnecessary for chat — messages in different channels don’t need relative ordering. Per-channel ordering: Messages within a single channel are strictly ordered via per-channel sequence numbers. Different channels are independent. Scales horizontally (one sequencer per channel). Use per-channel ordering. Chat only requires causal ordering within a conversation. A message in “Work Chat” doesn’t need to be ordered relative to a message in “Family Group.” Per-channel sequence numbers are assigned by the Chat Service and stored alongside each message.
Storage Engine: Cassandra vs. PostgreSQL vs. MongoDB PostgreSQL: ACID, rich queries, mature tooling. Harder to shard. Good for user/channel metadata. Not ideal for 365 TB of append-only message data. Cassandra: Built for massive write throughput and horizontal scaling. Partition key (channel_id) + sort key (message_id) perfectly matches the chat query pattern. No joins needed. Eventual consistency is acceptable for messages. Use Cassandra for messages and PostgreSQL for users, channels, and channel_members. Messages are append-only, time-series data with a simple access pattern (get by channel, sorted by time) — Cassandra’s sweet spot. User and channel metadata require relational integrity (foreign keys, unique constraints) — PostgreSQL’s strength.
Interview Tip: When discussing trade-offs, always connect your choice to the specific requirements. “We chose WebSocket over SSE because our FR requires bidirectional real-time messaging, and our NFR demands sub-100ms delivery. SSE would add an extra HTTP round-trip for sending, pushing us past the latency budget. The trade-off is operational complexity — we need a connection registry to track which server holds each user’s WebSocket — but this is a well-understood pattern used by WhatsApp, Slack, and Discord.”
