Design Search Autocomplete

Design a search autocomplete (typeahead) system that returns the top 5 most relevant suggestions as a user types each character — supporting multi-language queries, personalized ranking, real-time popularity updates, and offensive content filtering — all with sub-100ms response latency at the scale of 10 billion queries per day.

Medium Platform Asked at: Google, Amazon, Bing

1. Requirements

Functional Requirements

  • Prefix-based suggestions — As the user types each character, the system returns the top 5 matching search queries ranked by popularity/frequency. Typing “din” might return [“dinner recipes”, “dinosaur games”, “dining table”, “dinner near me”, “dine in restaurants”].
  • Ranked by popularity — Suggestions are ordered by query frequency (how often users have searched for that term). More popular queries appear first. Ranking may also factor in recency, trending topics, and user context.
  • Multi-language support — The system supports autocomplete in multiple languages (English, Spanish, Mandarin, etc.). Each language has its own trie or index. Language is detected from the user’s locale or input characters.
  • Personalization — Suggestions blend global popularity with the user’s personal search history. If a user frequently searches “dinner recipes keto”, typing “din” should surface that query higher than the global ranking would suggest.
  • Real-time updates — The suggestion corpus reflects recent trends. If a breaking news event causes “earthquake today” to spike in searches, it should appear in autocomplete within hours, not days.

Non-Functional Requirements

  • Ultra-low latency: Suggestions must be returned in under 100ms (p99). Users expect instant feedback as they type — any perceptible delay breaks the illusion of real-time assistance and degrades the search experience.
  • Massive scale: Support 10 billion search queries per day. Each query involves an average of 4 keystrokes before the user selects a suggestion or submits, generating ~40 billion autocomplete requests per day.
  • High availability: The system must be available 99.99% of the time. Autocomplete is a critical part of the search experience — if it fails, users see a blank dropdown, which feels broken even though search itself still works.
  • Data freshness: The suggestion index should be updated at least hourly for trending topics and daily for the full corpus rebuild. Stale suggestions (e.g., showing last week’s trending topics) erode user trust.
Interview Tip: Start by clarifying scope: “Are we designing just the autocomplete suggestion service, or the full search engine?” Autocomplete is a standalone service that sits in front of the search engine. Also ask: “Should suggestions only match prefixes, or also substrings and fuzzy matches?” Prefix matching is the standard expectation and maps cleanly to a trie data structure. Substring and fuzzy matching require an inverted index or n-gram approach, which is significantly more complex. Finally, clarify personalization depth: “Is personalization based on search history only, or also location, device, and time of day?”

Key Insight: The numbers reveal that the trie itself is small (~3 GB) and fits entirely in memory. The challenge is not storage — it is serving 460K QPS with sub-100ms latency. This is a read-heavy, latency-sensitive system. The design should optimize for fast prefix lookups (in-memory trie with pre-computed top-K at each node) and aggressive caching (both server-side and client-side). The data gathering pipeline that builds and updates the trie is a separate, offline system that runs on a different cadence.

3. API Design

The autocomplete system exposes a single, lightweight GET endpoint. It must be fast, cacheable, and stateless. No authentication is strictly required for public search suggestions, but user context can be passed for personalization.

GET /api/v1/suggestions?prefix={prefix}&limit={limit}&lang={lang}&user_id={user_id}

Return the top suggestions matching the given prefix, ranked by popularity. Results are returned in descending order of relevance score.

Request:
  GET /api/v1/suggestions?prefix=din&limit=5&lang=en&user_id=u_44556
  Headers:
    Accept: application/json
    X-Request-ID: req_abc123       // For tracing and deduplication

Query Parameters:
  prefix    (required)  The characters typed so far. URL-encoded for special chars.
  limit     (optional)  Number of suggestions to return. Default: 5, Max: 10.
  lang      (optional)  Language code (ISO 639-1). Default: "en".
  user_id   (optional)  For personalized suggestions. Omit for anonymous users.

Why GET (not POST)? GET requests are cacheable by CDNs, browser caches, and intermediate proxies. Since autocomplete responses for a given prefix are the same for most users (the global ranking), caching at the CDN layer can absorb a massive percentage of traffic. POST requests are not cached by default. The trade-off is that query parameters are visible in server logs and browser history, but search prefixes are not sensitive data. For personalized results, the user_id parameter creates a unique cache key per user, which reduces cache hit rates — this is why personalization should be blended client-side when possible.

4. Data Model

Trie Node Structure

The core data structure is a trie (prefix tree). Each node represents a single character in a search query. The path from root to any node spells out a prefix. The key optimization is storing the top-K suggestions at each node, so query-time lookups are O(prefix_length) with no additional traversal.

Query Frequency Table (Persistent Storage)

The trie is an in-memory data structure rebuilt periodically. The source of truth for query frequencies is a persistent database table used by the data gathering pipeline.

Column Type Description
query VARCHAR (PK) The normalized search query string
frequency BIGINT Total number of times this query has been searched
language VARCHAR Language code (en, es, zh, etc.)
last_updated TIMESTAMP When the frequency was last recalculated
is_filtered BOOLEAN Whether this query is blocked by the content filter
Key Insight: The trie is a read-optimized, derived data structure — it is not the source of truth. The source of truth is the query frequency table in the database, which is updated by the data gathering pipeline. The trie is rebuilt periodically (weekly full rebuild + hourly incremental updates) from this table and loaded into memory on the query servers. This separation of concerns means the query path (trie lookup) and the write path (frequency aggregation) are completely independent and can scale separately.

5. High-Level Design

The system is split into two independent subsystems: a Data Gathering Service (offline pipeline that collects query logs, aggregates frequencies, and builds the trie) and a Query Service (online service that serves autocomplete requests from the in-memory trie). These two subsystems operate on completely different timescales and have different scaling characteristics.

Key Components

  • CDN / Edge Cache: Caches autocomplete responses by prefix at edge locations worldwide. Since the top suggestions for “din” are the same for most users in the same region, the CDN absorbs ~60% of traffic. TTL of 5 minutes balances freshness with cache hit rate.
  • Trie Query Servers: Stateless servers that each hold a full copy of the in-memory trie (or a shard for very large tries). On receiving a request, they traverse the trie to the prefix node and return the pre-computed top-5 suggestions. Lookup is O(prefix_length) — typically 3-20 character traversals.
  • Query Log Stream (Kafka): Every search query executed on the search engine is logged to Kafka with metadata (query text, timestamp, user_id, language, location). This is the raw input for the data gathering pipeline.
  • Log Aggregator (MapReduce / Spark / Flink): Processes query logs to compute frequency counts per query. Runs as a batch job (weekly full aggregation) and a streaming job (hourly incremental updates for trending queries).
  • Trie Builder: Reads aggregated frequencies from the database, constructs the trie, pre-computes top-K at each node, applies content filters, and serializes the trie to a binary snapshot file stored in S3/HDFS.
  • Trie Snapshot (S3): The serialized trie file (~3 GB) is stored in object storage. Query servers download the latest snapshot on startup or when a new version is published. Blue-green deployment ensures zero-downtime updates.
Why Separate Data Gathering from Query Serving? The data gathering pipeline is a batch/streaming system that processes billions of log entries, runs MapReduce jobs, and rebuilds a multi-gigabyte trie. It is CPU-intensive, runs on a schedule, and tolerates minutes of latency. The query service is a real-time system that must respond in under 100ms at 460K QPS. Coupling these two would mean the query servers are doing heavy computation while trying to serve requests — a recipe for latency spikes. By separating them, the trie builder produces an immutable snapshot, and query servers simply load and serve it. Updates are atomic: swap the old trie for the new one.

6. Deep Dive

6a. Trie Data Structure — How It Works

A trie (pronounced “try”, from retrieval) is a tree-like data structure where each node represents a single character. The path from the root to any node spells out a prefix. Tries are the canonical data structure for autocomplete because prefix lookup is O(prefix_length), regardless of how many queries are stored.

top-3: try(20), true(15), tree(10)"] O2["Node 'o' (prefix 'to')

Time Complexity Summary: Building the trie is O(N × L) where N = number of queries and L = average query length. Computing top-K at each node is O(nodes × K) using a bottom-up merge. Lookup at query time is O(P) where P = prefix length — just follow the character edges and return the cached top-K. This is the key insight: we do expensive computation once during the build phase, so the query path is trivially fast.

Interview Tip: Mention the dual-cadence update strategy: “We run a full trie rebuild weekly using batch MapReduce over all historical query logs. Adaptive Debounce: A fixed 200ms debounce works well for fast typists but feels sluggish for slow typists who pause between characters. An adaptive approach adjusts the debounce interval based on typing speed: if the user is typing quickly (inter-keystroke interval < 100ms), use a longer debounce (300ms). If typing slowly (> 300ms between keys), use a shorter debounce (100ms) or send immediately. This balances responsiveness with request reduction.

6g. Filter Layer — Removing Offensive Content

Autocomplete suggestions are highly visible — they appear before the user even finishes typing. Showing offensive, harmful, or inappropriate suggestions is a significant brand and legal risk. A multi-layered filter ensures problematic content never reaches users.

Why Filtering Matters: In 2013, Google’s autocomplete suggested offensive completions for searches about certain ethnic groups, leading to lawsuits in multiple countries. Bing faced similar issues. Autocomplete suggestions carry an implicit endorsement — users perceive them as “Google thinks I should search for this.” A robust filtering pipeline is not optional; it is a legal and reputational necessity. Always mention this in interviews to show you think beyond pure engineering.

7. Trade-offs

Decision Option A Option B Recommendation
Trie vs. Inverted Index Trie: Purpose-built for prefix matching. O(prefix_length) lookup. Pre-computed top-K at each node. Compact in memory (~3 GB for 5M queries). Does not support substring or fuzzy matching. Inverted Index (Elasticsearch): Supports prefix, substring, fuzzy, and phonetic matching. More flexible but heavier infrastructure. Slower for pure prefix queries (~5-10ms vs. <1ms for trie). Requires a search cluster. Use a trie for the primary autocomplete path. The access pattern is exclusively prefix-based, and the trie’s O(prefix_length) lookup with pre-computed top-K is unbeatable for latency. If substring or fuzzy matching is needed (e.g., “recipes dinner” matching “dinner recipes”), add an inverted index as a secondary fallback, not the primary path.
Real-time vs. Batch Updates Batch only (weekly rebuild): Simple pipeline. Full trie rebuild from aggregated data. Consistent, well-tested snapshots. Stale data — trending topics take up to a week to appear. Real-time streaming: Flink/Spark Streaming processes query logs continuously. Trie updated every few minutes. Complex infrastructure. Risk of noisy/spammy data entering the trie before filtering. Use a hybrid approach: weekly full rebuild for the base trie + hourly incremental patches for trending queries. The hourly job only updates nodes with significant frequency changes (>10% delta), keeping patches small. This balances freshness (trending topics appear within 1 hour) with stability (base trie is well-filtered and tested).
In-Memory Trie vs. Disk-Based Trie In-memory: Sub-millisecond lookups. Entire trie loaded into RAM. Limited by server memory (typically 64-256 GB). Requires full reload on restart. Disk-based (memory-mapped file): Trie stored as a memory-mapped file. OS manages page caching. Can handle tries larger than RAM. Slightly higher latency for cold pages (~1-5ms). Use in-memory for the primary query path. At ~3 GB, the trie fits easily in RAM. The sub-millisecond lookup time is critical for meeting the 100ms end-to-end latency budget (which includes network, CDN, and client rendering time). Use memory-mapped files only if the trie grows beyond single-server memory (50M+ queries across all languages).
Global vs. Personalized Ranking Global only: Same suggestions for all users. Highly cacheable (CDN absorbs 60%+ traffic). Simple infrastructure. Misses user-specific relevance. Personalized: Suggestions tailored to each user’s history. Much better relevance. Destroys cache efficiency (each user gets unique results). Requires per-user storage and lookup. Use client-side blending: server returns global top-K (cacheable), client merges with local search history stored on the device. This preserves CDN cache efficiency while providing personalization. For logged-in users on premium products, consider server-side personalization with a per-user Redis lookup (+2-5ms latency).
Interview Tip: When discussing the trie vs. inverted index trade-off, connect it to the access pattern: “Our FR specifies prefix-based matching, and our NFR requires sub-100ms latency at 460K QPS. A trie gives us O(prefix_length) lookups with pre-computed results — effectively O(1) after reaching the node. Elasticsearch would add 5-10ms per query plus cluster management overhead.
