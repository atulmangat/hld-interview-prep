Consistent Hashing

Understand consistent hashing — the foundational technique that enables distributed systems to add and remove nodes with minimal data movement, powering everything from distributed caches to NoSQL databases.

Medium Core Infrastructure Asked at: Amazon, Facebook, Netflix

1. The Problem

In distributed systems, we frequently need to distribute data (cache entries, database rows, files) across multiple servers. The naive approach is modular hashing: compute hash(key) % N where N is the number of servers. This works — until the number of servers changes.

Why Naive Modular Hashing Fails

Consider 4 servers (S0–S3) and 8 keys. Using hash(key) % 4:

Key hash(key) hash % 4 (4 servers) hash % 5 (5 servers) Remapped?
user_1 14 S2 S4 Yes
user_2 27 S3 S2 Yes
user_3 8 S0 S3 Yes
user_4 33 S1 S3 Yes
user_5 20 S0 S0 No
user_6 11 S3 S1 Yes
user_7 5 S1 S0 Yes
user_8 36 S0 S1 Yes
The Core Problem: Adding just 1 server (4 → 5) remapped 7 out of 8 keys (87.5%). In a real system with millions of cached entries, this means nearly every cache lookup becomes a miss — causing a cache avalanche that can bring down the backend database.

The Impact at Scale

  • Cache avalanche: Nearly all cache entries become invalid simultaneously. Every request hits the database, potentially causing cascading failure.
  • Data migration storms: In a distributed database, most data partitions need to be moved between nodes — saturating the network and degrading performance for hours.
  • Downtime during scaling: Adding or removing a single server requires a coordinated, system-wide rebalancing operation rather than a localized adjustment.

The fundamental issue: hash % N creates a dependency on N. When N changes, nearly every key maps to a different server. We need a scheme where changing N only affects a small fraction of keys — ideally K/N keys, where K is the total number of keys.

Interview Tip: Always start by explaining why consistent hashing exists before diving into how it works. Demonstrating the failure of naive hashing with a concrete numeric example shows the interviewer you understand the motivation, not just the mechanism.

2. Basic Consistent Hashing

Consistent hashing, introduced by Karger et al. (1997), solves the remapping problem by using a hash ring instead of modular arithmetic. Both servers and keys are mapped onto the same circular hash space.

The Hash Ring Concept

  1. Define the ring: The hash space is a circle from 0 to 232−1 (or any large range). The value wraps around: position 232 is the same as position 0.
  2. Place servers on the ring: Hash each server's identifier (e.g., IP address or hostname) to get its position on the ring. position = hash(server_id)
  3. Place keys on the ring: Hash each key to get its position. position = hash(key)
  4. Map keys to servers: For each key, walk clockwise around the ring until you hit the first server. That server owns the key.

Adding a Server

When a new server S3 is added to the ring, it is placed at its hash position. Only the keys that fall between the new server and its predecessor (counter-clockwise neighbor) need to be remapped — they now belong to S3 instead of the server that was previously their clockwise neighbor.

Key Remapping: The Math

With K keys and N servers, adding or removing a server only remaps approximately:

Keys remapped ≈ K / N

Example: 1,000,000 keys across 10 servers
  Naive hash % N:        ~900,000 keys remapped (90%)
  Consistent hashing:    ~100,000 keys remapped (10%)
Why K/N? Each server owns approximately 1/N of the ring. When a new server is added, it takes over a portion of the ring from its clockwise neighbor. On average, that portion is 1/N of the total ring — so approximately K/N keys move. This is the theoretical minimum for any scheme that maintains balance.

3. Virtual Nodes (Vnodes)

The Problem with Basic Consistent Hashing

With only a few physical servers on the ring, the distribution of keys is highly uneven. Servers are placed at arbitrary hash positions, creating arcs of vastly different sizes. Some servers end up owning a disproportionately large portion of the ring while others own very little.

The Solution: Virtual Nodes

Instead of placing each physical server at a single point on the ring, map each physical server to multiple virtual nodes (typically 100–200 per server). Each virtual node is placed at a different position on the ring by hashing variants of the server identifier:

// Generate virtual nodes for server "S0"
for i in 0..149:
    position = hash("S0#" + i)
    ring.add(position → S0)

// Server S0 now has 150 points on the ring
// Repeat for S1, S2, etc.

Handling Heterogeneous Servers

Virtual nodes also solve the problem of servers with different capacities. Assign more virtual nodes to more powerful servers:

Server A (16 GB RAM):  100 virtual nodes
Server B (32 GB RAM):  200 virtual nodes  ← 2x the vnodes, handles ~2x the keys
Server C (64 GB RAM):  400 virtual nodes  ← 4x the vnodes, handles ~4x the keys
Interview Tip: Virtual nodes are the single most important improvement to basic consistent hashing. Always mention them proactively — it shows you understand the practical limitations of the basic algorithm and know the standard production solution.

4. Hash Functions

The choice of hash function directly affects the uniformity of key distribution on the ring and the performance of lookups. A good hash function for consistent hashing must produce uniformly distributed outputs and be fast to compute.

Hash Function Comparison

Hash Function Output Size Speed (ops/sec) Distribution Quality Cryptographic? Notes
MD5 128 bits ~300M Excellent Yes (broken) Widely used in legacy systems. Good distribution but slower than non-crypto alternatives. Used by Memcached’s ketama algorithm.
SHA-1 160 bits ~250M Excellent Yes (broken) Slightly slower than MD5. Overkill for consistent hashing since we don’t need cryptographic properties.
MurmurHash3 32/128 bits ~2B Excellent No Fast, excellent distribution. Used by Apache Cassandra. The go-to choice for most consistent hashing implementations.
xxHash 32/64/128 bits ~5B Excellent No Fastest general-purpose hash. Excellent avalanche properties. Ideal for high-throughput systems.
FNV-1a 32/64 bits ~1.5B Good No Simple implementation, decent speed. Slightly worse distribution than Murmur/xxHash. Used in some older systems.
Key Insight: For consistent hashing, you do not need a cryptographic hash function. Cryptographic hashes (MD5, SHA) are designed to resist preimage attacks and collisions — properties irrelevant for load distribution. Non-cryptographic hashes like MurmurHash3 and xxHash provide equally good distribution at 5–10x the speed.

What Makes a Good Hash for Consistent Hashing?

  • Uniform distribution: Every bit of the output should be equally likely to be 0 or 1, regardless of input patterns. This ensures keys are spread evenly across the ring.
  • Avalanche effect: A small change in input (e.g., "key1" vs "key2") should produce a drastically different output. This prevents clustering of similar keys.
  • Speed: The hash function is called for every key lookup. At millions of operations per second, even nanosecond differences matter.
  • Determinism: The same input must always produce the same output, across all machines and restarts.

5. Real-World Usage

Consistent hashing is a foundational building block in many large-scale distributed systems. Here are the most notable real-world applications:

Amazon DynamoDB

DynamoDB uses consistent hashing to partition data across storage nodes. Each table’s partition key is hashed to determine which storage partition owns the data. When partitions split or merge, only the affected key range moves — the rest of the table is untouched. Described in the original Dynamo paper (2007).

Apache Cassandra

Cassandra uses consistent hashing with virtual nodes (vnodes) as its core data distribution mechanism. Each node owns multiple token ranges on the ring. By default, Cassandra assigns 256 vnodes per physical node (configurable via num_tokens). Uses MurmurHash3 as its default partitioner.

Discord

Discord uses consistent hashing to route messages to the correct guild (server) process. When a user sends a message, the guild ID is hashed to determine which backend process handles it. This allows Discord to scale to millions of concurrent guilds while ensuring all messages for a guild are processed by the same node.

Akamai CDN

Akamai (co-founded by Karger, one of the consistent hashing inventors) uses it to map content URLs to edge servers. When a user requests a resource, the URL is hashed to find the nearest edge server that caches it. Adding or removing edge servers only redirects a fraction of URLs, preventing cache stampedes across the CDN.

Memcached (Ketama)

The Ketama algorithm is a consistent hashing implementation for Memcached clients. It distributes cache keys across a pool of Memcached servers. When a server is added or removed, only ~1/N of the keys are remapped, avoiding the thundering herd problem that would occur with naive hash % N. Uses MD5 with 160 virtual nodes per server.

Other Notable Uses

  • Riak: Dynamo-inspired key-value store using consistent hashing with a fixed 64-partition ring.
  • Nginx: upstream module supports consistent hashing for load balancing backend servers.
  • HAProxy: Consistent hashing mode for sticky session routing.
  • Apache Kafka: Consumer group rebalancing uses a similar concept (though not classical consistent hashing).
Pattern: Consistent hashing appears wherever you need to distribute data or work across a dynamic set of nodes — caches, databases, CDNs, load balancers, and message routers. If the set of nodes can change at runtime, consistent hashing (or a variant) is almost certainly involved.

6. Implementation Details

Data Structure Choices

The core operation is: given a key’s hash position on the ring, find the next server position clockwise. This is a successor query — find the smallest ring position that is ≥ the key’s position.

Data Structure Lookup Add/Remove Node Memory Notes
Sorted Array + Binary Search O(log N) O(N) — requires shifting elements Compact, cache-friendly Best for read-heavy workloads where nodes rarely change. Simple to implement.
Balanced BST (TreeMap) O(log N) O(log N) Higher per-node overhead (pointers) Best when nodes are added/removed frequently. Java’s TreeMap.ceilingEntry() gives the successor directly.
Skip List O(log N) O(log N) Moderate Concurrent-friendly. Good for multi-threaded implementations.

Here, N is the total number of points on the ring (physical servers × virtual nodes per server). With 100 physical servers and 150 vnodes each, N = 15,000 — binary search over 15K entries is extremely fast.

Pseudocode Implementation

class ConsistentHashRing:
    ring: SortedMap<Integer, String>   // position → server_id
    vnodes_per_server: int = 150

    function addServer(server_id):
        for i in 0..vnodes_per_server - 1:
            position = hash(server_id + "#" + i)
            ring.put(position, server_id)

    function removeServer(server_id):
        for i in 0..vnodes_per_server - 1:
            position = hash(server_id + "#" + i)
            ring.remove(position)

    function getServer(key):
        if ring.isEmpty():
            return null
        position = hash(key)
        // Find the first server position >= key position (clockwise walk)
        entry = ring.ceilingEntry(position)
        if entry is null:
            // Wrap around to the first server on the ring
            entry = ring.firstEntry()
        return entry.value   // server_id

Handling Replication

In distributed databases, each key is replicated to N nodes for fault tolerance. To find the N replica nodes, walk clockwise from the key’s position and collect N distinct physical servers (skipping virtual nodes that belong to an already-selected physical server):

function getReplicaNodes(key, replica_count):
    position = hash(key)
    replicas = []
    seen_servers = Set()

    // Walk clockwise from the key's position
    for entry in ring.tailMap(position):
        if entry.value not in seen_servers:
            replicas.add(entry.value)
            seen_servers.add(entry.value)
        if replicas.size() == replica_count:
            return replicas

    // Wrap around if we haven't found enough replicas
    for entry in ring.headMap(position):
        if entry.value not in seen_servers:
            replicas.add(entry.value)
            seen_servers.add(entry.value)
        if replicas.size() == replica_count:
            return replicas

    return replicas  // fewer replicas than requested (not enough servers)

Replication Pitfall: When collecting replica nodes, you must skip virtual nodes belonging to the same physical server. If you naively take the next N positions on the ring, you might select 3 virtual nodes that all map to the same physical server — giving you 1 actual replica instead of 3. Always track distinct physical servers.

Ring Membership Management

In production systems, the ring membership (which servers are on the ring) must be consistent across all clients. Common approaches:

  • ZooKeeper / etcd: Store the server list in a coordination service. Clients watch for changes and rebuild their local ring copy. Used by Kafka, HBase.
  • Gossip protocol: Servers communicate membership changes peer-to-peer. Eventually consistent but highly available. Used by Cassandra, DynamoDB.
  • Configuration service: A centralized config service (e.g., Consul) maintains the ring and pushes updates to clients.

7. Trade-offs

Decision Option A Option B Recommendation
Virtual node count Few vnodes (10–50): less memory, faster ring operations, but uneven load distribution (~15–25% std dev). Many vnodes (150–200): more memory and slightly slower ring rebuilds, but near-uniform distribution (~5–10% std dev). Use 100–200 vnodes per server for production. The memory overhead is negligible (a few MB for thousands of servers) compared to the benefit of balanced load.
Hash function Cryptographic (MD5, SHA-1): excellent distribution, well-understood, but 5–10x slower. Non-cryptographic (MurmurHash3, xxHash): equally good distribution, much faster. Use MurmurHash3 or xxHash. Cryptographic properties are unnecessary for consistent hashing, and the speed difference matters at high throughput.
Data structure Sorted array + binary search: compact, cache-friendly, but O(N) insert/delete. Balanced BST (TreeMap): O(log N) insert/delete, but higher memory overhead. Sorted array if nodes change rarely (most caching scenarios). TreeMap if nodes change frequently (auto-scaling clusters).
Handling hotspots Ignore: simple but some keys (e.g., celebrity user profiles) create uneven load regardless of ring balance. Hotspot mitigation: replicate hot keys to multiple servers, or use a secondary hash to split hot keys across sub-partitions. For most systems, vnodes handle balance well enough. For extreme hotspots, add an application-level caching layer or split hot keys explicitly.
Rebalancing strategy Immediate: move all affected keys as soon as a node joins/leaves. Consistent but causes a burst of data transfer. Gradual: transfer keys in the background over minutes/hours. Less disruptive but temporarily inconsistent. Gradual rebalancing with read-repair. Serve stale data from the old node while transferring to the new node. Cassandra and DynamoDB use this approach.
Ring consistency Strong consistency (ZooKeeper/etcd): all clients see the same ring at the same time. Requires coordination service. Eventual consistency (gossip): clients may temporarily disagree on ring membership. Simpler, more available. Eventual consistency for most distributed databases (Cassandra, DynamoDB). Strong consistency when routing correctness is critical (e.g., distributed locks).
Bounded vs Unbounded loads Standard consistent hashing: a node can receive arbitrarily more load than average if keys are skewed. Bounded-load consistent hashing (Google, 2017): caps each node at (1 + ε) × average load. Overloaded nodes redirect to the next node on the ring. Use bounded-load variant when strict load balancing is required (e.g., load balancing HTTP requests). Standard is fine for data partitioning where slight imbalance is tolerable.
Interview Tip: Discussing trade-offs is where you differentiate yourself. Mentioning bounded-load consistent hashing (Google’s 2017 paper) or the gossip-vs-ZooKeeper decision for ring membership shows depth beyond the textbook explanation.
