Design a News Feed System

Design a scalable news feed system that aggregates and delivers a personalized stream of posts from friends and followed accounts — supporting text, images, and video content, real-time updates, engagement actions (likes, comments), and intelligent ranking at the scale of hundreds of millions of daily active users.

Hard Social & Feed Asked at: Meta, Twitter, LinkedIn

1. Requirements

Functional Requirements

  • Publish posts — Users can create and publish posts containing text, images, or video. Posts are visible to their friends or followers.
  • Personalized feed — Users see a feed composed of posts from people they follow or are friends with, ordered by relevance or recency.
  • Multi-media support — Posts can contain plain text, images (up to 10 per post), or video (short-form and long-form). Media is stored separately and served via CDN.
  • Likes and comments — Users can like and comment on posts. Like counts and top comments are displayed inline in the feed.
  • Pagination — The feed supports infinite scroll with cursor-based pagination. Users can scroll back through older posts without missing or duplicating content.
  • Follow/friend model — Support both symmetric (friend) and asymmetric (follow) relationships. A user’s feed includes posts from all connections.

Non-Functional Requirements

  • Low latency: Feed generation must complete in under 500ms (p99). Users expect the feed to load instantly on app open.
  • Massive scale: Support 500 million daily active users (DAU), each with an average of 300 friends/followed accounts.
  • Eventual consistency: It is acceptable for a new post to take a few seconds to appear in all followers’ feeds. Availability is prioritized over strict consistency.
  • High availability: The system must be available 99.99% of the time. Feed reads should never fail, even if the ranking service is degraded (fall back to chronological).
  • Read-heavy: The read-to-write ratio is approximately 100:1. The architecture must be optimized for fast reads.
  • Global distribution: Users are worldwide. Feed data must be served from geographically close data centers to minimize latency.
Interview Tip: Start by clarifying the social graph model. “Is this a symmetric friendship model (like Facebook) or an asymmetric follow model (like Twitter/Instagram)?” This fundamentally affects the fan-out strategy. In a follow model, celebrities with millions of followers create a massive write amplification problem that drives the entire architecture. Also clarify: “Is the feed chronological or ranked?” — ranked feeds require an ML ranking service, which adds significant complexity.

2. Capacity Estimation

Assumptions

Parameter Value Notes
Daily Active Users (DAU) 500 million Facebook-scale system
Average friends/followed per user 300 Mix of close friends and acquaintances
Posts per user per day 5 (among active posters) ~10% of users post daily; rest are consumers
Feed opens per user per day 10 Users check their feed multiple times daily
Posts per feed page 20 Each scroll loads 20 posts
Average post size ~1 KB (metadata) Text + metadata; media stored separately on CDN

Throughput Calculation

Write path (post creation):
  Active posters       = 500M × 10% = 50M users
  Posts per day         = 50M × 5 = 250M posts/day
  Posts per second      = 250M / 86,400 ≈ 2,900 posts/sec
  Peak (5x)            ≈ 14,500 posts/sec

Read path (feed requests):
  Feed opens per day   = 500M × 10 = 5 billion reads/day
  Reads per second     = 5B / 86,400 ≈ 58,000 reads/sec
  Peak (3x)            ≈ 174,000 reads/sec

Fan-out (push model):
  Each post fans out to avg 300 followers
  Fan-out writes/sec   = 2,900 × 300 = 870,000 cache writes/sec
  Peak fan-out          ≈ 4.35M cache writes/sec

Storage Calculation

Post metadata storage:
  Per post             = ~1 KB (text, user_id, timestamp, media_urls)
  Daily                = 250M × 1 KB = 250 GB/day
  Yearly               = 250 GB × 365 = ~91 TB/year

Feed cache (Redis):
  Per user feed cache  = 500 post IDs × 8 bytes = 4 KB per user
  Total feed cache     = 500M × 4 KB = 2 TB
  With replication (3x)= 6 TB Redis cluster

Media storage (CDN/S3):
  ~20% of posts have images (avg 500 KB per post)
  ~5% of posts have video (avg 50 MB per post)
  Image storage/day    = 50M × 500 KB = 25 TB/day
  Video storage/day    = 12.5M × 50 MB = 625 TB/day
Key Insight: The numbers reveal why news feed is a hard problem. At 58K reads/sec, the read path must be served from cache — hitting the database for every feed request is impossible. The fan-out write rate of 870K/sec is manageable for Redis, but a single celebrity post to 10M followers would generate 10M cache writes, creating a thundering herd problem. This is the core tension that drives the hybrid fan-out architecture.

Cursor-Based Pagination is Essential: Offset-based pagination (?page=2&limit=20) breaks in a news feed because new posts are constantly being inserted at the top. If a user is on page 2 and 5 new posts arrive, offset-based pagination would shift all posts down, causing the user to see duplicates. Cursor-based pagination (?cursor=last_seen_post_timestamp) anchors to a specific point in time, ensuring stable results regardless of new insertions.

4. Data Model

users

Core user table storing profile information.

Column Type Description
user_id UUID (PK) Unique user identifier
username VARCHAR (unique) Display handle (e.g., @janesmith)
name VARCHAR Full display name
avatar_url VARCHAR Profile picture URL on CDN
follower_count INT Denormalized follower count (for celebrity detection)
is_celebrity BOOLEAN True if follower_count > threshold (e.g., 100K)
created_at TIMESTAMP Account creation time

posts

Stores all published posts. Sharded by user_id for write locality (all posts by a user on the same shard).

Column Type Description
post_id UUID (PK) Unique post identifier (Snowflake ID for time-ordering)
user_id UUID (FK, indexed) Author of the post
content TEXT Post text content (max 5,000 chars)
media_urls JSON Array of media objects [{type, url, width, height}]
visibility ENUM friends, public, private
likes_count INT Denormalized like count (updated async)
comments_count INT Denormalized comment count
created_at TIMESTAMP (indexed) Post creation time

friendships

Stores the social graph. For symmetric friendships, store two rows (A→B and B→A). For asymmetric follows, store one row per follow.

Column Type Description
user_id UUID (PK, part 1) The user who follows
friend_id UUID (PK, part 2) The user being followed
relationship_type ENUM friend, follow, close_friend
created_at TIMESTAMP When the relationship was established

feed_cache (Redis)

Pre-computed feed stored in Redis as a sorted set per user. This is the primary data structure that powers fast feed reads.

Key / Field Type Description
feed:{user_id} Sorted Set (key) Redis key for the user’s feed
post_id Member The post ID stored in the sorted set
timestamp / score Score Post timestamp (or ranking score) used for ordering 
Redis operations for feed:

  # Add a post to a user's feed (fan-out on write)
  ZADD feed:u_98765 1713091800 post_7f3a9b2c

  # Retrieve top 20 posts (most recent first)
  ZREVRANGE feed:u_98765 0 19

  # Cursor-based pagination (posts older than cursor timestamp)
  ZREVRANGEBYSCORE feed:u_98765 1713091799 -inf LIMIT 0 20

  # Trim feed to keep only latest 500 posts (memory management)
  ZREMRANGEBYRANK feed:u_98765 0 -501
Graph DB for Social Connections: At scale, the friendships table becomes a bottleneck for queries like “get all followers of user X” or “find mutual friends.” Companies like Facebook use a specialized graph database (TAO) that stores the social graph in a distributed, cache-friendly format. For interviews, mentioning a graph database (Neo4j, or a custom solution like TAO) for the social graph shows depth. The posts and feed cache remain in relational/Redis stores.

5. High-Level Design

The news feed system has two distinct data flows: the write path (publishing a post and distributing it to followers) and the read path (retrieving a user’s personalized feed). The architecture is optimized for the read path since reads outnumber writes 100:1.

System Architecture

Key Components

  • Post Service: Stateless API that validates post content, stores it in the Posts DB, uploads media to object storage (S3), and enqueues a fan-out job to the message queue.
  • Fan-out Service: Consumes from the message queue, looks up the author’s followers in the social graph, and writes the post ID to each follower’s feed cache in Redis. Skips fan-out for celebrity users (handled at read time).
  • Feed Service: Reads the user’s pre-computed feed from Redis, hydrates post details from the Post Cache, merges in celebrity posts (pull model), applies ranking, and returns the paginated result.
  • Feed Cache (Redis): Sorted sets storing post IDs per user, ordered by timestamp or ranking score. This is the critical hot path — all feed reads hit Redis first.
  • Ranking Service: ML model that scores and re-ranks feed items based on relevance signals (recency, engagement, relationship strength, content type).
Why Two Separate Paths? The write path and read path are decoupled by design. The Post Service returns 201 Created immediately without waiting for fan-out to complete. Fan-out happens asynchronously via a message queue. This means a user’s post may take 1–5 seconds to appear in all followers’ feeds (eventual consistency), but the publishing experience is instant. This trade-off is acceptable because users rarely check if their post appeared in a specific friend’s feed immediately.

6. Deep Dive

6a. Fan-out on Write (Push Model)

In the push model, when a user publishes a post, the system immediately pre-computes the feed for every follower by writing the post ID into each follower’s feed cache. This makes reads extremely fast (just read from cache) at the cost of write amplification.

graph TD subgraph Write Time UA[User A publishes post_123] --> FOS[Fan-out Service] FOS -->|Get followers of A| FL[Followers: B C D E] FOS -->|ZADD feed:B| FB[Feed Cache B] FOS -->|ZADD feed:C| FCa[Feed Cache C] FOS -->|ZADD feed:D| FD[Feed Cache D] FOS -->|ZADD feed:E| FE[Feed Cache E] end subgraph Read Time - User B opens feed UB[User B] --> FSV[Feed Service] FSV -->|ZREVRANGE feed:B 0 19| RD[Redis - Pre-computed Feed] RD -->|1ms latency| RES[Return post_123 post_119 post_115 ...] end

Advantages

  • Extremely fast reads — feed is pre-computed in cache, just a single ZREVRANGE call.
  • Simple read path — no complex aggregation or merging at read time.
  • Real-time updates — new posts appear in followers’ feeds within seconds.

The Celebrity Problem

graph TD CEL[Celebrity publishes post - 10M followers] --> FOS[Fan-out Service] FOS -->|ZADD| F1[Feed Cache follower_1] FOS -->|ZADD| F2[Feed Cache follower_2] FOS -->|ZADD| F3[Feed Cache follower_3] FOS -.->|...| FN[Feed Cache follower_10M] FOS --> PROB[10M Redis writes for ONE post] PROB --> TIME[17 MINUTES to fan out] PROB --> HOT[Hotspot on fan-out workers] PROB --> WASTE[Wasted writes - 80 pct inactive users] PROB --> MEM[Memory waste in 10M feed caches]
This is the #1 insight interviewers want to hear. The push model works beautifully for normal users (avg 300 followers), but breaks catastrophically for celebrities. A single Cristiano Ronaldo post (600M followers on Instagram) would require 600 million cache writes. This is why no production system uses pure push — it always requires a hybrid approach.

6b. Fan-out on Read (Pull Model)

In the pull model, no pre-computation happens at write time. When a user opens their feed, the system fetches recent posts from all friends/followed accounts on the fly, merges them, and returns the result.

graph TD subgraph Read Time - User B opens feed UB[User B follows 300 accounts] --> FS[Feed Service] FS -->|Query posts from A| DBA[Posts DB - User A] FS -->|Query posts from C| DBC[Posts DB - User C] FS -->|Query posts from D| DBD[Posts DB - User D] FS -.->|300 parallel queries| DBN[Posts DB - User N] DBA --> MRG[Merge 6000 candidates] DBC --> MRG DBD --> MRG DBN --> MRG MRG --> SORT[Sort by timestamp or score] SORT --> RET[Return top 20 - Latency 200 to 800ms] end subgraph Write Time - User A publishes UA[User A] --> PSV[Post Service] PSV -->|Single INSERT| DB[Posts DB] PSV --> NOTE[No fan-out - No follower lookup - Instant] end

Advantages

  • No write amplification — publishing a post is a single DB write regardless of follower count.
  • No wasted computation — feed is only computed for users who actually open the app.
  • No celebrity problem — a celebrity post is just one row in the DB, not 10M cache writes.

Disadvantages

  • Slow reads — 300 parallel queries + merge + sort on every feed open. Hard to hit <500ms at scale.
  • High read-time compute cost — at 58K feed reads/sec, this means 17.4M DB queries/sec just for feed generation.
  • Difficult to rank — ranking requires all candidate posts to be available, which means fetching more data than needed.

6c. Hybrid Approach (The Real-World Solution)

This is the approach used by Facebook, Twitter/X, and Instagram in production. It combines push for normal users with pull for celebrities, getting the best of both worlds.

graph TD subgraph Classification PUB[User Publishes Post] --> CHK[Check Follower Count] CHK -->|Below Threshold| PUSH[PUSH MODEL - Fan-out on Write] CHK -->|Above Threshold| PULL[PULL MODEL - Fan-out on Read] PUSH --> WFC[Write post_id to each followers feed cache] PULL --> STO[Just store the post - No fan-out] THR[Celebrity Threshold approx 10K to 100K followers] end subgraph Read Path - Merging Push and Pull UB[User B opens feed - 295 normal plus 5 celebrities] --> FS[Feed Service] FS --> S1[Step 1 - Read push cache ZREVRANGE - 1ms] FS --> S2[Step 2 - Fetch celebrity posts - 5 parallel queries - 5ms] S1 --> S3[Step 3 - Merge push plus pull results] S2 --> S3 S3 --> S4[Step 4 - Return top 20 - Total 10 to 50ms] end

Push Model (Normal Users)

  • Applied to ~99% of users (those with <100K followers)
  • Fan-out to 300 followers = 300 Redis writes
  • Completes in milliseconds
  • Feed reads are a single cache lookup

Pull Model (Celebrities)

  • Applied to ~1% of users (those with >100K followers)
  • Zero fan-out writes at publish time
  • Posts fetched at read time from post cache
  • Merged with push results before ranking

Hybrid Result

  • Eliminates the celebrity problem entirely
  • Read latency stays under 50ms (p99)
  • Write amplification is bounded and predictable
  • Used by Meta, Twitter/X, LinkedIn in production
Interview Tip: The hybrid approach is the KEY insight that separates a good answer from a great one. Walk through the progression: “We start with push for simplicity and fast reads. Then we identify the celebrity problem. Pure pull is too slow. So we combine both: push for the 99% of users with manageable follower counts, pull for the 1% who are celebrities. At read time, we merge both sources and rank.” This demonstrates systematic problem-solving.

6d. Feed Ranking

Modern feeds are not purely chronological. They use ML-based ranking to maximize user engagement by surfacing the most relevant content. This is what makes Facebook’s and Instagram’s feeds feel “smart.”

Chronological vs. Ranked Feed

Chronological Feed

  • Posts ordered by timestamp (newest first)
  • Simple to implement (just sort by created_at)
  • Predictable for users — they know what to expect
  • Problem: important posts get buried by high-volume posters
  • Used by: Twitter (as an option), Mastodon, RSS readers

Ranked Feed (ML-Based)

  • Posts ordered by a relevance score computed by an ML model
  • Maximizes engagement (likes, comments, time spent)
  • Surfaces posts from close friends over acquaintances
  • Complex to build, requires feature engineering and model training
  • Used by: Facebook, Instagram, LinkedIn, TikTok

Ranking Signal Features

Signal Category Features Weight
Recency Time since post was created. Exponential decay function — a 1-hour-old post scores higher than a 12-hour-old post. High
Engagement Number of likes, comments, shares the post has received. High engagement signals quality content. High
Relationship Strength How often the viewer interacts with the author (messages, profile visits, mutual likes). Close friends rank higher. Very High
Content Type User’s historical preference for content types (video vs. text vs. images). If user watches lots of videos, video posts rank higher. Medium
Content Freshness Has the user already seen this post? Previously seen posts are demoted or hidden. High
Author Activity How frequently the author posts. Posts from infrequent posters may be boosted to ensure visibility. Low

6e. Caching Strategy

The news feed is one of the most cache-intensive systems in all of software engineering. Multiple caching layers work together to ensure sub-100ms feed loads.

graph LR CC[Client Cache - On-device - TTL 5min - 30 pct hit] --> CDN[CDN - CloudFront Akamai - TTL 24h - 60 pct hit] CDN --> AC[App Cache - Local in-memory - TTL 5min - 95 pct hit] AC --> FC[Feed Cache - Redis Sorted Sets - No TTL - 99 pct hit] FC --> DB[Posts DB - Source of Truth] CC -.->|Reduces network requests| CDN CDN -.->|Offloads 60 pct bandwidth| AC AC -.->|Reduces Redis reads 10x| FC FC -.->|Updated on fan-out| DB

Cache Invalidation Strategy

  • Feed cache: Updated on write (fan-out adds new post IDs). No TTL-based expiration — the cache is the primary read source. Stale entries are trimmed by keeping only the latest 500 posts per user (ZREMRANGEBYRANK).
  • Post cache: Write-through cache. When a post is created or updated (e.g., like count changes), the cache is updated immediately. TTL of 5 minutes as a safety net.
  • User profile cache: Cache-aside pattern. Read from cache first; on miss, read from DB and populate cache. TTL of 15 minutes. Invalidated on profile update.
  • Engagement counts: Updated asynchronously via a counter service. Counts in the feed may be slightly stale (showing “142 likes” when the real count is 145). This is acceptable for a feed view — exact counts are shown on the post detail page.

6f. Pagination — Cursor-Based vs. Offset-Based

Pagination strategy is critical for a news feed because new content is constantly being inserted at the top of the list.

Offset-Based (Bad for Feeds)

GET /feed?offset=20&limit=20

Problem: New posts shift all offsets

Time T1: Feed = [A, B, C, D, E, ...]
  User sees page 1: [A, B, C, D, E]
  (offset=0, limit=5)

Time T2: New posts X, Y inserted
  Feed = [X, Y, A, B, C, D, E, ...]
  User requests page 2: offset=5
  Gets: [C, D, E, F, G]
  
  User sees C, D, E AGAIN (duplicates!)
  User never sees A, B (skipped!)

Cursor-Based (Correct for Feeds)

GET /feed?cursor=post_E_timestamp&limit=5

Cursor anchors to a specific point

Time T1: Feed = [A, B, C, D, E, ...]
  User sees page 1: [A, B, C, D, E]
  cursor = E.timestamp

Time T2: New posts X, Y inserted
  Feed = [X, Y, A, B, C, D, E, ...]
  User requests page 2: cursor=E.ts
  Gets: [F, G, H, I, J]
  
  No duplicates! No skipped posts!
  X, Y will appear when user scrolls
  back to top (pull-to-refresh).
Cursor implementation with Redis sorted sets:

  # Page 1: Get the 20 most recent posts
  ZREVRANGEBYSCORE feed:u_98765 +inf -inf LIMIT 0 20
  → Returns: [post_A (score: 1000), ..., post_T (score: 981)]
  → next_cursor = base64encode({"score": 981, "post_id": "post_T"})

  # Page 2: Get the next 20 posts after the cursor
  ZREVRANGEBYSCORE feed:u_98765 (980 -inf LIMIT 0 20
  → Returns: [post_U (score: 980), ..., post_AN (score: 961)]
  → next_cursor = base64encode({"score": 961, "post_id": "post_AN"})

  # The cursor is opaque to the client — they just pass it back.
  # Using exclusive range "(980" ensures no duplicates even if
  # multiple posts share the same score (use post_id as tiebreaker).
Cursor Encoding: The cursor is typically a base64-encoded JSON object containing the last seen score and post ID. It is opaque to the client — the client treats it as an arbitrary string and passes it back on the next request. This allows the server to change the cursor format without breaking clients. Never expose raw timestamps or database IDs in cursors, as this leaks internal implementation details.

7. Trade-offs

Decision Option A Option B Recommendation
Push vs. Pull vs. Hybrid Fan-out Push (fan-out on write): Pre-compute feeds on publish. O(1) reads but O(N) writes where N = follower count. Breaks for celebrities (N = millions). Pull (fan-out on read): Compute feed on demand. O(1) writes but O(M) reads where M = following count. Slow reads at scale (300 queries per feed load). Use hybrid: push for normal users (<100K followers), pull for celebrities. This bounds write amplification while keeping reads fast. The merge at read time adds ~10ms — negligible compared to the 17-minute fan-out a celebrity post would require in pure push.
Chronological vs. Ranked Feed Chronological: Simple, predictable, no ML infrastructure needed. Users see everything in time order. Important posts get buried by high-volume posters. Lower engagement metrics. Ranked (ML-based): Surfaces relevant content, increases engagement 20–40%. Requires feature engineering, model training, A/B testing infrastructure. Users may feel manipulated or miss posts from certain friends. Use ranked feed as default with a chronological toggle for users who prefer it (like Twitter’s “Latest Tweets”). Start with a simple heuristic ranking (recency + engagement + relationship) and evolve to ML-based ranking as the system matures.
Cache Invalidation Strategy Write-through: Update cache on every write. Always consistent. Higher write latency (must wait for cache update). More complex write path. Write-behind (async): Update cache asynchronously after DB write. Lower write latency. Cache may be briefly stale. Simpler write path but requires a queue. Use write-through for the feed cache (fan-out writes directly to Redis) and write-behind for engagement counts (like/comment counts updated asynchronously). Feed correctness matters more than engagement count precision.
Consistency Model Strong consistency: A new post appears in all followers’ feeds immediately. Requires synchronous fan-out. Very high latency for writes. Not practical at scale. Eventual consistency: A new post may take 1–5 seconds to appear in all feeds. Asynchronous fan-out via message queue. Acceptable UX — users don’t notice a 2-second delay. Use eventual consistency. The author sees their own post immediately (read-your-writes consistency via local cache), but followers may see it after a short delay. This is the standard approach at Facebook, Twitter, and LinkedIn.
Feed Cache Size per User Small cache (100 posts): Lower memory usage. Frequent cache misses for users who scroll deep. Requires DB fallback for older posts. Large cache (1,000+ posts): Higher memory usage (10x). Rare cache misses. Most feed requests served entirely from cache. Higher fan-out cost (more entries to maintain). Cache 500 posts per user as a balance. This covers ~2 days of content for most users. For users who scroll beyond the cache, fall back to a pull-based query against the Posts DB. 500 post IDs × 8 bytes = 4 KB per user × 500M users = 2 TB total — feasible for a Redis cluster.
Post Storage: SQL vs. NoSQL SQL (PostgreSQL): Strong consistency, ACID transactions, rich query support. Harder to shard. Well-understood operational model. NoSQL (Cassandra/DynamoDB): Built for horizontal scaling. Excellent write throughput. Limited query flexibility. Eventual consistency by default. Use SQL (PostgreSQL) sharded by user_id for posts. The query pattern is simple (get posts by user_id, ordered by time), which SQL handles well. Sharding by user_id ensures all posts by a user are on the same shard. At extreme scale (1B+ users), consider Cassandra for its native horizontal scaling.
Interview Tip: When discussing trade-offs, always tie your recommendation to the specific requirements. “We chose eventual consistency because our NFR explicitly states availability over consistency, and a 2-second delay for a social media post is imperceptible to users. However, we ensure read-your-writes consistency for the author — it would be confusing if you published a post and couldn’t see it in your own feed.” This shows you understand the nuances, not just the theory.
