Design a Distributed Key-Value Store

Design a highly available, partition-tolerant distributed key-value store similar to Amazon DynamoDB, Apache Cassandra, or Riak — supporting tunable consistency, automatic data partitioning, replication, and failure handling at massive scale.

Hard Storage & Data Asked at: Amazon, Google, LinkedIn

1. Requirements

Functional Requirements

  • put(key, value) — Insert or update a value associated with a key.
  • get(key) — Retrieve the value associated with a key.
  • delete(key) — Remove a key-value pair from the store.
  • Automatic scaling — The system should automatically distribute data across nodes and rebalance when nodes are added or removed.
  • Tunable consistency — Clients can choose consistency levels per request (strong, eventual, or somewhere in between).
  • High availability — The system continues to accept reads and writes even when some nodes are down.

Non-Functional Requirements

  • Low latency: <10ms p99 for both reads and writes.
  • High availability: 99.99% uptime (less than 52 minutes of downtime per year).
  • High throughput: Handle 100K+ operations per second per cluster.
  • Durability: Once a write is acknowledged, the data must not be lost (even if individual nodes fail).
  • Scalability: Scale horizontally to handle billions of keys and tens of terabytes of data.
Interview Tip: Always clarify whether the interviewer wants a CP system (like HBase/ZooKeeper) or an AP system (like Cassandra/DynamoDB). This single decision shapes the entire architecture. If they say “highly available,” lean toward AP with tunable consistency.

2. Capacity Estimation

Assumptions

Average value size 1 KB JSON objects, serialized data
Total number of keys 10 billion Accumulated over time
Replication factor 3 Each key stored on 3 nodes

Storage Calculation

Raw data per key   = 100 B (key) + 1 KB (value) + 100 B (metadata)
                   ≈ 1.2 KB per key-value pair

Total raw storage  = 10B keys × 1.2 KB
                   = 12 TB

With 3x replication = 12 TB × 3
                    = 36 TB total storage

Per-node storage (20 nodes) = 36 TB / 20
                             = 1.8 TB per node

Throughput Calculation

Bandwidth per operation = ~1 KB (avg value)
Total bandwidth         = 100K ops/sec × 1 KB
                        = 100 MB/sec cluster-wide

Per-node throughput (20 nodes) = 100 MB/sec / 20
                                = 5 MB/sec per node (easily handled)
Key Insight: The storage requirement (~36 TB) is modest for modern hardware. The real challenge is not raw storage but achieving low-latency access, handling concurrent operations, maintaining consistency across replicas, and recovering from failures — all at 100K+ ops/sec.

3. API Design

PUT /v1/kv/{key}

Insert or update a key-value pair. The value is sent in the request body.

Request:
  PUT /v1/kv/user:12345
  Headers:
    Content-Type: application/octet-stream
    X-Consistency: quorum          // one | quorum | all
    X-Timestamp: 1713100800000     // client-side timestamp (optional)
  Body: <binary value>

Response (200 OK):
{
  "key": "user:12345",
  "version": "v3",
  "timestamp": 1713100800000,
  "replicas_acked": 2
}
GET /v1/kv/{key}

Retrieve the value associated with a key.

Request:
  GET /v1/kv/user:12345
  Headers:
    X-Consistency: quorum          // one | quorum | all

Response (200 OK):
{
  "key": "user:12345",
  "value": "<base64-encoded value>",
  "version": "v3",
  "timestamp": 1713100800000
}

Response (404 Not Found):
{
  "error": "KEY_NOT_FOUND",
  "message": "Key 'user:12345' does not exist"
}
DELETE /v1/kv/{key}

Delete a key-value pair. In distributed systems, deletes are typically handled as tombstones (a special marker indicating deletion) rather than immediate physical removal.

Request:
  DELETE /v1/kv/user:12345
  Headers:
    X-Consistency: quorum

Response (200 OK):
{
  "key": "user:12345",
  "deleted": true,
  "tombstone_expiry": "2025-04-14T00:00:00Z"
}
Tombstones Matter: In a distributed KV store, you cannot simply remove a record. If you delete on node A but node B is temporarily down, when B comes back it still has the key and would replicate it back. Instead, write a tombstone (a deletion marker with a timestamp). Tombstones are garbage-collected after a configurable grace period (e.g., 10 days in Cassandra’s gc_grace_seconds).

Storage Engine: LSM-Tree vs B-Tree

The choice of on-disk storage engine fundamentally affects read/write performance characteristics.

LSM-Tree (Log-Structured Merge-Tree)

Write-optimized. All writes go to an in-memory buffer (memtable), then are flushed to sorted immutable files (SSTables) on disk. Background compaction merges SSTables.

  • Writes: O(1) amortized — sequential I/O only
  • Reads: O(log N) — may check multiple SSTables
  • Space amplification: Higher (multiple copies during compaction)
  • Used by: Cassandra, HBase, RocksDB, LevelDB

B-Tree

Read-optimized. Data is stored in a balanced tree structure on disk. Writes require finding and updating the correct page in-place, potentially causing random I/O.

  • Writes: O(log N) — random I/O for page updates
  • Reads: O(log N) — single tree traversal
  • Space amplification: Lower (in-place updates)
  • Used by: MySQL (InnoDB), PostgreSQL, MongoDB (WiredTiger)
Why LSM-Trees Dominate KV Stores: Distributed KV stores typically choose LSM-trees because (1) writes are the bottleneck in distributed replication, (2) sequential I/O is dramatically faster on both HDDs and SSDs, and (3) the compaction process naturally handles tombstone cleanup. Cassandra, DynamoDB, and RocksDB all use LSM-tree variants.

Key Components

  • Coordinator Node: Any node that receives a client request acts as the coordinator. It determines which nodes own the key (via consistent hashing) and forwards the request to those nodes.
  • Consistent Hash Ring: Maps keys to nodes. Uses virtual nodes (150–200 per physical node) for balanced distribution. See the Consistent Hashing page for details.
  • Replication: Each key is stored on N nodes (typically N=3). The coordinator writes to all N replicas and waits for W acknowledgments before responding to the client.
  • Gossip Protocol: Nodes exchange membership and health information peer-to-peer. No single point of failure for cluster coordination.
Why Leaderless? A leader-based design (like Raft/Paxos) provides strong consistency but creates a single point of failure per partition and adds latency (writes must go through the leader). A leaderless design allows any node to accept writes, maximizing availability — at the cost of potential conflicts that must be resolved.

6. Deep Dive

6a. CAP Theorem & System Classification

The CAP theorem states that a distributed system can provide at most two out of three guarantees: Consistency, Availability, and Partition tolerance. Since network partitions are inevitable, the real choice is between CP (consistency + partition tolerance) and AP (availability + partition tolerance).

HBase CP Rejects writes to affected regions Strong consistency (single leader per region)

DynamoDB AP (tunable) Continues serving; may return stale reads Eventually consistent (strong optional)
Riak AP Continues serving; uses vector clocks for conflicts Eventually consistent
Interview Tip: Don’t just say “we pick AP.” Explain why: for a key-value store serving user-facing traffic, a few milliseconds of stale data is usually acceptable, but downtime is not. Shopping carts (Amazon’s original Dynamo use case) should always be writable — even if two conflicting carts must be merged later.

Data is distributed across nodes using consistent hashing with virtual nodes. Each physical node is assigned 100–200 virtual nodes (tokens) on the hash ring, ensuring balanced data distribution.

When a node joins or leaves, only the keys in the affected token ranges are redistributed — approximately K/N keys move (where K is total keys, N is number of nodes). This is the minimum possible redistribution.

6c. Replication & Quorum Consensus

Each key is replicated to N nodes (the replication factor, typically 3). The coordinator writes to all N replicas but only waits for W acknowledgments (write quorum) before responding to the client. Similarly, reads query all N replicas but only wait for R responses (read quorum).

The Quorum Formula

Strong Consistency Guarantee: If W + R > N, at least one node in the read quorum must have the latest write. This guarantees the client always sees the most recent value. The overlapping node ensures no stale read can occur. 
N = Number of replicas (typically 3)
W = Number of write acknowledgments required
R = Number of read responses required

Strong consistency:  W + R > N
                     Guarantees overlap between read and write sets

Example with N=3:
  W=2, R=2 → 2+2=4 > 3 ✓ (strong consistency, balanced)
  W=3, R=1 → 3+1=4 > 3 ✓ (strong consistency, fast reads)
  W=1, R=3 → 1+3=4 > 3 ✓ (strong consistency, fast writes)
  W=1, R=1 → 1+1=2 < 3 ✗ (eventual consistency, fastest)

6d. Consistency & Conflict Resolution

In an AP system, concurrent writes to the same key on different nodes can create conflicting versions. The system needs a strategy to detect and resolve these conflicts.

Vector Clocks

A vector clock is a list of (node, counter) pairs that tracks the causal history of a value. Each node increments its own counter on every write. By comparing vector clocks, the system can determine if one version happened before another, or if they are concurrent (conflicting).

Conflict Resolution Strategies

Strategy How It Works Pros Cons Used By
Last-Write-Wins (LWW) Attach a timestamp to each write. Highest timestamp wins. Simple, no client involvement Data loss (silently drops concurrent writes); clock skew issues Cassandra (default)
Application-level resolution Return all conflicting versions to the client. Client merges them. No data loss; application-specific merge logic Complex client code; increased read latency Riak, DynamoDB (shopping cart)
CRDTs Use conflict-free replicated data types that can be automatically merged. Automatic resolution; mathematically guaranteed convergence Limited to specific data structures (counters, sets, maps) Riak 2.0 (data types)
Vector Clock Limitation: Vector clocks grow with the number of nodes that write to a key. In large clusters, this metadata can become significant. Solutions include (1) truncating old entries (DynamoDB uses a timestamp-based truncation), (2) using dotted version vectors (an optimization), or (3) using LWW timestamps instead (simpler but lossy).

6e. Failure Handling

A distributed KV store must handle three categories of failures: detecting failures, handling temporary failures, and recovering from permanent failures.

Failure Detection: Gossip Protocol

Each node periodically (every 1 second) picks a random peer and exchanges membership state. If a node hasn’t been heard from within a timeout (e.g., 8 seconds), it is marked as suspected. After further confirmation from multiple nodes, it is marked as down.

Temporary Failures: Sloppy Quorum & Hinted Handoff

When a replica node is temporarily down, the system uses a sloppy quorum: instead of failing the write, it sends the data to the next healthy node on the ring. That node stores a hint (a note saying “this data belongs to node X”). When node X recovers, the hinted data is transferred back.

Sloppy Quorum Caveat: With sloppy quorum, W=2 does not guarantee strong consistency even if W+R > N. The write may have gone to a hinted node outside the normal replica set. During this window, a read with R=2 might contact the original replicas (which don’t have the latest write) and return stale data. Sloppy quorum trades consistency for availability.

Permanent Failures: Anti-Entropy with Merkle Trees

When a node is permanently lost (disk failure, decommissioned), its data must be reconstructed from replicas. To efficiently detect which keys are out of sync between replicas, the system uses Merkle trees (hash trees).

Bloom Filter Deep Dive

Bloom filters are critical for read performance. Without them, a read for a non-existent key would need to check every SSTable on disk.

Bloom Filter Properties:
  - Space: ~10 bits per key (1.25 bytes per key)
  - False positive rate: ~1% with 10 bits/key and 7 hash functions
  - False negatives: IMPOSSIBLE (if bloom filter says "no", key is definitely not there)
  - Time: O(k) where k = number of hash functions (constant, typically 7)

Example:
  SSTable with 1M keys → Bloom filter = 1.25 MB
  10 SSTables → 12.5 MB of bloom filters (easily fits in RAM)
  
  Without bloom filter: 10 disk reads per miss
  With bloom filter: 0.1 disk reads per miss (99% filtered out)
Interview Tip: The write path and read path are the most commonly asked follow-up questions for KV store design. Be prepared to walk through each step. Key points to emphasize: (1) commit log ensures durability, (2) memtable enables fast writes, (3) bloom filters prevent unnecessary disk reads, (4) read repair heals inconsistencies passively.

7. Trade-offs

Decision Option A Option B Recommendation
Strong vs Eventual Consistency Strong (W+R>N): Every read returns the latest write. Higher latency (must wait for quorum). Lower availability during partitions. Eventual (W=1, R=1): Reads may return stale data. Lowest latency. Highest availability. Conflicts must be resolved. Default to quorum (W=2, R=2, N=3) for a good balance. Offer tunable consistency so clients can choose per-request based on their needs.
LSM-Tree vs B-Tree LSM-Tree: Excellent write throughput (sequential I/O). Higher read amplification. Background compaction uses CPU/I/O. Space amplification during compaction. B-Tree: Excellent read performance (single lookup). Write amplification from in-place updates. No compaction overhead. More predictable latency. Use LSM-Tree for write-heavy distributed KV stores (Cassandra, DynamoDB). Use B-Tree for read-heavy, single-node databases (PostgreSQL, MySQL).
In-Memory vs Disk-Based In-memory (Redis): Sub-millisecond latency. Limited by RAM capacity. Data loss risk without persistence. Expensive at scale. Disk-based (Cassandra): Higher latency (1–10ms). Virtually unlimited capacity. Durable by default. Cost-effective for large datasets. Use disk-based with memory caching for a general-purpose KV store. Use in-memory for caching layers or latency-critical hot data.
Single-Leader vs Leaderless Single-leader (per partition): Strong consistency is straightforward. Leader is a bottleneck and SPOF. Failover adds latency. Used by HBase, MongoDB. Leaderless: Any node accepts writes. Higher availability. Conflicts possible. More complex consistency. Used by Cassandra, DynamoDB, Riak. Use leaderless for AP systems prioritizing availability. Use single-leader for CP systems where strong consistency is non-negotiable.
Vector Clocks vs LWW Timestamps Vector clocks: Detect true conflicts (concurrent writes). No data loss. Growing metadata overhead. Complex client-side resolution. Last-Write-Wins (LWW): Simple timestamp comparison. No conflict resolution needed. Silent data loss on concurrent writes. Clock skew issues. Use LWW for simplicity when occasional data loss is acceptable (Cassandra default). Use vector clocks when every write matters (shopping carts, collaborative editing).
Gossip vs Centralized Coordination Gossip protocol: No SPOF. Eventually consistent membership. O(log N) convergence time. Simple to implement. Used by Cassandra, DynamoDB. ZooKeeper/etcd: Strongly consistent membership. Immediate convergence. Additional infrastructure dependency. SPOF if coordination service fails. Use gossip for AP systems (consistent with the leaderless philosophy). Use ZooKeeper for CP systems or when strong membership consistency is required.
Compaction Strategy Size-tiered (STCS): Merge SSTables of similar size. Better write throughput. Higher space amplification (up to 2x). Good for write-heavy workloads. Leveled (LCS): Maintain non-overlapping key ranges per level. Better read performance. Higher write amplification. More predictable space usage. Use size-tiered for write-heavy workloads (logging, time-series). Use leveled for read-heavy workloads (user profiles, product catalog).
Interview Tip: The strongest candidates don’t just list trade-offs — they connect them to real systems. “Cassandra uses LWW because most of its use cases (time-series, logging) are append-heavy and idempotent, so losing a concurrent write is rarely a problem. DynamoDB’s original shopping cart use case required vector clocks because merging two carts is better than losing items.”
